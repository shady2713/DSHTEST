## 问题

应用必须遵循可复现的 DSH 发布及其工程规则，同时保留归属明确的本地差异。

## 提案

对于新选定的外部插件路线，[可安装插件计划](../architecture/2026-10-04-web-testing-installable-plugin-plan.zh.md)替代下文独立应用身份、安装器及源码分叉交付假设。固定基座继续作为初始接口核对目标；原版 DSH 的实际安装兼容性由 S0 验证，当前尚未确认。历史记录及无关上游改动继续保留。

本文件是基座身份、上游规则继承和集成差异的真源。它规定开发方式，不代表任何代码、补丁或安装包已实现、已验证。产品范围见[产品需求](../feature/2026-09-28-web-testing-requirements.zh.md)，运行更新协议见[DD12](../architecture/2026-09-28-web-testing-design-models-release.zh.md)。

工具结果补齐保留 TOOL_OUTCOME_UNKNOWN / TOOL_NOT_STARTED 的证据边界，不能据此判业务失败、无副作用或完成。此前已经关闭的异常历史仍须单独验证；模型恢复和领域恢复分别验收。上游已包含修复只说明源码可用，不代表本应用已通过验收。

此前从 dsh-v0.1.7-rc.2 升级到 dsh-v0.2.0-rc.1 时，保留了共同历史和未提交的应用工作，并通过文件摘要核验仓库外备份。两个旧标签的 Session writer V4 和 storage-sqlite schema 1 均未变化；该轮探针连同原输入保留为历史证据，不代表当前选定版本通过。阶段状态和后续执行顺序归[协作指南](2026-09-28-web-testing-agent-guide.zh.md)。

## 增量升级至 rc.2

以下源码变化用于确定定向复验范围，不代表应用运行验收结果，也不改变浏览器 R0–R3 顺序、M1 有限开发许可或最终验收阈值。

## 规则继承

完整保留官方仓库共同历史及工程体系。适用的根、祖先、最近目录规则和引用文件共同构成研发要求；本应用只补充明确归属的业务约束，不复制一套“兼容版 DSH 规范”。源码只读约束针对被测项目，不禁止已获授权的本应用研发修改。

| 文件类别 | 引入与升级时的处理 |
|---|---|
| AGENTS.md、CLAUDE.md 等规则入口 | 保留上游正文、链接关系与作用范围；Windows 上核对实际目标内容，接收上游新增/移动/删除，不仅比较文件名 |
| .agents/skills、架构、开发、测试及包 README | 按实际任务加载关联规则；官方研发 Skills 与用户业务 Skills 分别装配，不同名覆盖 |
| lint、类型、覆盖、构建、生成器及 CI | 保留官方机制，适配仓库/环境身份；从源重新生成，不降门槛或手改生成结果 |
| vendor/native、格式历史和发布材料 | 沿用官方同步、版本及兼容流程；保留许可证和署名；旧已发布格式不能改写 |
| 本应用插件和局部约束 | 当前消费方、数据所有者和目录明确后再创建；局部规则链接到唯一产品事实源，不复制整份需求 |
| 用户凭证、Skills、任务与证据 | 属于运行数据；通过配置/数据迁移处理，Git 更新不得覆盖它们 |

入口：[根规则](../../../../AGENTS.md)、[包规则](../../../../packages/AGENTS.md)、[架构](../../../../docs/architecture.zh.md)、[文档规则](../../../../docs/AGENTS.md)、[测试政策](../../../../docs/testing.zh.md)。这些链接不穷尽所有适用规则；M0-T01 生成实际 RulesMap。

规范冲突按实际语义解决，不机械采用“最近文件”“更严格的一条”或“保留自己的版本”。优先调整本应用实现与补充文案；未解决的冲突阻止该组合验收。官方规则入口若需要引用本应用约束，使用简短链接并登记差异，不能覆盖正文。DSH 的项目名不授权初始化另一个个人 Harness 治理体系。

运行时业务 Skill 的指令、脚本、MCP 或 PTC 必须经过产品实际策略。官方研发工具可改代码，不构成本产品修改被测代码的许可。

## 文档语言与入口

遵循固定基座的[官方双语规范](../../../../docs/i18n/README.zh.md)，不另设“英文给 AI、中文给用户”或英文优先的规则。中英文同等权威，可以任一语言先编写和审阅；配对内容必须同义，出现冲突时核对已确认需求和实际依据并修正，不能按语言自动裁决。

适用范围及例外由官方规范和实际检查器决定。正式入库的适用文档使用同目录三文件：英文 `foo.md`、中文 `foo.zh.md`、一致性记录 `foo.i18n.yaml`；README 对应 `README.md`、`README.zh.md`、`README.i18n.yaml`。按官方要求维护语言切换链接、标题和列表结构、表格、代码及目标语言链接；需求编号、接口标识和行为约束保持一致。AGENTS 等官方明确排除的规则文件沿用其英文维护方式，不机械增加译本或自设排除项。

修改任一语言时，当前编辑 agent 按官方术语同步另一语言，确认语义后使用官方配对命令记录并验证；不自动启动专用翻译流程。结构和哈希通过不能代替语义核对，不能只更新一致性记录掩盖未同步的译文。生成文档和冻结历史按各自官方规则处理，不手改生成源或重新翻译冻结记录。

17 组详细规范按本仓库的 proposed Agent Note 格式维护，分别归入 feature、architecture、process 和 testing；[应用交接页](../../../../docs/developer/web-testing/README.zh.md)作为仓库内入口，链接到各规范的归属文件，不维护第二份副本。RepositoryMap 登记当前路径和事实归属。proposed 保留已确认范围，同时明确设计和执行计划尚未实现；实现后把实际约定、配置和用户说明放到所属目录，并更新原提案的生命周期与链接。

CODE_ROOT 是 Git／工程根目录；DOC_ROOT 是其中的 docs/developer/web-testing 目录。根 README 三文件保留上游正文，仅增加应用交接导航；AGENTS 和官方规则保持原有归属。接手仓库时先读官方规则，再读本应用协作提案及关联任务。长期维护的规范和任务指令必须位于仓库内，不依赖个人目录或被忽略文件。完整提交身份、锁文件摘要和实际命令输出属于本地证据，放在已被忽略的 .artifacts/web-testing 目录；缺失证据时从 Git 和实际检查重新生成，不得视为已通过。维护文件按官方引用规范使用标签、PR 和相对链接。后续升级沿共同 Git 历史合并，保留少量导航补充，并检查配对及应用引用。

## 集成成本登记

M0-T01 建立 IntegrationSurfaceRegister，M0-T08 审阅，每个功能任务更新自己触及的行。每行至少有：

- 所属任务、实际目录/文件、上游版本、当前消费方与数据所有者。
- 类型：公共扩展点／内部修改／原生封装；接口、Host/Client 边界、取消及资源所有权。
- 是否涉及持久格式、旧历史读取、生成器、双语文档及适用检查。
- 更简单的合法替代、运行证据、采用理由、升级时需重验的场景。
- 本应用差异的负责人、补丁来源、预期移除条件和实际维护负担。

“窄改动”不是可行性证据。规范符合、产品有效和升级兼容分别取证；包数量不按架构图框数机械增加。附件引用/删除扩展与安装恢复协调入口必须显式登记，不藏进通用适配器。P02 用实际负载选最小合格持久结构；没有测量依据不预建完整事件溯源框架。

## 后续升级

1. 主 agent 固定目标发布及 SHA，比较旧基座、上游变化和本应用差异；已有工作不因每次发布自动重启。
2. 在隔离工作区准备升级，审查规则、配置、协议、模型、浏览器、持久格式、遥测、安装和发布目标。文本无冲突不等于行为兼容。
3. 基于共同 Git 历史适配。保留仍必要的产品差异，移除上游已经完整覆盖且经回归证明的重复实现；官方删除/更名按新结构迁移。
4. 更新 RulesMap、RepositoryMap、IntegrationSurfaceRegister、PatchManifest 和锁文件/BOM；按官方生成入口重建，检查受影响使用方，不只检查新增行。
5. 执行适用官方检查和本产品回归，重跑受影响 P/V 场景。保留旧会话、运行批次、共享附件与失败历史材料；缺平台/凭证不得记通过。
6. 形成可审阅的升级产物及数据迁移/回退证据。合入、推送、发布按用户明确授权办理；运行版本切换遵守 DD12。

不得下载新版文件夹覆盖旧仓库，不热换正在运行的 Host、浏览器、模型路由、规则或执行器。普通更新检查所有未结算批次；旧程序无法继续时按 DD12 的封存、兼容检查、recovery-only 与关联新批次恢复。封存不等于取消/完成，UNKNOWN 不清零，Git 回退也不等于数据回滚。

升级交接保存基线、规则变化、补丁处置、迁移结果、实际命令和证据、剩余缺口。G01 证明规则被实际应用，G16 证明升级后规则、实现和结果一致；缺失验证保持未执行。
