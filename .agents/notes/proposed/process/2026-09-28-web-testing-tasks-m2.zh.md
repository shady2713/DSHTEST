# Agent Note: 开发任务：M2 测试闭环

Status: proposed

[English](2026-09-28-web-testing-tasks-m2.md) | 中文

## 问题

分析、确认用例、真实执行、证据及报告必须形成可使用的测试流程。

## 提案

阶段准入与当前任务状态以协作指南及其 TaskRegister 为准；历史探针结果不代表这些实施卡已完成。任务接口、改动归属、独立复核、检查和交接格式以[agent（智能体）开发与协作指南](2026-09-28-web-testing-agent-guide.zh.md)为准。改动归属须经 RepositoryMap 解析为真实路径，并在派发时登记。前置完成指交付物已被消费方和独立复核者接收；提交代码或口头宣布完成不等于满足前置，明确标注的分项依赖除外。

本阶段 9 张卡，目标是一条完整真实业务链，最终功能范围仍由全部需求决定。T07 只依赖已定义的 ReportRevision 前置约定，T08 才接通真实报告后清理，因此不存在数据清理与报告互等的开发依赖。

**M2-T01：扩展完整业务 fixture（测试前置数据）与历史材料**

**目标：** 给分析到报告闭环提供可独立判断的 F2／F3／F4 材料。

**前置：** `M1-T06`、`M1-T07`。

**阅读：** 实施计划 F1–F6、AC05／AC07／AC09／AC22／AC50、DD04。

**改动归属：** 官方 fixture 与测试材料目录；沿用 M0 FixtureManifest。

**执行分工：** 材料 subagent 扩展公开业务系统，独立验收者持有答案；可提前准备独立静态材料，但本卡需接收 M1 真实历史后才完成。

**步骤：**

1. 扩展双入口、双角色的同记录创建—审批／驳回—查看流程，提供正常、边界、文件、换行及植入缺陷版本；补齐代表性不同语言／多代码根材料。
2. 加入可独立观察的异步后端入口和只读日志；保存每个版本的源码、运行标识、初始数据及复位办法。
3. 从 M1 真实资产演进一个业务变化版本，保存未变化对照；独立维护标准答案，不将隐藏缺陷清单输入产品当需求。

**交付：** 扩展 FixtureManifest、业务状态机及独立 Oracle、两个可追溯版本和 F3 初版；供 T02 至 T09 使用。

**接续：** T02–T09 使用同版本 FixtureManifest，跨语言、双角色和旧记录均有可复位入口；Oracle 的访问权不随代码材料一同交给产品 agent。

**正常验收：** 验收者可独立定位同一业务记录、确认状态变化及错误版差异，历史资产确实来自前一版本。

**失败对照：** 不同记录拼接流程、用新材料伪造历史、把缺陷答案泄给产品的材料不合格。

**停止条件：** 业务规则不确定、没有独立观察或复位失败时，先补材料，不以工具生成用例充当验收答案。

**M2-T02：全项目读取、快照与需求推导**

**目标：** 从用户提供的全部代码形成有来源的功能清单与候选需求。

**前置：** `M1-T03`、`M1-T04`、`M1-T05`、`M1-T06`、`M2-T01`。

**阅读：** DD04／DD06／DD09、AC05／AC07／AC15／AC44、G08。

**改动归属：** web-test-analysis、源码快照服务和 Runtime 的版本提交接口。

**执行分工：** 分析 subagent 负责读取和推导，持久化 owner 仅提供冻结快照接口；可委派只读材料盘点，不让多个 subagent 同时写 SourceSnapshotRevision。

**步骤：**

1. 建立多根材料清单和可读性记录，处理编码、大文件、链接、扫描时变更；保护密钥材料，不把不可读部分静默当作没有功能。
2. 保存实际使用的版本内容／摘要与引用，区分 Git 基线、未提交修改、运行版本声明和观察；源码版本不自动等于线上版本。
3. 通过已配置模型生成模块、入口、角色、业务流程和候选预期；将代码证据、用户规则、skill（技能）知识及页面事实分开，冲突转为具体问题。
4. 复用 P06 的独立验证方法，将业务意图、通用规则与实现推断显式分类；输出 criticalRuleReview，不凭实现清楚就免除关键规则确认。

**交付：** SourceSnapshotRevision、FeatureInventory／RequirementDraft、来源与缺口索引；T03 生成用例，后续历史与报告复用。

**接续：** T03 收到带来源和 criticalRuleReview 的候选需求；M4-T05 比较不可变快照，报告引用保存内容而非活动文件。

**正常验收：** 跨语言材料无需模板即可进入分析，结论能定位保存的源片段；扫描后原文件改变不使历史引用跳到新内容。

**失败对照：** 代码实现与用户规则相反、文件不可读及扫描中变更均显式呈现，不能把实现当正确预期。

**停止条件：** 无法保证使用材料的一致性时暂停该部分结论，其他有依据模块可继续；不擅自修改代码以便解析。

**M2-T03：用例、范围、澄清及动态覆盖**

**目标：** 把需求推导转成可执行、可询问、可计数的版本化计划。

**前置：** `M2-T02`。

**阅读：** DD04／DD05／DD06、报告规格、AC10／AC27／AC28／AC41／AC53。

**改动归属：** analysis 规划模块、Runtime 计划提交和 Client 确认卡片。

**执行分工：** 规划 subagent 负责用例与覆盖语义，Client owner 接确认卡片；Runtime 约定变动由集成人合入。验收者检查关键规则未确认的反例。

**步骤：**

1. 生成场景、用例、步骤、预期断言和适用执行实例；范围默认完整测试，专项按需勾选，角色／视口按适用性展开，不制造无意义笛卡尔积。
2. 开测前集中澄清预期冲突、分辨率及必要信息，答案固化为计划／用例版本；只生成用例时只列准备动作，不修改业务数据。
3. 定义开始条件、范围修改与新增发现去重；运行中新疑问阻塞受影响实例并保留报告项，用户确认后产生新用例再补测。动态分母变更可追溯。
4. 关键金额／权限／状态等逐条归组确认，范围批准和操作许可不能替代规则确认；implementation-only 的必测业务断言保留待确认分母，不能自动删除或变通过。

**交付：** PlanRevision／CaseRevision／ExecutionInstance、澄清与范围变更协议、完整性检查；T04 按此调度，T08 按此统计。

**接续：** T04 获得冻结计划与实例依赖，T07 获得准备要求，T08 获得分母定义；确认变动生成新版本并说明受影响实例。

**正常验收：** 同一业务流程有可验证预期和依赖，用户自然语言／选项生成一致计划；计划范围与实例数可解释。

**失败对照：** 缺预期、重复新发现、工具自动移出失败项和“只生成用例却准备数据”被拒绝；未验证仍留在相应分母。

**停止条件：** 关键预期不清时先询问而非编答案；部分范围未清可整理用例，但不得提前执行其业务变更。

**M2-T04：真实动作执行与最小持久调度**

**目标：** 按已确认用例进行真实页面操作，并从第一条动作起防止重复业务。

**前置：** `M2-T03`、`M1-T03`、`M1-T05`、`M1-T07`。

**阅读：** DD02／DD06／DD07／DD08、AC13／AC37／AC46、V05／V06。

**改动归属：** Runtime 执行调度、Browser Use 实际动作实现和 Session 事实接入。

**执行分工：** 执行 subagent 负责持久调度与实际动作，Browser owner 承接有界适配；动作槽位／Runtime 主循环由单一 owner 修改，独立核对业务次数。

**步骤：**

1. 分配 StepCursor、stepRevision 与 actionSlotId，先保存动作意图，再重验环境授权／目标代次后派发；记录发送状态和业务结果，成功提交后才推进。
2. 实现实际点击、输入、CRUD 等最小集合，步骤结果和工具调用进入正确 Session；业务断言等待 T05，执行成功不直接等于用例通过。
3. 实现最小中断恢复：已完成槽位不重派，已发未知先观察核实，确定未发生才合法重试；复试有限且保留原失败。

**交付：** ActionRequest／Result、持久 StepCursor、执行状态迁移和真实动作证据；T05／T06 及 M3 扩展同一调度器。

**接续：** T05 接收动作事实和观察；T06／T07 使用同一授权与槽位入口；M3 扩展现有调度器，不新增恢复循环。

**正常验收：** 同一计划完整执行一条真实流程，每个页面动作可对应业务记录和持久事实。

**失败对照：** 崩溃在业务已发生但结果未存、旧槽位重送、目标重渲染及迟到结果均不导致重复操作；模糊结果保留未知。

**停止条件：** 需要未授权操作或无法确认源码影响时阻塞该步骤；不得以临时内存调度替代首次动作持久记录。

**M2-T05：证据、断言和视觉判断**

**目标：** 把实际观察转成可复核的判断，覆盖无设计稿场景且不过度声称正确。

**前置：** `M2-T04`。

**阅读：** DD02／DD09、报告规格、AC08／AC29／AC38、G08。

**改动归属：** 证据附件服务、analysis 断言模块及 Runtime 统计投影。

**执行分工：** 断言 subagent 负责判定与统计，附件 owner 提供保留票据／发布接口；视觉正常和缺陷 Oracle 由独立验收者维护，不能用首张截图自建真值。

**步骤：**

1. 经正式附件接口保存原件后发布引用，分开截图原字节与模型规范化图片；关联批次／实例／步骤／尝试及版本，避免临时 URL 冒充资产。
2. 实现确定性业务检查与视觉辅助判断；在固定数据／视口和稳定页面状态下检查遮挡、溢出等客观问题，不把审美差异判失败。
3. 按已提交断言计算成功、失败、阻塞、跳过及未验证；同一实例一次完整尝试形成通过，不把多次不完整流程拼成功。
4. 证据发布经 P07 保留票据协议保护；AssertionResult 区分 observationComparison 与业务 verdict，加入实现明确但规则错误、通用规则不适用及普通会话共享附件的反例。

**交付：** EvidenceRef、AssertionResult、可回放证据链及统计规则；T08 直接读取，M4 扩展复杂页面／录像。

**接续：** T06／T07 复用 EvidenceRef，T08 读取已提交 AssertionResult；M3-T05 取得证据引用 owner，M4 扩展媒体格式不改判定语义。

**正常验收：** 正常版与缺陷版可区分，报告统计能从原始事实重算；重开后原图仍可读。

**失败对照：** 首张截图自动当正确基线、页面未稳定直接判样式坏、附件损坏、证据不足和模型自报成功均不能产生确定通过。

**停止条件：** 预期或视觉依据不足则形成待确认问题／未验证，不调用修复工具，也不隐藏证据缺口。

**M2-T06：已有后端入口、只读核验与外部服务**

**目标：** 支持完整业务链的后端核实，同时守住只读源码和第三方动作边界。

**前置：** `M2-T04`、`M2-T05`。

**阅读：** DD04／DD07、AC24／AC25／AC32、V08／V15。

**改动归属：** 后端入口描述、受控命令／只读观察工具及 Runtime 授权检查。

**执行分工：** 后端适配 subagent 负责既有 API／命令和只读观察；策略 owner 审核具体参数与作用范围，外部发送对照使用隔离服务和独立计数。

**步骤：**

1. 登记已有 API／命令的参数、工作目录、作用范围和可验证效果；命令使用结构化参数并检查重定向／脚本间接写入，不开放任意 shell。
2. 接入日志与只读数据库证据，异步受理后等待真实业务终态；优先用实际只读凭证和限定查询，不凭名称宣称只读。
3. 识别支付、短信、邮件及间接触发；真实服务需独立授权，确认不存在可跳过，未知则待确认，发送结果未知不得盲重发。

**交付：** BackendDescriptor、ReadOnlyObservation、外部动作授权与对账证据；T07 数据与 M4 时间流程消费。

**接续：** T07 使用已有执行入口准备／清理；M4-T04 使用只读终态观察，报告收到可定位的后台事实而非模型总结。

**正常验收：** 合法已有入口和只读查询能完成业务核实，授权发送在具体次数／记录范围内执行。

**失败对照：** 命令试图改源码、数据库写入、服务未知、回执丢失与授权过期有不同拒绝／等待结果；后台受理不等于完成。

**停止条件：** 无法判定命令副作用或第三方状态时阻塞该动作，保留其他可执行实例，不自行启动被测服务。

**M2-T07：测试数据、文件与清理台账**

**目标：** 让数据准备与后处理可追踪，并保留复现和复测所需材料。

**前置：** `M2-T03`、`M2-T04`、`M2-T05`、`M2-T06`。

**阅读：** DD04／DD07／DD09、AC33／AC50、报告规格。

**改动归属：** Runtime DataLedger、受控材料生成和清理计划服务。

**执行分工：** 数据 subagent 负责 DataLedger、材料和清理计划；报告 owner 提供已冻结 ReportRevision 查询约定，不等待报告 UI。共享资产删除仍归附件 owner。

**步骤：**

1. 用已确认计划生成数据准备步骤；生成文件只写本应用暂存区，记录真实格式／编码／换行／内容与校验，不碰源码目录。
2. 所有准备动作同样走授权、动作槽位及事实提交；记录新旧数据来源、创建批次和保留理由，不承诺旧数据删除可自动回滚。
3. 设计清理入口强制要求已提交初始 ReportRevision，保护失败复现／复测依赖，只清符合规则的新成功测试数据；清理过程可恢复，结果用于新报告版本。

**交付：** DataLedger、GeneratedFixture、CleanupPlan／Result 和报告前置校验接口；T08 集成真实初始报告后触发。

**接续：** T08 先提交真实报告再调用清理，随后生成新报告版本；本卡交付可拒绝“无初始报告”的真实服务测试，避免双向依赖。

**正常验收：** 准备后真实页面使用生成文件，数据可追踪；满足初始报告门槛才能按计划清理，失败材料保留。

**失败对照：** 仅生成用例、报告未提交、旧数据误纳清理、共享复测依赖及中断重开不会越界删除或伪报清理完成。

**停止条件：** 清理授权／归属不清则保留数据并报告；本卡可测试报告前置接口，不能伪造产品已生成真实报告。

**M2-T08：报告、缺陷包及离线导出**

**目标：** 让用户和修复 AI（人工智能）能凭材料理解、复现问题，同时保留所有未验证项。

**前置：** `M2-T05`、`M2-T07`。

**阅读：** 报告规格全文、DD09、AC14／AC31／AC39、V12、G08。

**改动归属：** 报告投影／版本提交、Client 报告视图及 HTML／Markdown／JSON 导出。

**执行分工：** 报告 subagent 负责不可变投影与导出，Client owner 只呈现同一版本；独立复现者仅拿离线缺陷包，验证材料足以复现且无宿主执行权限。

**步骤：**

1. 固定 ReportRevision 和输入事实范围，输出环境／版本、需求依据、覆盖、步骤、预期与实际、严重性、证据和未验证原因；代码位置标明事实或怀疑，不能编造根因。
2. 集成初始报告提交 → Runtime 清理 → 新报告版本，旧报告不可变；缺陷包附最小复现数据、前置、实际路径与观察，使修复 AI 无需聊天历史。
3. 导出固定版本及附件清单，核对校验和与缺失；跨盘／网络目录写入先形成可识别临时产物，完整发布后才声明成功，报告 HTML 不取得宿主脚本能力。
4. 三格式报告分别显示预期依据、实现诊断、业务待确认及各类分母；恢复更新后旧报告不改写，新组合通过 RecoveryLink 展示续测，不能拼跨版本成功。

**交付：** 报告 schema、三格式示例、单缺陷包、导出完整性及清理闭环证据；T09 会话入口调用。

**接续：** T09 获得三个格式与清理闭环；M3-T05／M4-T05 接受报告引用及版本规则，发布后不允许就地覆盖。

**正常验收：** 离线打开报告可复现 fixture 问题，统计与源事实一致，初始报告及清理后版本均可定位。

**失败对照：** 缺附件、导出中断、恶意报告文本、旧版同时导出及清理失败如实显示；不得覆盖旧报告或执行自动修复。

**停止条件：** 无法证明引用完整性时交付明确不完整包／失败状态，不宣称导出完整；缺根因证据不阻止报告事实。

**M2-T09：最小完整对话闭环与阶段复核**

**目标：** 把各模块作为一个真实应用验证，而不是独立 mock 测试的集合。

**前置：** `M1-T06`、`M2-T02`、`M2-T03`、`M2-T04`、`M2-T05`、`M2-T06`、`M2-T07`、`M2-T08`。

**阅读：** AC07／AC09／AC14／AC26–AC29／AC31、G03／G10／G15、M2 退出条件。

**改动归属：** 现有模块集成、官方组合测试、工具展示转换器与 Client 卡片。

**执行分工：** 集成主 agent 安排端到端运行；独立验收 subagent 对照 Oracle、源码状态与外部业务账。功能 owner 只修所属缺陷，不自行改预期。

**步骤：**

1. 从对话接入正常版和缺陷版，完成需求澄清、用例确认、准备、同记录业务流程、判断、报告及清理；保存完整输入与实际证据。
2. 验证“只生成用例”、运行中发现新疑问、暂停／恢复和状态查询；文本命令与卡片调用同一服务，提醒只在所属会话。
3. 独立核对源码状态、业务变化、统计和资产；补适用行为快照、工具展示、typed locale 及工程检查，记录尚未覆盖的 M4 能力。

**交付：** M2 GateEvidence、最小端到端可复现步骤、真实报告及工程检查记录；作为 M3 的恢复负载。

**接续：** M3-T01 接收真实 Run／Report／Session 负载和可复现中断点；未完成 M4 能力单列，不能混入本阶段已通过项。

**正常验收：** 真实 Loader、ctx.llm、存储、浏览器和报告链同时工作，正确对照通过，植入缺陷被有据识别。扩展 P06 保留材料复核实际检出与人工负担；自建 fixture 贯通不能独自证明陌生项目有效性。

**失败对照：** 缺后端、错误预期、模型口头成功、旧引用和缺附件不会被 UI 拼接成全绿；修复指令不能让产品修改被测代码。

**停止条件：** 核心链仍靠假实现、不能从事实重算报告或阶段对照失败时，不放行 M3；阶段通过不等于 58 项已全验收。

**阶段交接门槛**

正常版、缺陷版和待澄清版均从自然语言入口走到真实报告；首条动作就具备持久化与基本恢复。源码保护、环境授权、统计、清理和离线材料都有失败对照。复杂页面、完整并发和所有历史情形尚待 M3／M4，不得提前宣称全面测试能力完成。

## 验收标准

执行本提案中的正常和失败对照，并满足[统一验收标准](../testing/2026-09-28-web-testing-acceptance.zh.md)及相应任务的证据要求。文档迁移不代表这些条件已通过。

## 风险

单层成功可能掩盖结果丢失或报告误导，集成流程必须消费真实前置产物。
