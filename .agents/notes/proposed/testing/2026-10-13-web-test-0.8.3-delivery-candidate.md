## 修的三类缺陷

### ACL — Windows 有真实失败证据

**问题 A：函数成功返回，但 Everyone 权限仍在。** `principalsOf` 要求主体前至少
两个空白字符，而真实 icacls 每个路径的第一行是「路径 + 一个空格 + 主体」，
首条权限被整个漏掉；修改前的检查与修改后的验收共用这个解析器，于是一起漏检。

改读 `icacls /save` 的 ACL dump：平台固定的主体标识符形式，与机器语言无关，
**覆盖根目录和每个已有子项**。只在根目录上枚举正是子文件里的显式 Everyone
能活下来的原因。

**问题 B：中途失败使当前账号失去写入能力。** `/inheritance:r` 先执行，
`/remove:g` 失败，属主授权没有执行，账号读回为空且不可写。

现在属主授权排在所有删除之前，任何一步失败都先重新授权再抛错。

另外：重解析点检查覆盖根路径本身；枚举失败不再被吞掉；核验用一个更宽松的
标识符扫描，不复用决定要删除哪些条目的枚举，同一个解析缺陷不可能同时让
修改和验收都通过。

### 授权 — Windows 从目标提交原样组合执行

仓库里原有的用例把 `mayPrepareIdentity` 固定 mock 成 `false`，所以一直是绿的，
从未测过这条路径。Windows 报告两个放行组合：切换到 seller 后旧 buyer 挂载
被放行；运行已到第 2 代而挂载与认领仍是第 1 代时被放行。

- 身份记录记下核验属于哪一代
- 准备窗口要求运行代次一致；「本代次已核验」永久关闭该角色的窗口（此前绑在
  `activeRole` 上，角色一切换旧角色就重开）
- 守卫要求认领、挂载与运行当前代次三者一致；答不出代次时按保守处理

### 工具成功路径

`settle_operation` 的入参 `outcome` 用了 `'passed'`，不是它的合法枚举。解析
失败被计为 refusal，所以它从来没进过成功输出校验，看起来只是「需要浏览器」
的正常拒绝。`operation_unknown` 同样缺操作记录。

真实成功返回的工具从 8 个增到 **10/12**。剩下 `assume_role` 与
`begin_operation` 需要真实浏览器才能核验角色，作为拒绝路径另测。

## 门禁与验证

183 个单元测试通过。四个变异各钉一个测试：

| 变异 | 结果 |
| --- | --- |
| ACL 授权移回删除之后 | 2 红 |
| ACL 只枚举根目录条目 | 2 红 |
| 准备窗口绑回 `activeRole` | 2 红 |
| 同时去掉守卫侧与 store 侧代次比较 | 1 红 |

最后一项单独去掉任一侧都不红：两层互相兜底。

```sh
cd dsh-plugin-web-test
bash scripts/check-candidate-tarball.sh
bash scripts/check-delivery-identifiers.sh 0.8.3
```

**验证的是「重复打包现有产物」**，不是「干净源码构建可复现」。后者需要从提交
重新走 tsc → tsdown → pack 并得到同样字节，依赖工具链版本与顺序，本记录
不声称。
