## Reproducing the build

Node `^22.19 || >=24`. From the repository root:

```sh
export PATH=/home/weetion/.nvm/versions/node/v24.15.0/bin:$PATH
cd dsh-plugin-web-test && pnpm install
cd packages/web-test
node ../../node_modules/typescript/bin/tsc -b tsconfig.json   # types + lib/types
node ../../node_modules/vitest/vitest.mjs run                 # 116 tests
```

The order matters. `tsdown` reads the `lib/types/` that `tsc` writes, so deleting
`lib/` and running `tsdown` without `tsc` first fails with
`Cannot resolve entry module lib/types/role-browser.js`, which the host reports
only as `failed to import` and a preset that `never started`.

## The two failures

### Two roles cannot share a host

Three public routes were tried and measured:

1. Mount at environment load — single role works; after a host restart the
   provider registers but identity reading fails with
   `browser tool belongs to another Session`.
2. Mount at `agent/created` — the same refusal. `agent/created` fires for every
   agent, and `mountSessionMcp` takes a `ctx` rather than a target, so the event
   does not control the binding.
3. A derived scope — the tools then reach no agent's list at all.

The underlying cause is that the provider binds its resources to whichever agent
exists when it registers, while defining its tools for every agent. One host
process therefore holds one role browser. This is a host interface boundary, not
an implementation choice.

Moving the browser row inside the preset removes the leak outright — a plain
session's `mcp__` namespaces come back empty — but the host then refuses to load
the preset:

```
Preset services require isolate realms: webTestRoleBrowsers
```

The registry's predicate, read from
`dsh-agent-preset-registry/lib/types/mount.js`, flags a service when it sits inside
the preset service's own fiber and `ctx.root[Context.isolate]` maps that name to the
same symbol. So the question is not whether the pool is in the preset but why the
host root's isolate table holds `webTestRoleBrowsers` pointing at the preset's
instance. That is host-internal registry behaviour with no public interface and no
configuration reaching it.

A controlled experiment on a fresh `DSH_HOME` — profile created with
`--from-default-profile web`, the patch read **before the host starts** (`[]`),
one variable between groups — showed the same failure whether or not the pool ever
mounted a browser. Ruled out along the way: a stray row in the profile patch (the
plugin manager never writes loader rows there), the root entry's `static inject`,
whether the pool is used at all, the order of the two preset rows, and the pool
reaching root storage through `ctx.get`. The run log is
`2026-10-05-web-test-windows-acceptance-corrections.zh.md` sections 0.6.26–0.6.34.

The host's `tools.restrict` does not help either: `ToolRestriction` carries only
scope-wide `allow` and `deny` with no per-agent selector, so a deny from this
plugin's host-level rows takes the web-test session's tools with it.

Supersession: this note is the delivery record; the running experiment log above is
its authority for the two failing scenarios and records the corrections to earlier
conclusions that the record's earlier revisions carried.

### A plain session sees the role browser tools

The provider defines the server's tools for every agent, so a session created
without the `web-test` preset lists `mcp__playwright-role-buyer` alongside its own
`web_search` and `web_fetch`. Calls are refused by the guard, so a plain session
cannot drive a browser, but the tool appearing in its list is interference. The
only route that hides it is route 3 above, which breaks the preset.

## Assembly ordering — read before rechecking

`putEnvironment` must be called **before** `session/create`. The environment call
mounts the role browser, and the provider binds to the agent that exists at that
moment. In the other order the browser lands on an agent that is already there
and `assume_role` fails with `browser tool belongs to another Session`. Every
single-role measurement above worked only because the environment was loaded
first.

## Troubleshooting the recheck

**"The model dispatched nothing."** Two unrelated causes, and the `code` in the
session log settles it. `MISSING_CREDENTIAL: llm-deepseek: no API key for
provider route` means the model request never left — the tool list is irrelevant.
Otherwise the model narrated instead of calling, which a long numbered prompt
triggers reliably: one action per short prompt dispatches immediately.

**A clean home has no credentials.** Copy `.credentials.yaml` into the isolated
`DSH_HOME` before measuring. The file is `-rw-------`, stays on the machine, and
is not committed.

## Remaining limits

- Two roles on one host: no working public path.
- A plain session's tool list is polluted; its calls are refused.
- Process reclamation is verified only on host exit. Closing a run does not free
  the provider, because `releaseRole` can only dispose the wrapper effect this
  plugin owns and the effect `mountSessionMcp` registers on its own context is
  never returned. Authority is revoked for real; the Chromium process stays until
  the host exits.
- Ownership across a browser disconnect is unmeasured.
- The Windows ACL hardening item is still open and is not claimed here.
- 0.1.3 remains the original handoff checkpoint; 0.2.x through 0.6.7 are
  development checkpoints.
