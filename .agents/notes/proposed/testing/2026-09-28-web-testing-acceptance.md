# Agent Note: Acceptance criteria and traceability

Status: proposed

English | [中文](2026-09-28-web-testing-acceptance.zh.md)

## Problem

Complete product scope and DSH engineering obligations need independent, traceable pass criteria.

## Proposal

Design state: current acceptance criteria; historical probes do not establish acceptance of the final product combination. Corresponds to [requirements R01–R58](../feature/2026-09-28-web-testing-requirements.md), [technical design TD01–TD12](../architecture/2026-09-28-web-testing-architecture.md), the [report specification](../feature/2026-09-28-web-testing-test-case-report-spec.md), and [foundation and upstream upgrades](../process/2026-09-28-web-testing-upstream-baseline.md). AC01–AC58 accept product requirements; G01–G16 refine their DSH engineering obligations. Neither substitutes for the other. This document contains no test-run results and does not establish implementation or acceptance.

**Acceptance subject and judgment rules**

Acceptance concerns the testing tool itself. Finding defects in a tested project is a correct tool outcome; lacking promised operational capability is a tool-delivery gap. Producing a report containing unverified items does not establish that capability's completion.

Ultimately save each criterion's ID, software/model versions, environment, prerequisites, exact input, actual operations, expectations, actual results, evidence references, and execution time. Distinguish unexecuted checks, insufficient environments, and unmet criteria; apparent feasibility is not a pass. Every required designed scenario needs evidence. Defect dispositions cannot overwrite original execution facts.

Separate tool-delivery acceptance from coverage of real user projects. Fixed acceptance materials may contain deliberately planted defects and correct behavior to verify detection and avoid false positives; passing them does not imply no missed defects in all real projects. Tool-development code coverage follows selected DSH rules, and is not tested-project code coverage.

The accepting party predetermines mandatory fixture features, applicable execution combinations, known defects, and correct controls. The tool's own generated inventory cannot serve directly as the answer key. Independently verify actual business state and evidence; model claims or report generation alone cannot pass. Cross-criterion controls below refine existing AC entries without adding product requirement IDs.

M0 P06 uses preregistered business subsets from unfamiliar projects and human references, deciding continuation under the implementation plan's limited-sample gates. M2/M4 expand the held-out set; M5 reviews it. P06 cannot replace full AC acceptance or justify universal zero-miss claims from small samples. Test startup, passing check scripts, model connectivity, product effectiveness, default-route benefits, and upgrade compatibility are judged separately.

**Recovery verification matrix**

| Interruption or error point | Required behavior |
|---|---|
| Between initial creation intent, child-entity head, and resource-entry publication | Same commandId recovers the original resource without duplicate projects/runs; unpublished entries do not start execution. |
| Intent not committed | No business dispatch; preparation may resume after recovery. |
| Intent committed, not dispatched | Recheck prerequisites and execute once. |
| Connection lost during dispatch | Mark outcome uncertain and inspect target state before replay. |
| Business succeeded, result not committed | Confirm success, save recovery grounds, and continue without duplicate creation/sending. |
| Materials saved, RunHead not committed | Orphaned materials are not authoritative results; handle them before progressing. |
| RunHead committed, conversation notification incomplete | Redeliver the notification without lost progress or duplicate UI runs. |
| Notification appended, delivery acknowledgement unsaved | Recognize redelivery by deliveryId. Projections/model notifications do not retrigger business actions; logs retain actual facts. |
| Two Hosts try to recover the same run | Only the valid writer commits/dispatches; old owners cannot continue, and one run cannot execute twice. |
| Model returns late after pause, cancellation, or takeover | Invalid dispatch permission cannot authorize new actions. Retain receipts for occurred actions without restoring user state to running. |
| In-flight request/large attachment never returns and user pauses/cancels | Immediately prohibit dispatch and revoke permission. Prioritize control persistence without waiting for those requests; list in-flight results separately. |
| Control storage stalls/fails during pause/cancel | Keep dispatch prohibited. Distinguish pending save, failure, and saved; do not claim unpersisted controls survive restart. |
| Model retry proposes an unsettled action, or old request redelivers after settlement | Link the original action; consumed slots return the original result or reject old revisions, never execute again under a new ID. |
| Query temporarily finds no record but the original request may still take effect asynchronously | Keep outcome unknown. Without terminal rejection/nondelivery grounds, do not declare nonoccurrence or blindly resend. |
| Business outcome unknown and no further observation is confirmed available | Block affected instances and preserve unknown facts, continue independent ones; no endless empty queries, blind resend, or treating unknown as nonoccurrence. |
| Authoritative record corrupt or version unreadable | Explicitly identify persistence/compatibility issues; do not skip bad records and show empty history or complete passes. |
| Tool request logged, step closes after preparation/scheduling failure | Preserve existing results. After official completion of unstarted/unknown tool results, actual subsequent model requests are valid and can continue. Reconcile UNKNOWN through original operationId. Failed log writes or already closed corrupt histories cannot be falsely called repaired. |
| Only scheduled messages/default Jobs records show completion | Do not complete test instances from those records alone. Check authoritative RunHead, actual assertions, and business results; duplicate wakeups do not duplicate dispatch. |
| Model stream returns partial output only | Do not execute incomplete decisions; record failure and recover by category. |
| Browser rebuilt or page generation changes | Reject old elements/coordinates and reobserve before acting. |
| Fault simulation not yet removed | Reconcile simulation on recovery, isolate/remove effects, and avoid contaminating later cases. |
| Restart after user pause was durably saved | Stay paused; verify/advance only after explicit continuation. |
| Restart during ctx.llm auxiliary-request backoff | Restore original wait/retry count; recheck observation/control state without stacking SDK/tool retries anew. |
