# web-test 0.8.0 delivery candidate

Status: **a two-role delivery candidate.** All six items of the round-6 directive are
measured on a real Ubuntu host against the delivered tarball. Nothing in this document is
a Windows result; the Windows items are listed separately at the end and are not counted
in the pass list.

This supersedes the 0.6.12 delivery candidate, now archived at
`archived/implemented/testing/2026-10-08-web-test-0.6.12-delivery-candidate.md`. All three
of its stated limitations are closed here: cross-role collaboration is measured, a plain
session is measured keeping its own tools while holding no role browser tools, and the
plugin can be disabled through the real management entry point. It is archived rather
than deleted because it records where the single-role loop, restart recovery, host-exit
reclamation and the pluginManager measurements were first taken.

## What was measured on this build

| # | Item | Evidence |
|---|---|---|
| 1 | Tool input, internal parse, real return, host validation and render agree | The execution test drives every registered tool body against a real store and validates each returned value with that tool's own `output.schema`. `operation_unknown`, `wait`, `resume_wait` and `settle_operation` all share one `operationResultSchema`, so the `required` list matches every real return. |
| 2 | Plain sessions unaffected; preparation bound to the owning run | A `standard` session read `/etc/hostname` and returned `weetion`, and `read_file`, `fs_write`, `bash` and another provider's `mcp__other-*` all return `undefined` from the guard. Preparation is judged against the run that owns the role's browser, and the test pins that asking about run B answers for B while asking about run A does not, though both sit in one session and declare the same role. |
| 3 | Start errors surfaced; the second role works | Each mount is awaited and its result checked; a failure never writes `started`, and concurrent `ensure` calls await one start. Each role is named by its own mount generation, so a re-mount never collides with the client it replaces. `readAccount` addresses the role by the server name of its live mount. |
| 4 | Resources owned and released together | Browsers are filed under project, environment revision, run and role. Two runs in separate sessions each kept their own browser, and ending one left the other's browser alive (`Chromium 20 → 10`). `releaseRun` releases what a run claimed and nothing else. |
| 5 | Disable and re-enable through the real management entry point | Disabling the role-browser row returned `changed: true, application: "failed"` and took `Chromium 20 → 0`; `web-test` stayed `fiberPhase: pending` and the row `None`. Re-enabling returned `application: applied` with all three rows `active`. Disabling the whole bundle `dsh-plugin-web-test` removed every web-test row and restoring brought all three back. The host stayed at 1 and the user's own 25 browsers were untouched throughout. |
| 6 | Clean build and full regression on the final tarball | See below. |

## The regression on 0.8.0

The acceptance fixture was restarted first so its order table started empty, and every
observation came from an order created in that round.

| # | Regression | Result |
|---|---|---|
| 1 | Sign in, verify the role, receive an authority | `now acts as buyer … Present authority`, `Chromium=10` |
| 2 | Two roles in one session, each holding its own authority | `buyer-login-run` and `seller-login-run` both `running` with their own roles, `Chromium=20` |
| 3 | Two roles working on one business object | order `1c6eb1e4` titled `Final-1`, `createdBy: Alice Buyer`, `approvedBy: Bob Approver` |
| 4 | Pause releases the browser, resume remounts it, the generation increments | `paused` at generation 1 → `resume` → `running` at generation 2, `Chromium 10 → 20`, role verified again |

Cross-role evidence, all measured across two sessions, two runs and two separately
signed-in browsers holding their own authority strings:

- A the buyer creates a record under its own authority.
- A's attempt to approve it is refused with `403 Alice Buyer 无权审批`.
- B the seller signs in independently with its own authority and sees A's record.
- B approves that same record under its own permissions, and the record then carries
  `createdBy: Alice Buyer` and `approvedBy: Bob Approver`.

A re-read of the record by A after the approval was not run separately. The response
already carries both fields on one record, and those two fields together say A's record
was processed by B, so a second read adds nothing. It is recorded as not separately
executed rather than claimed.

The plugin holds no credentials. The model completes the sign-in through the site's form
and the plugin reads back the account the site declares, refusing an empty one. That is
the reason a run cannot bootstrap a role in an environment that does not declare it.

127 tests pass and the typecheck is clean on this build.

## Windows: listed separately, not verified

None of these has been run. Ubuntu results do not substitute for any of them.

1. Desktop acceptance on the user's existing Windows DSH at `0.2.0-rc.2`, with the
   plugin installed into that application.
2. ACL behaviour on Windows, which is untested.
3. Resource reclamation on Windows: the Chromium process tree differs from Linux's, so
   the `20 → 0` observation has no Windows counterpart yet.
4. The values `application` takes on disable and enable, and the fiber states, on Windows.
5. Whether regressions one through four behave the same across rounds on Windows.

## What a verifier should do first

Install `dist/dsh-plugin-web-test-0.8.0.tgz` into the Windows application, confirm
`web_test_status` reports `0.8.0`, then repeat regression 1 alone before anything else.
Every other item depends on that first loop closing on Windows.
