# Agent Note: web-test 0.8.0 delivery candidate

Status: proposed

## Problem

The delivery record pointed at 0.6.12, a single-role candidate whose three stated limits were cross-role collaboration, a plain session and disabling the plugin, and none of those limits were closed. A verifier reading that record would be verifying bytes that no longer carry the behaviour the plugin now has, and would have no record of what the current build was measured against.

This names 0.8.0 as the version to verify and states what was measured on it. The SHA below is the commit whose tree produced this tarball. It is the current `HEAD`, and it has to be: a change anywhere under the plugin's package directory, including a document, changes the tarball and with it this line. Three earlier drafts named commits that could not have produced it: `86d7d494df`, whose source still reads 0.7.7, `43b9a10e40`, which predates the README corrections, and `71393d989a`, which predates the Windows checklist corrections.

```

sha256   f87bb2556a589e5313642f6790d3ad35b73ff98cc3bcdc98e03242ec9f36b1f9
```

All earlier packages are kept, 51 tarballs in `dist/`. Packing the current source reproduces the recorded `sha256` byte for byte, so the hash is a reliable identifier and a verifier can confirm the bytes they received against it. Every measurement below was taken on the earlier package with hash `80c48832e…bbf94f`, which differs from this one in exactly three files: `README.md`, `README.zh.md` and `WINDOWS-ACCEPTANCE.zh.md`. Packages `67663e4e…` and `fca2d26e…` added the README and checklist corrections; each was compared against its predecessor and differs from it in documents only, so every measurement taken up to that point applies to them unchanged. Two packages after those change JavaScript. The first adds the `start_run` entry check that names the project holding the environment, measured on a real host: a wrong project key returned `project "acc-w4" is not stored; stored projects are [shop]`, and a stored project paired with another project's environment returned `environment "acc-other" belongs to project "other", not "shop"`. The one after that requires a stored project in `putEnvironment`, so the operator surface and `start_run` no longer disagree about whether an environment is usable. Measured on a real host starting from no projects at all: an environment naming a project that was never stored was refused with `stored projects are []` and left the table at zero rows; after creating a project the same call was still refused and the list read `[shop]`, and an environment under that project was accepted. The one delivered here moves resource release out of the tool handlers: the store announces every status change and the browser pool subscribes, so a cancel, pause or wait issued through the operator's `webTest/*` surface releases the run's browsers the way the model tools already did. Measured on a fresh host against this package: cancelling through `webTest/controlRun` took Chromium from 10 to 0, where the previous build left it at 20, and pausing did the same, with the run at `paused` and its generation unchanged. The host stayed at 1 and the user's own 27 browsers were untouched. The state machine, the guard and the generation rules are untouched. The source SHA names the tree those bytes came from.

## Proposal

| # | Item | Evidence |
|---|---|---|
| 1 | Tool input, internal parse, real return, host validation and render agree | The execution test drives every registered tool body against a real store and validates each returned value with that tool's own `output.schema`. `operation_unknown`, `wait`, `resume_wait` and `settle_operation` all share one `operationResultSchema`, so the `required` list matches every real return. |
| 2 | Plain sessions unaffected; preparation bound to the owning run | Measured on the package delivered here, on a host that has the plugin installed: both the `standard` and `web-test` presets create a session, and a `standard` session called `bash` and `read`, and `read /etc/hostname` returned `weetion`. It called no `web_test_*` tool and no role browser tool, its log contains no `playwright-role` string at all, and Chromium stayed at 0 throughout, so the guard narrows to test agents without taking the plain session's tools away. Preparation is judged against the run that owns the role's browser, and the test pins that asking about run B answers for B while asking about run A does not, though both sit in one session and declare the same role. |
| 3 | Start errors surfaced; the second role works | Each mount is awaited and its result checked; a failure never writes `started`, and concurrent `ensure` calls await one start. Each role is named by its own mount generation, so a re-mount never collides with the client it replaces. `readAccount` addresses the role by the server name of its live mount. |
| 4 | Resources owned and released together | Browsers are filed under project, environment revision, run and role, and `releaseRun` releases what a run claimed and nothing else. Measured on 0.8.0: two sessions each verified their own role and held their own browser, `Chromium 20`; closing one run took it to 10 while the other stayed `running` and still drove its browser to `/account`, and the host stayed at 1 with the user's 25 browsers untouched. Pause releases the browser and resume remounts it with the generation going 1 to 2. On the build that carried those handler-level releases, all three terminal statuses released: `completed` went 12 to 0, and `cancelled` and `blocked` each took Chromium from 10 to 0. **That does not hold on the package delivered here.** Moving the release onto the store's status change left the terminal write path out of it, so a run closed through `finish_run` no longer releases anything, and no operator interface can reclaim it either. Measured on the intermediate package: two `completed` runs held `Chromium 20`, and `pause` and `cancel` were both refused with `is completed and cannot`. **That is fixed here**: the run write is now the single place a status is announced, so the terminal write reaches the pool like every other one. The store test drives `putRun` to `completed` and observes the announcement, and a repeated write of the same status is not announced again. Measured on a real host against this package: a run verified through `assume_role` and then closed with `finish_run` as `completed` left `Chromium 0`, while a second run verified the same way and left `Chromium 10`. The session log shows the first run's browser had loaded `/account` before the close, so the zero is the close's doing and not a browser that never started. All three terminal statuses were then measured on the same host and the same package: `blocked` and `cancelled` each took a verified run from Chromium 10 to 0, with the host at 1 and the user's 27 browsers untouched. Each started from a run that had been verified, so the zero is the close's doing. The non-terminal actions behave the same way: `await-user` and `pause` both release, and `continue` or `resume` restores the run at generation plus one with the old authority void, after which re-verifying the role brings the browser back from 0 to 10. |

Re-enabling returned `application: applied` with all three rows `active`. Disabling the whole bundle `dsh-plugin-web-test` removed every web-test row and restoring brought all three back. The host stayed at 1 and the user's own 25 browsers were untouched throughout. |

### The regression on 0.8.0

The acceptance fixture was restarted first so its order table started empty, and every observation came from an order created in that round.

| # | Regression | Result |
|---|---|---|
| 1 | Sign in, verify the role, receive an authority | `now acts as buyer … Present authority`, `Chromium=10` |
| 2 | Two roles in one session, each holding its own authority | `buyer-login-run` and `seller-login-run` both `running` with their own roles, `Chromium=20` |
| 3 | Two roles working on one business object | order `1c6eb1e4` titled `Final-1`, `createdBy: Alice Buyer`, `approvedBy: Bob Approver` | order `b448967e` titled `W3-One`, carrying `createdBy: Alice Buyer` and `approvedBy: Bob Approver` on the same record, read back from the site. Each step was issued as its own prompt after the previous one was confirmed there. |
| 4 | Pause releases the browser, resume remounts it, the generation increments | `paused` at generation 1 → `resume` → `running` at generation 2, `Chromium 10 → 20`, role verified again |

Cross-role evidence, all measured across two sessions, two runs and two separately signed-in browsers holding their own authority strings:

- A the buyer creates a record under its own authority.
- A's attempt to approve it is refused with `403 Alice Buyer 无权审批`.
- B the seller signs in independently with its own authority and sees A's record.
- B approves that same record under its own permissions, and the record then carries `createdBy: Alice Buyer` and `approvedBy: Bob Approver`.

A re-read of the record by A after the approval was not run separately. The response already carries both fields on one record, and those two fields together say A's record was processed by B, so a second read adds nothing. It is recorded as not separately executed rather than claimed.

The plugin holds no credentials. The model completes the sign-in through the site's form and the plugin reads back the account the site declares, refusing an empty one. That is the reason a run cannot bootstrap a role in an environment that does not declare it.

127 tests pass and the typecheck is clean on this build.

## Acceptance criteria

Every item below is unmet and none has been run. Ubuntu results do not substitute for any of them, so this candidate cannot be called accepted until they are.

1. Desktop acceptance on the user's existing Windows DSH at `0.2.0-rc.2`, with the plugin installed into that application.
2. ACL behaviour on Windows, which is untested.
3. Resource reclamation on Windows: the Chromium process tree differs from Linux's, so the `20 → 0` observation has no Windows counterpart yet.
4. The values `application` takes on disable and enable, and the fiber states, on Windows.
5. Whether regressions one through four behave the same across rounds on Windows.

## Risks

The browser must be told which authority to present, so the model carries a string by hand; it failed on this path until the prompt named the parameter, and nothing in the plugin enforces it. Resource reclamation is observed through process counts, which on Windows means a different judgement than a process tree on Linux, so the `20 → 0` observation has no counterpart there. The values `application` takes and the fibre states on disable are assumed to match Linux and are untested. A run that is only paused keeps its browser, while a cancelled one does not, so an operator who cancels expecting to resume has to start again. The build is byte-reproducible here because the packer pins its timestamps, so the recorded `sha256` is a reliable identifier rather than a label for one build.

## Alternatives considered

Keying role browsers by role name alone was rejected because the same role declared by two projects or environments would share one browser. Requiring the model to present an authority string on every browser call was kept, but the alternative of binding the authority to the run so the guard reads it from context was not implemented; the model has to carry the string, which failed until the prompt named the parameter. Letting the plugin hold credentials to complete the sign-in itself was rejected: it would put test credentials in the plugin. Releasing role resources on cancel was kept even though a run that only pauses would keep them, because a cancelled run may never be resumed.

## Supersession

Replaces the archived 0.6.12 delivery candidate. The 0.6.12 record's three stated limitations are closed here and the measurements it holds are re-measured on this build, so it is a full rather than partial supersession. No other active note covers the web-test delivery candidate.

## What a verifier should do first

Install `dist/dsh-plugin-web-test-0.8.0.tgz` into the Windows application, confirm `web_test_status` reports `0.8.0`, then repeat regression 1 alone before anything else. Every other acceptance item depends on that first loop closing on Windows.
