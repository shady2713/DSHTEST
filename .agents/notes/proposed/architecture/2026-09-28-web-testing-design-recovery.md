# Agent Note: Detailed Design: Data and Recovery

Status: proposed

English | [中文](2026-09-28-web-testing-design-recovery.zh.md)

## Problem

Long tests must retain authoritative outcomes across failures without duplicating business effects or losing shared evidence.

## Proposal

Design state: proposed product design; partial probes and prototype work do not establish final implementation or acceptance. This document elaborates I02 in the [Architecture](2026-09-28-web-testing-architecture.md). See [Interfaces and Execution](2026-09-28-web-testing-design-execution.md) for calls and actual execution, and [Models and Release](2026-09-28-web-testing-design-models-release.md) for model retries and release. The [Report Specification](../feature/2026-09-28-web-testing-test-case-report-spec.md) is the source of truth for result semantics.

Reading order: DD06 data → DD07 commits and ownership → DD08 scheduling and recovery → DD09 snapshots, evidence, and reports. The fields below form a proposed domain schema; the implementation derives types from zod declarations rather than maintaining three separate handwritten TypeScript/JSON/RPC definitions.

**DD06: Identities, Records, and Storage Boundaries**

All business IDs are opaque branded types; do not extract times, file locations, or business fields from them. revision is a monotonically increasing safe integer within an entity. Store UTC instants, with business time separately recording IANA time zone, local time, and applicable rules. Long-term scheduling persists an absolute dueAt; individual operation durations use a monotonic clock. System-clock jumps trigger wait revalidation.

FrozenRunManifest, RecoveryUpdateIntent, and RecoveryLink are proposed recovery records: respectively, a consistent freeze manifest; package/data/lock/backup identities and recovery phase; and links between old/new runs and unsettled actions. Define them at explicit persistent boundaries owned by Runtime/the installation coordinator, without creating another session log. Unknown actions retain verification responsibility under their original operationIds, are checked across new runs, and block semantically duplicate dispatches. If business equivalence cannot be determined, keep them blocked. Recovery writers and ordinary Runtime contend for the same control-root lock and never write concurrently.

RunHead is the run commit entry point and contains at least runId, headRevision, phase, status, ownerEpoch, controlEpoch, planRevisionId, committedViewRef, lastCommitRef, activeAttemptRefs, unsettledOperationRefs, waitRefs, outboxRef, latestReportRevisionId, recoveryRequired, and updatedAt. Large collections use versioned paginated manifest references; the head must not grow without bound for every screenshot or action.

Execution tools do not trust model-supplied operationIds. Runtime assigns operation identities from committed instanceId, attemptId, stepId, and actionOrdinal and saves a semantic action hash. Each step also has a persistent StepCursor recording stepRevision, current actionSlotId, and consumed slots. Tool requests bind to the slot, observation, and revision present when generated. The same slot and semantics return the original action and current result, including settled actions; different semantics in the same slot are rejected. An old revision does not automatically receive the next ordinal. The next action is accepted only after Runtime commits a new slot from fresh observations and case progression. Multiple legitimate actions such as continuous typing are accounted for separately; duplicate toolCallIds and duplicate business actions belong to different identity layers.

Access domain data through ctx.storageDomain/ctx.storage.domain, defineDomain, and domainTable. SQLite/single layout is the first-release candidate; P02 checks access patterns and the actual composition before recording StorageDesignDecision. Business packages do not connect to SQLite directly. Strictly reject incompatible or invalid authoritative records; do not preserve test history using backup-and-skip or by treating unknown versions as absent. Official domain update provides serial atomic updates within its owning instance only, not database CAS across Hosts. [Storage reference](../../../../docs/subsystems/storage.md), [Domain declarations](../../../../packages/storage/storage-domain/src/spec.ts)

The segmented physical organization below is a P02 comparison candidate, not a frozen implementation. To avoid loading all historical actions into memory at application startup, it divides units by asset and run: a small catalog stores project/run entry points; each run's control domain stores RunHead; plan/case assets and runtime facts use immutable segments; cross-run lists are rebuildable indexes. One owner factory creates validated unit names from the same schema, using internal IDs and sequence numbers only, never user paths.

The catalog's CatalogHead is the authoritative resource-registration entry point, referencing segmented creation intents, published resources, and commandId receipt indexes; UI history lists remain rebuildable projections. ProjectHead and SkillHead commit their own active revisions and command receipts; file modification times cannot determine current versions. Heads remain bounded, with indexes/history paginated through immutable manifests. Only published entry points enter normal analysis/execution scheduling.

Suggested active-segment rotation is at 1,024 business records or 8 MiB of serialized content, whichever comes first, at complete-record boundaries. This is implementation configuration guidance, not a task-length limit. Frozen segments are immutable and opened only for queries, recovery, or reports; keep the current segment, required checkpoints, and a few recent pages open. Open domain handles need reference counting and closure owners; concurrent calls share the same open handle instead of opening a same-named domain repeatedly.

A suggested current-view checkpoint occurs every 128 business commits or before report generation, recording membership indexes and each entity's latest revision references. History remains traceable along commit references, while queries need not replay every record from the first step. CommitRevision describes business changes, the previous commit, record references, and command receipts; it does not duplicate model token streams, generic tool events, or Session logs. Segmentation, manifests, checkpoints, and these values are candidate implementation choices. M0 must measure access costs and compare simpler designs meeting the same constraints before retaining or adjusting them. Business authority, non-overwritable history, recoverable control, and official storage ownership are mandatory; this internal structure is not an established necessary framework. Failed rotation or checkpoints must not delete facts or advance RunHead.

P02 compares at least a minimal per-run record design satisfying the same persistent-intent, head-commit, deduplication, and history constraints against the segment/checkpoint candidate. Measure opening, commits, queries, recovery, memory, and implementation/migration costs with identical materials and failure points. Enter M1 with the smallest qualifying structure; adopt the more complex one only when measurements identify a specific bottleneck that it solves. Segmentation/checkpoints are physical-organization candidates; Head/commit/unknown-action semantics remain. Record the choice in StorageDesignDecision for all subsequent tasks instead of prebuilding a framework from numbers in this design.

**DD07: Sole Writer, Commit Order, and Dispatch**

The first release permits one Host writer per application data root, scheduling multiple isolated tasks without multiple Hosts competing for a run. Retain official Electron single-instance behavior and add a Windows named mutex held for the process lifetime for the test data root. Use the Global namespace, a fixed protocol prefix, and a digest of the canonical control-root identity, with access limited to the current user and system. Different application versions or installation identities must not obtain independent locks for the same control root. Host acquires the lock before opening authoritative domains; a fixed owner thread holds it until executors and domain handles close. Other Hosts do not take over on timeouts or lease expiry; recovery begins only after the old process actually exits and the lock can be acquired. WAIT_ABANDONED triggers recovery checks, not a clean-exit assumption. [Official single-instance implementation](../../../../apps/desktop/src/single-instance.ts), [Windows mutex](https://learn.microsoft.com/en-us/windows/win32/sync/using-mutex-objects), [Cross-login-session namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)

The mutex wrapper is a proposed narrow Windows capability implemented and verified under native-module rules. It is not an existing public DSH service and does not reuse installation/configuration transaction locks for the entire Host lifetime. The control root is the stable directory holding the data-generation pointer; lock identity derives from its final directory identity, not the candidate data directory currently selected by that pointer. Upgrade generation switches do not change lock identity. Data-root aliases and junctions must resolve to the same actual directory identity. If exclusive ownership cannot be established, reject writes and dispatches instead of falling back to an in-memory lock. The first release does not support moving the control root at runtime; launches across Windows login sessions must contend for the same data-root lock.

Each successful Host startup generates a new ownerEpoch. All active Agents, targets, dispatch permits, and responses carry it; recovering the same runId does not keep old connections valid. After handshaking with Host, Electron Main recognizes only the current generation and discards undelivered queued items on disconnect. Actual asynchronous model/tool waits must not occupy Runtime's business commit queue, which would block pause and cancellation.

**Business commit order.** Read the committed version first, keeping model/network waits, large-attachment saves, and bulk material preparation outside the commit queue. Once ready, enter a short serial queue and revalidate commandId, expected version, control generation, and current state. Only if validation still holds, write bounded business records and CommitRevision, then publish references, headRevision, and notification outbox in one RunHead.update. Recompute or return a conflict when versions change; stale candidate facts must not directly advance execution progress. A successful receipt requires the head write to finish. An individual storage write can still stall; pause/cancel therefore has the immediate dispatch gate below.

**The update path must carry two copies of the record, and no write order removes that.** There are no cross-record transactions, and the record and the head live in one document, so a committed update cannot be made atomic by reordering. For a creation, a preceding write is merely an unreferenced material that recovery follows head references past. For an update the record is *already* head-referenced, so writing the new revision first leaves a published entry dangling, and publishing the entry first leaves an entry pointing at content that does not exist — head-first only moves the dangling reference to the other side. The record therefore keeps its published revision and holds the uncommitted next revision in a pending slot; reads resolve a head entry against the published revision or the pending one, so every interruption point lands on a state the record can answer from. The update commits in three writes — stage, publish the head, fold the pending slot in — and the head carries the same replayable command ledger the create path uses, so a retry returns the original receipt and appends nothing. **A published entity must never become unreadable, across restart.**

**Initial creation must also recover.** Creating a project, run, or skill first registers createIntent in one CatalogHead commit, including commandId, normalized parameter hash, and reserved resource ID. Then idempotently create the child entity head using the same ID, finally publishing the entry point and final receipt. Interruption between any of these three stages resumes from the registered intent to completion or explicit creation failure without allocating another ID. Unpublished entry points must not start execution Agents. Resending the same command returns the original resource and progress; reusing its ID with different parameters is rejected. Existing project/skill version changes commit through their own Heads, with the original command reference locating results, and carry the same replayable ledger the create path uses. The resource-registration ledger is not a disposable list index.

Business actions require two persistent commits: first save PREPARED intent and pre-action observations, then save DISPATCHING and permit identity before actual dispatch. Recheck the immediate dispatch gate, control generation, target, and execution conditions before handing work to the actual executor. dispatchState records only PREPARED/DISPATCHING/RECEIVED; outcomeState separately records UNKNOWN/CONFIRMED_OCCURRED/CONFIRMED_NOT_OCCURRED. Observations append evidence, not a successful terminal state called OBSERVED. Advance StepCursor only when evidence settles the action and case progression conditions hold. DISPATCHING means possible delivery; absence of RECEIVED cannot establish non-occurrence.

| Delivery/outcome condition | May the same business action be sent again automatically? | Next step |
|---|---|---|
| PREPARED, definitively without a dispatch permit | Yes, after rechecking target and conditions | Continue the original operationId without adding a business action. |
| DISPATCHING/RECEIVED, outcome unverified | No | Read target state, business IDs, service receipts, or read-only logs. |
| CONFIRMED_OCCURRED | No | Save observations and continue; occurrence is not an assertion pass. |
| CONFIRMED_NOT_OCCURRED | Depends on case, authorization, and environment conditions | Create another delivery attempt for the original action, preserving verification bases. |
| UNKNOWN with valid observation channels remaining | No | Save the next check time and continue independent work. |
| UNKNOWN with no further observation conditions confirmed available | No | Block the affected instance and report the unknown operation and follow-up test conditions. |

Do not claim exactly-once execution for arbitrary websites. This tool guarantees that unsettled operations are not blindly replayed. Record and reuse reliable target-provided idempotency keys when available; otherwise rely on verification, which may still be inconclusive. For partially delivered keyboard input, read the current value and recover according to the case. If a keystroke itself triggered submission, verify the business outcome rather than selecting all and retyping directly.

CONFIRMED_NOT_OCCURRED requires evidence sufficient to exclude later effects of the original request, such as the actual executor confirming it was never delivered, or the target providing a definitive terminal rejection with no residual asynchronous work. Temporarily absent records, unchanged pages, replica lag, client timeouts, and request cancellation are insufficient. Keep UNKNOWN while queueing or eventual-consistency windows exist. Without reliable verification conditions, block; elapsed time alone never authorizes resend.

When pause/cancel reaches Runtime, immediately close the in-memory dispatch gate and revoke old executor permits without waiting for large attachments, models, or business-network responses. At the same time, prioritize a control commit persisting the new controlEpoch and decision. Receipts separately show local blocking of new dispatches, decision pending/saved/save-failed, whether executors confirmed they stopped accepting work, and in-flight action count. Do not show “pause saved” before persistence finishes. On storage failure, retain the dispatch prohibition and explain that control persistence across restart is not guaranteed. resume opens the dispatch gate only after successful persistence and renewed environment checks. Already-delivered operations cannot be withdrawn instantly and still require outcome verification. Late model answers are records only and cannot resume user-stopped tasks.

Session notifications use an outbox outside the transaction. Derive deliveryId stably from runId, commit revision, event kind, and a fixed sequence within that commit. After business commit, append registered test-session events with businessRef, revision, and deliveryId, then commit delivery acknowledgment. If append succeeds but acknowledgment is lost, redelivery retains the ID. Session preserves actual append history; Client projections and semantic notifications fed to models each deduplicate by ID. Hiding duplicates only in the UI is insufficient.

DSH Session stores actual model inputs, outputs, and tool calls. Read-only query results entering a later model request must also pass through Session-reconstructible tool results or persistent references; unrecorded business summaries must not be injected from memory. Background model-assisted decisions call ctx.llm within recorded execution-Agent tool processes, saving inputs, outputs, and ownership. DD10 defines public decision formats and candidate-protocol rules.

Calling ctx.llm alone does not prove an auxiliary request entered Session. Before sending, the decision tool appends a typed test-decision-request event recording decisionId, requestAttemptId, actual input references, routeRevision, and observationId. Responses/failures append corresponding result events with actual outputs/errors, usage, and model versions. Model retries of one decision share decisionId; every actual request has a distinct requestAttemptId, separate from business Attempt. Adopt a decision only after its result is persisted and the observation remains valid. Implement events and presentation/replay under DSH extension rules; domain actions reference these events without duplicating model logs. Save failure stops adoption of the result.

**Crash recovery order.** Acquire exclusive write ownership → strictly open the control domain → check RunHead-referenced records and attachments → restore notification delivery → distinguish user pause/cancel from unexpected interruption → create new active-Agent/target generations → verify source, deployment, identities, and browser environment → reconcile all unsettled business actions → schedule resumable instances by dependencies. Notification repair triggers no business actions. Successful login cannot conceal source/deployment version changes.

Records written but not referenced by RunHead remain unreferenced materials awaiting inspection and do not enter reports. Garbage collection handles them only after proving no authoritative references, active writers, or pending commit users exist; automatic deletion of user history is not designed in this phase. Missing attachments, corruption, or incompatible formats explicitly block recovery; never show an empty project or “no failures.”

Recovery updates are a separate user-selected path; see DD12. Frozen old runs do not enter ordinary automatic recovery. Unknown-action reconciliation lists remain effective across RecoveryLink; new runIds/command identities cannot bypass deduplication. Restarting, updating, or changing models cannot clear this obligation.

**DD08: Scheduling, Waits, and Retries**

The selected baseline provides activity-check and stop extension points for session archival. Runtime must include queued, executing, paused, waiting, recoverable, and unsettled runs in session activity decisions. The first release blocks archival in these states and prompts in the original conversation to handle tasks first. Archiving, closing cards, and unloading plugins do not mean user cancellation of runs; upstream turn cancellation during archival must not silently clear persistent tasks. Integrate through public extension points in the selected baseline without changing the Agent loop.

Run phase is analysis/planning/execution/reporting/cleanup; status is queued/running/recovering/waiting-user/waiting-time/paused/frozen-recovery/ended/cancelled. They are separate dimensions. Waits and controls do not overwrite instance or assertion results. An ended run also distinguishes completed-coverage from incomplete-coverage, with gaps listed for the latter; cancelled cannot be renamed completed.

Instance scheduling states are ready, executing, waiting, blocked, and settled. Final results still use the report specification's passed, failed, needs-confirmation, blocked, skipped, and not-run semantics. A failed instance can also contain later unverified assertions. Keep a Run running while independent executable instances exist, showing local waits in waits. Choose an overall waiting status only when all work capable of advancing is waiting.

| Event | Persistent change | Scheduling rule |
|---|---|---|
| Unclear business expectation before testing | Question plus affected-case dependencies | Ask and apply answers to cases first. Formal execution and business-changing data preparation wait for pre-test questions; independent material reading and analysis may continue. |
| New business question during execution | Affected assertions need confirmation; report question | Skip affected portions this run; apply answers to a new case version and create linked follow-up tests. |
| Temporary API, network, or rate-limit failure | Failure plus retryAt and routeAttempt | Exhausting short retries does not end the task; resume after cooldown or use a capability-matched fallback route. |
| Invalid credentials or unsupported configuration | Question and waiting-user reason | Do not rapidly repeat invalid requests; resume after a configuration-repair event and recheck. |
| Missing environment declaration, insufficient scope, or related configuration change | Declaration question, required authorization, and affected scope | Satisfy R54 before formal execution/business preparation; do not reuse inapplicable old authorization. |
| Space enters protection state | Space sample, affected save locations, and recovery conditions | Block dispatches requiring new materials, retain in-flight verification, and reschedule after space recovers and save checks pass. |
| Sustained lack of progress in effective work | ProgressCheckpoint, reason, and bounded recovery count | Recover or advance independent items first; if progress remains impossible, wait and notify. Larger counters do not reset stagnation. |
| Business timer becomes due | Time conditions and nextObservationAt | No model wait occupancy; collect evidence when due and record missing evidence if the window was missed. |
| Deployment, source, or external-browser version changes | Environment-change facts and affected set | Isolate old results and create linked version segments or a new run; expectation changes require confirmation. |
| User continues | New controlEpoch plus recoveryRequired | Check targets and in-flight facts before dispatch; do not directly reuse old coordinates. |
| Main window closes | No business terminal-state change | Retain necessary hosting resources; restore the target window when native input is needed. |
| Explicit exit | Save recovery position and stop dispatching | Do not restart the application automatically. On next launch, recover non-paused, non-canceled runs under the rules; frozen-recovery does not automatically continue and follows DD12 recovery-only and linked continuation. |
| All tests settled | Pin the test-result version and enter reporting | Do not force-settle pending verification or temporarily recoverable items to manufacture completion. |
| Preliminary report saved successfully | ReportRevision plus cleanup plan | Clean through controlled business entry points and generate a new report revision afterward. |

Model retries and business retests use different configuration. For primary Agent requests, explicitly assembled official llm-retry applies the provider's normal policy at the request-failure extension point. After short retries are exhausted, Runtime persistently schedules recoverable failures. Auxiliary requests such as lightweight decisions calling ctx.llm directly do not pass through that extension point, so Runtime records each failure and schedules the next ctx.llm call. If short retries are needed, this single owner computes them under the same provider policy; SDKs, adapters, and tools do not add their own loops. Both paths must not schedule the same failed request. [Official retry plugin](../../../../packages/llm/llm-retry/src/index.ts), [Provider retry policy](../../../../packages/llm/llm/src/retry-policy.ts)

**Session recovery after tool-scheduling failure.** M0 P03/P05 cover recorded tool requests, completed results, subsequent preparation or scheduling failure, step closure, and a real continued model request. V05 and M3 reuse this control. The selected baseline includes #4595's live repair; short retries and restart-tail repair alone still do not establish this behavior. Revalidate the application combination and preserve completed results, UNKNOWN reconciliation, and not-started distinctions. Do not maintain a duplicate Agent result-repair loop.

| Session or business fact | Runtime handling | Conditions for continuation |
|---|---|---|
| Existing formal tool result | Preserve the original result and corresponding ActionRecord; completion must not overwrite them | Check the current action and commit state referenced by the result; assertions still determine pass/fail. |
| Official repair emits TOOL_OUTCOME_UNKNOWN | Map to required reconciliation, retaining original operationId/action slot | Settle using business/executor evidence; valid model messages do not establish known external effects. |
| Official repair emits TOOL_NOT_STARTED | First correlate domain intent, permits, and dispatch records by tool-call identity | Continue through PREPARED only when non-delivery and absence of late-arriving semantically equivalent actions are both established. Text alone cannot clear an existing UNKNOWN. |
| Log-write failure, inconsistent closed history, or unmappable tool identity | Mark protocol-recovery failure and affected scope, preserving unknown business outcomes | Use verified official read/repair scope; do not delete history or create another session to bypass business reconciliation. |
| Accepted tool dispatches remain at cancellation | Close dispatch gate, drain or settle accepted work, and retain uncertain outcomes | Do not restart canceled tasks or call tools again merely because results were completed. |

P03/P05 verify valid tool request/result pairing, preservation of completed results, no false execution claims for unstarted actions, and continuation of subsequent model requests. Session-protocol recovery and safe business recovery are separate conclusions. Patch versions, applicable historical boundaries, and upstream check records enter the baseline manifest.

Official Schedule is not a prerequisite of persistent Runtime. When timed wakeups are needed, explicitly select the optional schedule bundle before applying its plugin-row configuration; an unselected bundle has no rows to patch. Reminder receipts establish Inbox delivery only. Deduplicate stable wakeup identities, then check RunHead, retryAt, control generation, and eligibility; stale or already-enqueued reminders cannot resume paused, canceled, or frozen runs. Runtime retains persistent retries and startup scans when delivery fails.

Suggested long-term recovery backoff is 30 seconds, 1 minute, 2 minutes, 5 minutes, then at most 15 minutes, with jitter. A valid Retry-After is a lower bound for the next request and may exceed the local backoff cap. Before waiting, save failure category, next time, route, requestAttemptId, and recovery conditions; restart does not reset to the first short retry. Each recovery first checks observation and control state; do not keep retrying an old decision. New observations create new decisions while preserving original request history. Config owns concrete values; there is no cumulative-call limit for the entire task.

Absence of a user cost quota does not justify constant high-frequency idle looping. Fallback routes select only configured models with sufficient capabilities; one unavailable provider does not block other independent tasks. Permanently unsupported requests or judgments switch to a legal route or wait for repair instead of retrying an invalid schema forever. Task cancellation stops new retries; late model results cannot reactivate the task.

A business retest is a new Attempt and requires verification of the original action plus case-specific retest conditions. The suggested default schedules at most one complete attempt to reproduce a failure, preserving the initial failure; explicit case policy or user requests schedule additional attempts. This is a configurable default awaiting implementation, not a limit on user regression runs. Repeating until a coincidental pass cannot erase failures.

Acquire scheduling locks by target resource: the native desktop is serial, ordinary flows in one identity context are serial, and business-concurrency cases have one planned execution group owning multiple isolated contexts and recording participants, synchronization points, and business linkage IDs. A single DD02 SessionResources.run coordinates the group; each branch independently passes DD07 dispatch checks without reacquiring the same queue in a nested call. Independent runs in one environment queue by default, running in parallel only with plan-defined isolated data and resources. Accidental contention for the same test data is not concurrency simulation. Dependency blocking propagates only to real successors; one failed module does not make all other modules fail.

Fault simulation saves FaultLease with target, type, start condition, original state, removal method, and impact scope. Browser offline mode or request latency proves only the tool-imposed condition, not a real service failure. Recovery first checks remaining simulations and removes or isolates them. Failed removal stops affected subsequent execution and reports residual environment effects without hiding errors.

R57 uses phase-specific ProgressPolicyRevision containing effective active-time windows, repeated-signature thresholds, available recovery actions, maximum consecutive recovery cycles, and reminder-coalescing rules. Determine parameters before M3 acceptance using normal long flows and looping controls; they are not model-token budget limits. Runtime maintains progress checkpoints from new material results, StepCursor advancement, valid assertions, and question settlement. Recommitting the same fact, rewriting the same plan, screenshots without business changes, and UI clock changes do not advance the checkpoint.

Detection accumulates active time only for executable work and combines it with repeated behavior. Timed waits, API backoff, user pauses, takeover, and environment/space waits have separate reasons and wake conditions. First try re-observation, legal route changes, or already-permitted execution recovery, never blindly resending unknown business actions as “recovery.” If bounded recovery remains ineffective, save the stall reason and enter waiting-user while independent instances continue. Recheck upon new evidence, configuration repair, or user continuation. Deduplicate same-cause reminders by runId/stagnation cycle; restarting alone neither resets recovery counts nor repeatedly floods cards.

R58 RunMetrics is a read-only projection of domain progress, DSH request records, and active-time intervals. Aggregate each model request once by requestAttemptId; primary Agent requests use official request identities without double-counting the two categories. Separate known tokens, requests with unknown usage, failures, and retries; missing usage is never filled with zero. Show sampling/session-delivery times and gaps when delayed. Metrics cannot advance business state, release waits, or alter report conclusions.

**DD09: Snapshots, Evidence, Reports, and Migration**

The selected baseline uses Session V4 and separate tool/developer messages. Domain history keeps its own schema. Use current official asynchronous history-reading and message-construction entry points; do not add implementations using deprecated snapshotEvents/eventAt/ownEvents. Do not assume official generic exports discover attachments saved in custom events automatically. EvidenceManifest explicitly maintains references, permissions, and export-read paths, and actual old-format materials verify officially supported adjacent migrations.

SourceSnapshot saves each file's original-content digest, actually used content reference, relative path, encoding/newlines, collection time, and read status. Recheck files changed during collection. If consistency at one instant cannot be guaranteed across roots, mark consistency=unverified and explain scope. Git commits are one possible basis, not a substitute for actual snapshots of uncommitted contents or ignored configuration. Code-location line numbers refer to saved versions; later source changes do not move line numbers in old reports.

SkillRevision's manifest lists SKILL.md, declared local rules, scripts, and dependency references/digests. Unfrozen dynamic dependencies cannot be claimed as part of an old version. Model-suggested skill updates produce Drafts only; user acceptance adds a version, while running batches retain the original.
