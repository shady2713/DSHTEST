# Agent Note: Detailed Design: Models and Release

Status: proposed

## Problem

Purpose-based model selection and manual desktop updates must preserve quality, authorization, and durable task state.

## Proposal

Design state: proposed product design; partial probes and prototype work do not establish final implementation or acceptance. This document elaborates I04 and I05 in the [Architecture](2026-09-28-web-testing-architecture.md) and provides detailed-design acceptance scenarios. See [Interfaces and Execution](2026-09-28-web-testing-design-execution.md) for browsers and execution, and [Data and Recovery](2026-09-28-web-testing-design-recovery.md) for persistence and recovery.

Reading order: DD10 generic decisions and adaptation → DD11 model routing → DD12 release and updates → DD13 verification scenarios. [Baseline and Upstream Upgrades](../process/2026-09-28-web-testing-upstream-baseline.md) owns the baseline, required official patches, and dependency versions; pinned versions do not establish runtime acceptance.

**DD10: Generic Lightweight Decisions and Candidate Protocols**

This section defines replaceable lightweight structured-decision capabilities and domain formats without binding to Jev or another brand. At least one real lightweight model must complete the required candidate selection/classification, Chinese-language, error, and replacement controls. Ordinary users without a configured lightweight route may still use a qualified general-purpose model; this does not permit the product to deliver only unimplemented adapter stubs.

| Domain object | Required contents and rules |
|---|---|
| ModelCapabilityDescriptor | Provider/model/identifiable version, supported modalities and languages, selection/classification and optional ranking/scoring, output-constraint mechanism, and usage/confidence field semantics. Verify unknown capabilities first; model names do not establish them. |
| DecisionRequest | schemaVersion, taskKind, observationId, routeRevision, candidate-set revision, required state, and complete candidates or labels, including exits such as none/reobserve. Inputs retain task-required materials only; secrets stay out of prompts. |
| DecisionResult | Matching request/observation identities; selected/classified/ranked/scored/abstain discriminator; legal candidates or labels; available provider metadata; raw-response evidence references. Missing results cannot be filled in as success. |
| Optional confidence information | Preserve source, numeric range, and specific meaning; missing values are unknown. Record candidate probabilities, scores, model-reported confidence, and empirical calibration separately; none is interchangeable with accuracy. |
| RoutePolicyRevision | Selects primary/fallback routes by taskKind and actual capabilities; binds encoding/validation/calibration versions. Replacing adapters or configuration does not alter business actions, assertions, or report semantics. |

Reuse an existing DSH adapter when it supports the selected provider. The application encodes DecisionRequest into a supported request and parses and strictly validates output. Use structured output through the provider's actual interface when available; without enforced schema support, still parse and validate the complete response and handle refusals/format errors without claiming server guarantees. Add an LlmAdapter only when existing adapters cannot express a proprietary protocol. Keep application schemas in the domain package, without extending DSH core message types or creating a model-call channel parallel to ctx.llm.

The public minimum capability is finite-candidate selection and finite-label classification. Enable ranking, scoring, and probability output only when selected; not every model must support them. Models return recommendations only; executors recheck observation generation, complete action candidates, permissions, and targets. High confidence cannot bypass third-party authorization or business assertions. Reject capability mismatches during routing instead of dropping necessary inputs such as images and pretending the task is unchanged.

Each request saves actual inputs, selected adapter/model, outputs, available usage, cancellation, and termination facts. DD08's sole Runtime scheduling owner manages auxiliary requests; one ctx.llm call does not automatically provide Agent logging and recovery. Selected DSH V4 supports identified messages and one-shot user inputs. Use current public constructors/RequestMessage instead of manually building old tool-result wrappers. purpose remains limited to upstream-defined purposes; taskKind stays in domain requests. [Current messages](../../../../packages/llm/llm/src/message.ts), [Request types](../../../../packages/llm/llm/src/types.ts)

Validation covers illegal candidates, missing labels, unsupported modalities, malformed JSON, non-finite numbers, missing usage, and stale observations. First verify replaceability with contract controls exhibiting different output characteristics, then make real calls and calibrate the route actually adopted. Controlled substitutes do not count as real testing of a second provider. There is no requirement to purchase two services first, and missing credentials for one brand do not block usable alternatives.

**Optional adaptation for proprietary providers.** Prefer adapters already in the selected baseline. Only when the candidate's actual protocol cannot be expressed, add an adapter under the official LlmAdapter/registerAdapter contract. Ordinary chat selectors must not treat finite-decision-only models as general chat replacements. Proprietary primitive fields, model names, and HTTP addresses belong only in the adapter's package documentation and contract tests, not in product-domain protocols or first-release brand dependencies.

Adapters explicitly define permitted modalities, message shapes, output constraints, and parameters. Unsupported images, tools, multi-turn input, or sampling parameters return explicit errors instead of silently dropping input. GenerateOptions.purpose is for upstream-defined purposes only; business taskKind stays in DecisionRequest. Provider/model, sessionId, and signal use existing DSH fields. If one JSON text message carries a decision envelope, validate version, candidates, and original values first. Do not force arbitrary chat history into a proprietary request or add parallel message types to core.

Validate result identity, candidate-set revision, complete answers, and output types. Optional probabilities, scores, and confidence retain their own units and are not renamed accuracy. Non-finite numbers, missing required answers, illegal candidates, out-of-range values, and bad formats cannot generate executable decisions. Split dependent questions into separate calls; batch interfaces do not automatically reason in business order.

Only adapters send provider HTTP requests; DD08's sole owner handles retries. After complete response validation, map non-streaming protocols to standard DSH text blocks, available usage, and finish without fabricating per-token streams or reasoning blocks. replayState uses currently permitted upstream structures, preserving adapter version, actual model, and obtainable request identity. Emit no chunks after termination and no tool blocks without real tool calls.

Map usage only from clearly defined fields under DSH's non-overlapping counting semantics; do not invent cache, reasoning, or zero-token usage. Reliable input/output counts may be summed; missing counts are unavailable. Billing rules and token statistics remain separate. Every failure retains request identity, reliable usage, and actionable reasons; an unusable answer does not erase an actual call.

| Failure fact | DSH termination and application classification | Next handling |
|---|---|---|
| User cancellation or invalidated owning task | aborted, preserving cancellation reason | Do not switch models to restart canceled work. |
| Network disconnect, request timeout, HTTP 429/529, temporary 5xx | error plus status/available requestId/providerRetryAfterMs | DD08's auxiliary-request recovery queue schedules the next ctx.llm call or capability-matched fallback route; do not assume the Agent retry plugin covers this call. |
| HTTP 401/403 or missing key | error, credential/authorization classification | Retain the task and prompt for repair in the conversation; do not continuously repeat the same request. |
| HTTP 400/422, unknown model, unsupported parameter or modality | error, configuration/input classification | Correct input or select a legal route; do not retry the same invalid request indefinitely. |
| Missing response fields or illegal probabilities/candidates | error, provider-protocol classification | Save diagnostics and prohibit result execution; bounded retry or fallback, with persistent errors awaiting intervention. |
| Response completes after observation generation becomes stale | Model response still succeeds; business decision is rejected-stale | Re-observe; model-interface success does not count as action success. |

Expose failures through existing DSH LlmFailure/HarnessError and standard finish semantics, preserving original facts and classification bases. HTTP errors are not text answers. Implement and accept concrete error-code registration together with official retry-policy recognition; custom non-retryable errors must not enter an infinite default “network error” loop. When provider error-body fields are unstable, read only validated fields and redact sensitive responses first.

Classify request timeouts separately from user cancellation: timeouts are recoverable failures, cancellation is a control result. Do not mark both aborted merely because both trigger AbortSignal. Every actual request has requestAttemptId, with waits and retry counts persisted. Recheck current observation before adopting an answer. If response validation fails but usage fields remain reliable, retain confirmed usage and request diagnostics; unusable answers do not erase calls that occurred. DD07–DD08 own complete auxiliary-request records and retry ownership.

**DD11: Model Selection, Thresholds, and Performance Acceptance**

Model integration first validates package inventory through the actual Loader, then compares ordinary requests with and without web-test using the same profile, build, and model configuration. The diagnosed REQUEST_EXTENSION occurs when tsconfig resolves a bare package name but PluginPackages.packageOf cannot resolve its manifest; source and artifact file-URL extension-preparation controls succeed. Treat this as an integration error, not a transient network failure. Real provider requests and failed-step continuation still need separate evidence. The selected baseline already includes #5214's multi-image mapping batch-deletion fix; verify the current combination without another backport.

R56 configuration proceeds as follows: select provider/model → enter credentials through dedicated controls or select an existing credential reference → show the request connection validation will make → verify connection and declared capabilities → save valid configuration/routes → show readiness or specific gaps in the owning conversation. Reuse selected DSH provider, configuration, and credential mechanisms, adapting explicitly to the product flow instead of creating a configuration channel unrelated to ctx.llm. ConnectionProbeResult records configuration version, request type, time, and result, never plaintext keys. HTTP reachability does not establish usable model/image/text capabilities; required capabilities need actual request verification.

Judge readiness for the current task, checking ordinary chat, requirement analysis, visual inspection, and lightweight decisions separately. One model may fill several roles; first startup does not require every fallback or lightweight route. Without a configured lightweight route, use configured text/multimodal routes with matching capabilities. Without vision capability, materials may still be prepared, but layout inspection cannot silently degrade to DOM reading and be declared complete. The product must still pass actual lightweight-route acceptance under AC18 and G05. User non-configuration and missing product implementation are different conclusions, independent of brand.

Credential addition/replacement/deletion uses dedicated sensitive inputs and protected storage, never Session text, route inputs, skills, or reports. Existing credentials show only masks and references. Connection errors retain actionable causes after sensitive-response cleanup. Before deleting/replacing active configuration, show impacts on associated tasks. New requests use effective configuration; already-sent requests retain original routeRevision and result ownership. Repairing credentials for the same provider may wake tasks; model/capability changes create a new route-policy version and recheck affected work, without rewriting historical usage or silently hot-swapping the run's rules.

Reuse official model-configuration controls and credential services directly; this application adds task routing, capability readiness, and connection-validation cards. M1 verifies whether public interfaces allow embedding existing editors into conversations. If not, use a thin adapter to the same configuration service while keeping initial configuration within conversations/cards; do not copy a provider backend. Official account onboarding and Coding Tools configuration cannot enable this application's prohibited write tools.

RoutePolicyRevision saves taskKind, requiredCapabilities, primary/fallback routes, model versions, input-generation version, timeouts, validators, and escalation conditions. Runs reference fixed policies; credential repair does not alter recorded historical choices. All new model requests go through ctx.llm; ordinary conversations retain native DSH Agent. Do not copy agent-loop or enable another untraceable AI backend in Browser Use.

| taskKind | Default capability | Conditions requiring escalation |
|---|---|---|
| requirements/case-planning/change-impact | Text model with strong code and business reasoning | Source/rule conflicts require user confirmation; changing models does not decide business intent. |
| candidate-selection/page-state-classification | First match a qualified deterministic recipe; otherwise use calibrated lightweight or general-purpose routes under RouteBenefitDecision | Re-observe, escalate, or wait for ambiguous targets, state changes, failed preconditions, or unmet calibration/benefit conditions; do not replay historical success. |
| visual-inspection/coordinate-grounding | Image-understanding model | Re-observe or wait if imagery is unclear or cannot be matched to targets; text models must not guess image contents. |
| exact-value/file-content/numeric-check | Deterministic parsing and comparison | Ask when semantics are undefined; do not introduce model judgment where unnecessary. |
| defect-explanation/report-summary | Model suited to evidence synthesis | Inputs come only from committed facts; outputs cannot change counts or conclusions. |
| skill-draft | Text-reasoning model | Adopt only after the user confirms the diff. |

A lightweight decision model selects one complete actionCandidateId. Candidates bind action, target, parameter references, and observation generation, avoiding separately selected actions/elements being combined into an unapproved operation. Generate candidates from cases, page observations, and policy filters; high confidence in “confirm payment” cannot bypass real-service authorization. Results remain recommendations; actual execution still passes DD02/DD03 checks.

Stable regression steps may save ExecutionRecipeRevision, binding case/rule versions, structured preconditions, semantic locators and unique-match conditions, parameter sources, controlled actions, and deterministic assertions. Resolve actual targets from fresh observations every time, recheck identity/environment/data preconditions and policy, obtain the current action slot through Runtime, then execute and collect new evidence. Recipes retain no old coordinates for direct reuse across runs, do not replay unknown business actions, and do not reuse historical passed. They are neither an additional agent-loop nor another browser-control stack. Page/semantic changes, target ambiguity, or unmet preconditions exit the recipe for reanalysis or waiting under existing rules.

RouteBenefitDecision selects default routes by task category and verified distribution. Control A is an adaptive general-purpose-model route; B is deterministic execution plus a qualified model for ambiguities; C includes lightweight decisions. All three share cases, required assertions, materials, executors, and authorization, with separate data resets and recorded order and separate first-pass/regression measurements. Include candidate generation, strong-model review, retries, failure recovery, and human takeover. B cannot skip real page operations because conclusions are cached.

Before comparison, freeze samples, repetition counts, quality constraints, primary benefit metrics, and measurement tolerance. An independent holdout set does not tune thresholds. C becomes the default for a task only if required-defect detection, correct controls, erroneous actions, and unverified counts meet the same quality gate, the preregistered primary metric improves beyond tolerance over the better qualified A/B control, and other constraints remain within limits. With insufficient evidence or no established benefit, retain the connected capability, default to qualified A or B, and report no demonstrated benefit. Delivering lightweight capability must not force an extra model call at every step. Revalidate effective scope when models, candidate generation, or business distributions change.

On first use of an uncalibrated model/language/action class, the route may assist selection but cannot independently drive business changes using an arbitrary 0.8 threshold. Establish fixed samples and select thresholds meeting predefined erroneous-action standards; otherwise use strong-model review or deterministic targets. Version calibration results and reassess changed candidate generation, model versions, or input languages. High confidence cannot replace evidence verification, and inability to calibrate must not stop other configured routes from testing.

Cache keys include input digest, actual model version, policy/schema version, case, and observation generation. Reuse only identical static analysis or exactly matching decision inputs. Dynamic-page, business-state, and modality-permission changes invalidate caches; yesterday's button selection cannot click today's page. Cross-request model-result caching is allowed only when the requested fixed model version is known before cache lookup. Seeing a version in the previous response does not establish that a drifting alias still points to it today. If versions cannot be pinned, disable this cache and record actual response versions and limitations; idempotent reads of the same committed request's result are unaffected.

DSH toolUpdate capability declarations and this application's result cache are distinct mechanisms. Use corresponding dynamic-tool projections only when the model/adapter actually declares support and passes protocol controls. Missing/unsupported declarations use upstream compatibility paths; do not fabricate capability for caching. Declarations do not prove actual provider cache hits or total savings. RouteBenefitDecision separately records input, output, available cache usage, and unknowns, including candidate generation, review, retries, and recovery in the same baseline. Recheck after changing models/adapters instead of assuming identical benefits across third-party models.

Enable expired-image-file handling only on adopted adapter paths. With DeepSeek file-upload mappings, P05/V10 cover simultaneous expiry of multiple images, invalid-mapping cleanup, reupload, and continued model requests; evaluate required upstream fixes under the baseline patch policy. Other providers perform equivalent input recovery through their own interfaces without imposing DeepSeek-specific file indexes. Check observation freshness before resending. Image expiry may refresh provider references for the same still-valid observation; changed pages require new observations. Never replay already-executed business actions that produced the screenshots or count resent model requests as new business Attempts.

Performance records separately count plan analysis, model waits, browser waits, real business waits, failure recovery, and exports. Compare the A/B/C groups above on the same cases, assertions, and environment for total duration, all known input/output tokens and unknown usage, calls, erroneous actions, defect detection, false positives, unverified counts, and user active time. Include strong-model review costs in the lightweight route. The first release promises no predefined speedup factor or savings percentage and does not remove IME, native-window, or flow verification to meet speed targets.

**DD12: Release and Updates**

The pinned manifest in [Baseline and Upstream Upgrades](../process/2026-09-28-web-testing-upstream-baseline.md) is the source of truth for baseline/dependency versions; this document maintains no second version table. M0 checks actual checkout, lockfile, required official patches, and Loader composition. M5 records actual Electron/Chromium/Node, native-driver, external-browser, and Host-protocol versions in build artifacts. Owning tasks explicitly pin candidate Playwright and selected models; dependency versions of other tools in the lockfile do not establish this application's adoption.

Register necessary official fixes by explicit commits and applicability boundaries. They enter releasable combinations only after upstream requirements and this application's failure controls pass; floating tracking of master is forbidden. DD08/V05 define missing-tool-result completion; DD11/V10 define expired-image adaptation. Every baseline-version or patch change updates BillOfMaterials and affected evidence; silent dependency replacement cannot evade baseline constraints.

The user confirmed C02: the first release supports Windows 10 22H2 (build 19045) and later, plus Windows 11 x64; earlier Windows 10 and ARM64 are excluded. The release manifest's designed minimumWindowsBuild is 19045, checked from the same field before installation. Electron 44 publicly states Windows 10+ support, but this does not replace actual verification of this application's native dependencies and complete interactions. [Electron 44 platform statement](https://github.com/electron/electron/blob/v44.0.0/README.md)

Verification includes Windows 10 build 19045 and representative Windows 11 x64 Home/Pro environments, recording full OS builds and patches. Pro-only isolation features cannot satisfy ordinary testing on Home. If future dependency upgrades require newer systems, explicitly propose the support-scope change instead of silently raising installation requirements.

Application windows use the official desktop layout; tested web viewports are independent of application-window dimensions. Users choose the actual viewport during project initialization. Native verification records monitors, scaling, DPR, and IME. Application-window adaptation covers at least 100%/125%/150%/200% scaling samples and multi-monitor switching. These are design-acceptance samples, not choices of project web resolution.

The user confirmed C03: the first personal-use release follows upstream's Windows x64 unsigned local-installation route with manually installed updates and no automatic updates. Windows may show an unknown-publisher prompt; do not disable system checks or fabricate signatures or completed formal-release records. Future signed releases retain upstream EV-signing, release-check, and application-owned update-source requirements. First-release unsigned status does not change engineering rules for upgrading with upstream. [DSH desktop release requirements](../../../../apps/desktop/README.md)

Continue reusing official desktop windows, tray, hiding, standard exit confirmation, and installer shell. Runtime supplies exit/update facts. Proposed PersistentActivitySnapshot contains sampledAt, controlRootIdentity, runId/headRevision/status, unsettled actions and recovery markers, read completeness, and errors. Its sources are persistent registration and each RunHead, not Client caches or live Agents alone. The adapter aggregates read-only facts and invokes existing lifecycle entry points without copying test state into the desktop main process.

If exit queries fail, show official confirmation on the assumption that unsaved/recoverable work may exist instead of treating activity as zero. Explicit user exit still stops dispatch and attempts to save, without promising forced termination or system shutdown always finishes disk writes. Ordinary updates require complete, consistent eligibility results and reject overwrite if missing. Static code indicates that official exit/update checks limited to live Agent/Job cannot cover all cold sessions and persistent runs. V06/V14 must verify with no active Agent; this inference is not an executed reproduction. Main-window closure retains official hiding behavior instead of entering update/exit flows.

This application must collect no product-usage analytics by default. The selected baseline's desktop composition enables desktop-product-telemetry and product-analytics, whose exporter defaults include the official collection service. Before this application's first startup, explicitly disable collection and the associated exporter through its composition/configuration; verify the effective profile, destinations, queued events, and export state. Disabling new collection does not clear an existing exporter queue. Explain and verify Session feedback telemetry, model requests, and tested-service traffic separately; preserve upstream rules and express application choices through its configuration.

Release BillOfMaterials records at least appVersion, DSH tag/build identity, lockfile digest, actual Electron/Chromium/Node versions, minimum Windows build, native dependencies, profile/plugin set, Host protocol, domain schema, DSH session format, report format, and build-evidence references. Installed artifacts require complete compiled JS and pregenerated Typert materials. Successful startup from a development directory does not pass installed-release acceptance.

The first release offers ordinary manual updates and recovery updates. Ordinary updates still require handling active, recovering, business-time-waiting, user-waiting, and unsettled runs first. Pausing does not automatically grant migration eligibility, and tasks are not forcibly canceled. Recovery updates address old-program defects preventing task progress. After explicit selection in the owning conversation or installer recovery entry point, freeze under the flow below without requiring old execution logic to finish tasks or convert UNKNOWN into settled outcomes. Neither route automatically downloads or hot-swaps executors, and neither changes C03.

Recovery-update order: close dispatch and revoke old permits → stop relevant Agents/execution processes and confirm they cannot accept more actions → obtain a consistent backup and FrozenRunManifest under the stable control-root lock → let an independent preflight/recovery entry point supporting the old format check compatibility evidence → register RecoveryUpdateIntent bound to package digest, backup digest, and frozen runs → user manually installs/candidate data migrates → new version enters recovery-only → read-only verification of history and in-flight business → create linked continuation after eligibility. The recovery coordinator owns freezing; it does not call the stalled business scheduler for completion acknowledgment. Do not overwrite the old combination if executor revocation is unconfirmed, formats unreadable, backups inconsistent, or migration unsupported. Offer read-only diagnostics and a handling path that retains materials.

FrozenRunManifest records the last committed head/plan/environment/original execution combination, original pause/cancel intents, every unsettled operationId, attachment/reference manifests, freeze reason, and user choice. Old runs display frozen-recovery, never ended, canceled, or passed; original reports and attempts remain unchanged. New execution combinations use new runIds and RecoveryLink to connect original runs, verified facts, and instances needing follow-up. Cross-version steps cannot be spliced into one complete pass. UNKNOWN remains on the cross-run reconciliation list; changing runId cannot restore dispatch eligibility for the same business intent. Redispatch is allowed under existing rules only after reliable proof that the original action did not occur and cannot take effect late. Choosing an update does not confirm non-occurrence.

recovery-only prohibits automatic business dispatch and cleanup. First restore references/control state and perform authorized read-only reconciliation; original pause/cancel choices remain effective. Independent work unaffected by unknown actions may create a new run after user-selected continuation and renewed environment/case readiness. Unknown portions still await verification or remain report gaps. Installing a fixed application and completing old tasks are separate acceptance conclusions; no promise is made that all corruption is automatically repairable.

Closing the application does not end all runs. Installation preflight reads persistent task registration and each RunHead, covering queued, paused, waiting, and unknown actions. Ordinary updates reject ineligible states; recovery updates accept only frozen runs passing recovery-eligibility checks. After the old program exits, an independent coordinator acquires DD07's same control-root lock. From checking through switching, new Hosts cannot open authoritative storage or accept tasks. Missing checkers, unrecognized formats, or absent recovery eligibility prohibit overwrite; never guess that no tasks exist. P08 verifies and M5-T02 completes independent preflight versioning, ownership, and real installer integration.

After installation eligibility, register an update intent bound to the target package digest at the stable control root; the installation coordinator holds the lock until the installation phase ends. A new Host acquires the same lock and handles the update intent first, permitting only the designated version to migrate and verify eligibility. Open tasks only after success. Coordinator crashes or unsettled update intents enter recovery instead of ordinary startup. Preserve verifiable original-program and original-data recovery materials before overwrite. These are proposed integrations requiring V14 and upstream installer checks, not existing official task-protection capabilities.

A run pins its application/executor combination. Recovery updates freeze old runs, assigning actual execution by the new combination to RecoveryLink-linked new runs instead of replacing old Attempts in place. If the system independently upgrades external Chrome/Edge, record actual environment changes and segment or rerun affected flows instead of pretending the original version remains. Official plugin management in this application configuration also follows runtime-version pinning and source protection; it cannot replace providers or load unrestricted tools during execution to bypass policy.

Code upgrades preserve upstream/origin history and compare root/nested AGENTS, skills, referenced rules, generators, and checks on a separate upgrade branch. Conflict-free text still needs semantic review. Runtime-data migration first backs up to a verifiable location, verifies candidate data generations, then switches under the same control-root lock. On failure, recover with the original program and data; never feed new-schema data directly to old programs. The [Upgrade Policy](../process/2026-09-28-web-testing-upstream-baseline.md) owns the concrete upstream-inheritance/change inventory.
