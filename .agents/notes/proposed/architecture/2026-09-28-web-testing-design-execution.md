# Agent Note: Detailed Design: Interfaces and Execution

Status: proposed

English | [中文](2026-09-28-web-testing-design-execution.zh.md)

## Problem

Browser and native operations need consistent target identity, authorization, observation freshness, and tested-source protection.

## Proposal

Design state: proposed product design; partial probes and prototype work do not establish final implementation or acceptance. This document elaborates I01 and I03 in the [Technical Architecture](2026-09-28-web-testing-architecture.md) and defines analysis, execution, and interaction interfaces. See [Data and Recovery](2026-09-28-web-testing-design-recovery.md) for data commits and [Models and Release](2026-09-28-web-testing-design-models-release.md) for models and release. [Requirements R01–R58](../feature/2026-09-28-web-testing-requirements.md) remain authoritative for product scope. Interfaces and package names here are proposed additions, not statements of existing DSH functionality.

Reading order: DD01 modules and calls → DD02 browser → DD03 native control and source protection → DD04 project analysis and backend → DD05 conversations and tool presentation. The user has confirmed C01: controlled operations under the current Windows account; DD03 defines the protection level and limitations.

**DD01: Modules, Callers, and Resource Owners**

Use the official workspace, Electron desktop startup, and Host/Client compilation surfaces pinned in [Baseline and Upstream Upgrades](../process/2026-09-28-web-testing-upstream-baseline.md). The following package locations are planned by responsibility; actual package splits require current callers rather than mechanically creating a package for every responsibility box. New packages follow existing package groups and formal repository-entry rules. Package AGENTS files add module facts only and do not replace upstream rules.

The official desktop owns the main window, chat, sidebar layout, shortcuts, tray, hiding on close, and standard exit confirmation. This application integrates test cards, target resources, and persistent-run facts without rebuilding these components. Model-provider and key editing/storage reuse official controls/services. M1 verifies card-embedding interfaces; do not claim zero adaptation in advance or make configuration possible only on a standalone settings page.

Do not separately export abstractions without current callers. Cross-package shared types belong in the definition package; types used by one implementation within a package stay there. Separate service providers and consumers, declare required dependencies through inject, and give registrations/subscriptions effect owners. Only Runtime changes authoritative test records; analyzers, models, Client, browsers, and report generators submit candidate facts.

Client→Host business calls use @Remote/@RemoteScope, with Typert-generated client types and runtime descriptors accessed through api-remotes, ctx.remote, and Connection. Do not handwrite parallel DTOs or carry project, case, or report business through Electron IPC. The methods below return commit receipts or query results; committed records and session projections express long-task completion. [DSH API gateway](../../../../docs/api-gateway.md)

Write commands share a receipt containing commandId, resourceId, acceptedRevision, outcome, and necessary pendingReason. accepted means committed only, never “test passed.” An existing commandId with the same original parameter hash returns the original receipt; different parameters raise COMMAND_ID_REUSED. pause/cancel operates on the current state of an explicit runId without depending on a stale UI-cached revision; plan changes and skill acceptance must check expected versions. Errors distinguish version conflicts, user waits, unavailable capabilities, invalid environments, save failures, and permanent configuration errors. Retry advice is not permission to replay a business operation.

commandId deduplication is scoped to the owning stable resource. Initial creation belongs to the data root's creation entry point, with method and parameters included in the hash. Client generates and retains the ID before first sending and reuses it on connection retries. Initial project/run creation must also persist this ID and a reserved resource ID first; deduplication cannot begin only after a new RunHead exists. Project and skill revisions commit through their respective authoritative heads; DD06–DD07 define creation/publication. The same command still creating or saving returns the original resource and pending, without starting another task.

Electron requires a controlled TargetBroker. M0 first checks reusable guest lease/preload/main-process mechanisms and adds only the minimum messages required for Host target automation. It accepts internal requests only from the connected Host, extending existing Node child-process IPC with discriminated messages carrying version, requestId, and hostEpoch. Do not expose process.send or raw Electron IPC to renderer pages. Changes to an existing message union synchronize senders, receivers, validators, protocol-version compatibility checks, packaging records, and expected outputs; changing one side or assuming type compatibility because the protocol number is unchanged is insufficient. [Existing Host process](../../../../apps/desktop/src/host-process.ts), [Protocol version](../../../../apps/desktop/src/host-protocol.ts)

Broker understands target lifecycle, observations, finite input actions, screenshots, viewports, download paths, dispatch-permit invalidation, and resource closure only; it does not understand “pass,” “defect,” or “update case.” A request's targetId must exist in the target table owned by the current Host generation. Reject arbitrary webContentsIds, arbitrary CDP methods, JavaScript strings, shells, and user-specified preloads. On Host disconnect, reject new actions and invalidate old permits before closing and rebuilding resources.

**DD02: Embedded Browser and Operation Protocol**

P01 resumes local implementation within M0-T03's existing write scope; an upstream browser-provider release is not a prerequisite. The selected baseline already ships a Desktop Sidebar webview with main-process guest ownership, while its official profiles assemble no Browser Use provider for controlled Host automation. This proposal connects those missing operations through one controlled provider and a finite Broker. Existing standalone-browser or UIA evidence does not satisfy embedded-browser or P03 acceptance; ordered implementation and failure controls belong to [M0-T03](../process/2026-09-28-web-testing-tasks-m0.md), and bounded implementation permission belongs to [limited development admission](../process/2026-09-28-web-testing-tasks-m1.md#development-admission).

The proposed first integration reuses the existing webview lease and presentation through the real DSH Loader and official desktop entry. Main retains ownership of guest WebContents; Host receives scoped target identities and finite observation/input operations, never Electron objects or arbitrary CDP access. After the main-document business scenario and target-denial controls produce evidence, P01 compares an independently owned WebContentsView under the same scenario and restrictions before choosing the carrier. BrowserCarrierDecision records runtime evidence, unresolved capability rows, required upstream changes, and maintenance costs; neither upstream adoption nor an isolated API failure determines the result. The unselected candidate need not be fully productized.

The Broker uses the connected Host's private child-process IPC described in DD01 and binds each request to its authenticated connection, Host/window/target epochs, and active lease. Main validates target ownership, current document/observation, dispatch permit, and the operation allowlist before execution; an unknown message or invalid owner/epoch is denied. Fixed, reviewed page-read operations may return bounded observations; callers cannot supply executable strings or choose arbitrary Electron/CDP methods. Page content, including child targets, receives no control credential or control endpoint. Disconnect, cancellation, release, and owner replacement invalidate affected permits before any late callback can dispatch another action.

Direct attachment to an owned page WebContents and automatic attachment to related targets are separate capabilities. The proposed main-document probe uses target-level debugger commands without making `Target.setAutoAttach` a prerequisite; child-frame/OOPIF, worker, and popup behavior still needs its own evidence. An auto-attachment failure must identify runtime, target type, and missing behavior before a route adjustment; it cannot justify weakening the matrix or guarantee that changing carriers solves it. Debugger detach and DevTools contention invalidate affected observations and permits. [Electron v44 Debugger](https://raw.githubusercontent.com/electron/electron/v44.0.0/docs/api/debugger.md), [CDP Target](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Target.pdl)

Official guests share temporary partitions by canonical CWD and forbid downloads, permission requests, and native dialogs by default. This application must specify run/activation/role scope before first navigation; changing partition requires a new target, never an in-place switch on an open page. Enable legitimate downloads/popups/file selection in a controlled, case-specific manner, without adopting the ordinary browser panel's blanket denial or removing isolation globally. Controlled targets must satisfy run lifecycle requirements after chat-sidebar unmount/window closure; React mounting alone cannot own them.

The official account-page WebContentsView has dedicated identity and preload semantics and cannot directly host untrusted tested pages. P01 may reuse its layout and lifecycle lessons, but test targets require this section's isolation configuration and separate ownership.

P01 comparison covers at least role partitions, navigation/iframes/popups, downloads, focus/input, viewports/screenshots, target retention after window closure, and Host-disconnect revocation/reconstruction. This section still owns the full capability matrix. Electron's current documentation warns of webview stability risks and suggests considering alternatives; this informs comparison rather than proving webview unusable or WebContentsView qualified. [Electron documentation](https://www.electronjs.org/docs/latest/api/webview-tag), [Upstream implementation and verification gaps](../../implemented/feature/2026-09-20-desktop-browser-webview.md)

The unified browser provider registers ctx.browserUse once and reuses SessionResources to manage ownership by the exact active Agent. ctx.browserUse itself registers providers only; it does not provide open/click operations, which belong to this application's tools and implementation. Each execution Agent owns a set of targets and identity contexts, with Runtime linking runId. Resuming an original Session into a new Agent cannot reuse the old Agent object or element tokens. [Official Browser Use](../../../../docs/subsystems/browser-use.md), [SessionResources source](../../../../packages/experimental/browser-use-runtime/src/index.ts)

In this baseline, SessionResources.run serializes by exact Agent; concurrent calls for the same Agent do not automatically produce business concurrency. To operate multiple identities concurrently, place the planned execution group inside one run callback. The group's executor dispatches concurrently to different targets, preserving each branch's action identity, authorization, and results independently. Never nest run for the same Agent inside its callback or modify the upstream queue to relax ownership. The group waits only for this bounded interaction; persist long business waits and exit the callback. The same target and native desktop remain serial. If the capability cannot support real concurrency, report unverified; sequential clicks cannot pass a concurrency scenario.

Embedded-page browser Sessions are separate from the application UI Session. A partition identity includes projectId, environment version, runId, active-Agent generation, and a unique contextId; role and isolation mode are context configuration, not grounds for sharing active profiles by role name alone. Different roles or independent runs must not share writable cookies, IndexedDB, cache, or Service Worker state. Preserve legitimate cross-origin login for one business identity. A plan's explicit ProfileRevision reference determines use of historical login state. Create new contexts through supported state import or profile copying with no active writer; do not directly share historical profile directories or reuse “whatever page happened to remain open.” Dynamic browser profiles and static source snapshots are distinct asset classes.

Test pages explicitly disable nodeIntegration, enable contextIsolation, sandbox, and webSecurity, and load no application preload. Popups and child targets inherit security settings and identity ownership at creation. Application credential injection is permitted only into application-owned documents. Neither main frames nor subframes may load dsh-app, file, or Host control addresses. Legitimate localhost test entry points are allowed; do not ban all local sites. Assign ownership individually for project redirects, login providers, browser permissions, and downloads rather than disabling isolation globally for compatibility.

Host control-plane restrictions also cover subresources, fetch, WebSocket, and Service Worker requests, not navigation alone. Host independently validates connection identities and origins and supplies no application authentication material to test pages; pages and child targets cannot access the control plane. Restrict actual control endpoints without disrupting configured local services under test.

**Observations and target identity.** Observation contains at least observationId, runId, instanceId, targetId, contextId, targetGeneration, navigationEpoch, frameId, documentId, observedAt, URL, role, CSS viewport, DPR, browser zoom, DOM/AX summary references, screenshot references, and candidate elements. Candidate-element tokens are usable only while their target, document, and observation conditions remain valid. Runtime may use backendNodeId internally without treating it as a permanent business ID.

Action requests contain operationId, stepId, actionSlotId, expectedStepRevision, actionKind, targetRef, observationId, preconditions, parameters, deadline, and dispatchPermit. Runtime assigns action slots and operation identities; models cannot advance step revisions or issue permits. See DD06 for deduplication. Text parameters reference saved InputValues, preserving CR/LF, spaces, Unicode, and exact values. Conversation presentation may escape them, but the presentation layer cannot rewrite execution values. Before clicking, check target document, role, visibility, interactability, and hit object; rerendering at the same URL can invalidate a reference. Screenshot coordinates include image dimensions, coordinate system, and collection generation; CSS coordinates must not be used directly as Windows physical pixels.

| Operation group | Implementation | What success establishes |
|---|---|---|
| observe/waitFor | DOM, AX, network/page events, and screenshots; waits on explicit conditions | A current observation or satisfaction of stated wait conditions, not a passed case. |
| navigate/back/forward/selectTarget | Broker-managed targets; records frame and navigation generation | Navigation or target selection completed; page readiness and business assertions remain necessary. |
| click/doubleClick/hover/scroll/drag | Finite CDP Input or controlled native input, dispatched after target validation | Input was delivered; save/drag outcomes require separate observation. |
| typeText/pressKey/paste | Real input events; the case fixes the input method | Direct assignment cannot bypass keyboard, newline, paste, or IME tests. |
| selectOption/toggle | Paths through user-operable controls | The selection took effect; no direct modification of internal page business state. |
| upload/download | Staged test-file directories, download events, and content reading | A file path was submitted or download completed; file contents require independent checks. |
| dialog/permission | Owned JS dialogs, browser permissions, and native dialogs | Records actual acceptance, rejection, cancellation, and subsequent page behavior. |
| capture/readNetwork/readConsole | Links current target, time, and request identity | Produces diagnostic evidence; network status codes do not automatically establish business success. |

Implementations may use reviewed fixed page-reading functions, but models cannot submit arbitrary evaluate expressions. Standard actions prefer browser-input capabilities; Canvas, closed Shadow DOM, Chinese IME, and native file selection use suitable visual/computer paths. Native file-dialog tests must actually open, select, or cancel; setting input.files belongs only to a separately planned file-content scenario.

Determine page readiness from element state, application characteristics, and bounded waits, not networkidle alone or fixed sleep followed by screenshot-based failure decisions. Distinguish operation wait limits from business acceptance deadlines; without a business deadline, record measurements and blocking bases only. Targets can still change between validation and clicking, so post-click observation is mandatory. If the affected record cannot be established, mark the outcome unknown rather than treating dispatched clicks as success.

Cross-origin iframe/OOPIF CDP child sessions, popups, downloads, and permissions belong to the provider's real capability matrix. Debugger detachment, DevTools contention, page crashes, or target closure invalidate tokens, record unfinished actions, and rebuild observations; never silently switch to another page with the same URL. With pending runs, reuse official hide-on-close behavior; do not destroy BrowserWindow and assume its pages remain active. Explicit exit follows the official exit flow enriched with persistent-run facts. Show foreground-input occupancy in the conversation and restore the test-target window; native input cannot be claimed on hidden pages.

The same provider's external implementation manages Chrome/Edge exception flows using dedicated browser contexts launched by Playwright. Pin the Playwright version for the first release, then record actual browser versions. Connect to an existing standalone browser only through explicit targets; report CDP attachment and native Playwright connection capabilities separately. Never take over users' everyday profile directories. Complete the relevant login/business flow in the selected identity context; external cookies do not automatically enter embedded pages. Playwright is a deterministic driver here and does not invoke its own AI routing. [Connection capability differences](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)

**DD03: Windows Native Control and Read-Only Source Protection**

Confirmed choice C01 uses the current Windows account and application-level controlled operations to protect tested source. Permit test browsers, relevant native windows, and validated existing commands; forbid arbitrary terminals, code editors, and unrestricted desktop control. If source-write effects cannot be established, block and explain affected items while independent items continue. This is not an operating-system-level isolation guarantee; the first release does not require creating an account or changing user ACLs.

The protection level follows these facts: the official Windows sandbox provider reports partial file isolation, with hard-link, read/network, AppContainer ACL, and other boundaries. Native input can control other programs at the same integrity level, and programs under the same account generally share that user's file permissions. The product therefore verifies restrictions at all its own supported entry points without claiming resistance to arbitrary same-account programs, executor vulnerabilities, or writes after users deliberately remove restrictions. [DSH sandbox](../../../../docs/subsystems/sandbox.md), [Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

The application runs without elevation, never requests administrator privileges automatically, does not operate the UAC secure desktop, and does not treat an administrator account as execution permission. Path checks use actual resolved identities, handling junctions, symbolic links, UNC paths, and directory replacement. A “read-only” file attribute is not proof of system protection. Separate accounts and stronger isolation are not first-release prerequisites; changing the guarantee level later requires redesign and explicit confirmation. [Windows file permissions](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)

Project configuration distinguishes source/configuration/dependency files from legitimate business databases, uploads, logs, and runtime caches. For overlapping paths or unclear effects, first analyze the existing deployment layout instead of changing configuration unilaterally. Local path checks cannot fully control writes by the tested service itself. Reject business entry points that edit source, write configuration, or execute arbitrary management scripts, even when exposed through a web page. Check existing commands' arguments, runtime configuration, and known file effects; mark them blocked when effects cannot be reliably constrained or assessed.

The protected set includes all source directories, project configuration, dependencies, Git metadata, and frozen analysis materials. The writable set covers application state, evidence, reports, managed browser data, and dedicated test files. Source files are never download/export destinations. Recheck write paths through final parent-directory and file identities; reject uncertain writes while retaining tasks. Exports cannot overwrite arbitrary user files; explicit selection of an existing destination file requires a separate overwrite decision.

Frozen application-owned analysis copies cannot have their contents rewritten. DD09's separate cleanup entry point handles lifecycle deletion after explicit R55 confirmation; it is not a general model-write tool and authorizes no deletion of original project files. Reference ownership determines mutual exclusion between shared-asset reading and cleanup.

Ordinary DSH conversations retain conversation, reading, and reasoning functionality without assembling project-modification tools by default. Skill scripts, PTC child calls, MCP, plugin installation, and management commands cannot broaden protected scope. User-added general DSH plugins that bypass unified executors cannot directly obtain operational capability in the test profile; add capabilities only through verified adapters. Controlled tools, path checks, and target checks must apply at actual execution. Prompts and after-the-fact file digests are aids, not substitutes for rejection mechanisms.

Enabling new tools at runtime or changing the enabled tool set during official onboarding must recheck actual executors and policy; configuration enablement is not safety clearance. Human approval after automated-review rejection also cannot override absolute prohibitions such as read-only source protection. Only business authorizations within allowed scope enter approval. V08 covers dynamic tools, onboarding configuration, PTC child calls, and approval paths together.

Native control uses @trycua/cua-driver pinned in the baseline manifest, creating its SDK instance inside Host. Because the upstream native provider exposes its entire discovered catalog, this application uses a controlled provider of its own, reusing the SDK and official tool-result conversion and registering as the sole Computer Use provider. Do not load the unrestricted upstream native provider alongside it. The first version accepts that a native SDK crash can terminate Host and recovers from committed DD07 state; it does not claim native-process isolation has been implemented. [Upstream provider implementation](../../../../packages/experimental/computer-use-cua-driver-native/src/index.ts)

At startup, verify the SDK's discovered catalog and parameter schemas for used tools. Map only window discovery, window snapshots, element/coordinate input, and necessary clipboard capabilities. Missing capabilities report capability-unavailable; do not guess tool names. Calls use the actual listToolsJson/callTool interfaces, merging execution and lifecycle cancellation signals. On unload, stop accepting work, cancel waits, settle or mark in-flight work, then call shutdown/uniffiDestroy; failures must not release occupancy prematurely.

DesktopLease records runId, instanceId, hostEpoch, windowToken, processId, acquiredAt, mode, and control generation. Prefer SDK-supported background input by default. Foreground-required scenarios explicitly occupy the desktop; foreground refusal never implicitly escalates. Before input, check foreground window, process, and a fresh snapshot; verify afterward and revoke subsequent permits if another program takes focus. System-global input has no atomic transaction with window switching by external applications; this residual risk is part of the confirmed application-level protection limit, and focus checks must not be claimed to eliminate it. Never automatically take over the application's own conversation, settings, plugin, or update windows. Native file dialogs expose only selection, cancellation, and controlled saving; ancillary deletion, permission changes, and program launching remain unavailable.

Record screen lock, sleep, Remote Desktop disconnect, and user takeover as environment waits, releasing releasable input resources. On recovery, verify the interactive desktop and display conditions. Independent cases may continue if background browsers can operate; steps requiring real input cannot fabricate success. Multi-role business concurrency can use isolated browser contexts, but native input serializes across the desktop; “two Agents clicking one desktop at once” is not the concurrency implementation.

**DD04: Analysis, Cases, and Existing Backend Entry Points**

Project analysis splits into small persistent tasks: inventory materials → collect contents → establish entry-point/feature/business-state relationships → generate scenarios → generate cases → check omissions and questions. Each task references input snapshots, analyzer/model versions, and output records; after interruption, redo only uncommitted tasks. Language detection selects optional parsers, while generic text reading and retrieval remain available. Inventory binary files, failed reads, oversized files, and uninferable portions; “enumerated” does not mean understood.

FeatureRecord's stable identity comes from business capabilities and entry-point/state relationships, not order IDs in temporary routes. Record source-derived inferences as implementation-derived, user-confirmed rules as user-confirmed, and existing requirements/skills with their own sources and versions. Conflicts or expectations that cannot support a judgment generate Questions to resolve for affected cases before testing; original code behavior cannot automatically override business expectations.

These source types describe origins, not assertion expectationAuthority. The report specification classifies assertions as confirmed-business, applicable-generic, or implementation-only. Critical rules for amounts, permissions, state transitions, deletion, and external effects enter criticalRuleReview; even clear code behavior requires binding to a user-confirmed concrete rule revision. Implementation-only matching enters observationComparison diagnostics, never business passed. Unconfirmed expectations retain questions and the coverage denominator.

CaseVersion saves stepId, role and entry point, original input values, action intent, preconditions, assertions and their bases, observation channels, data dependencies, and postprocessing. Skills provide check templates and business knowledge; executors provide real capabilities, and neither replaces the other. Without a design, visual assertions target occlusion, overflow, truncation, misalignment, inoperability, and business semantics; aesthetic preferences do not automatically become defects. Save imagery and element geometry for suspected issues, rechecking on stable pages with necessary controls.

Completeness checks separately produce material-analysis inventories, identified-feature inventories, case mappings, and execution-instance plans. Counts may show analyzed-file proportions, mapped-feature counts, and unverified assertions, but do not imply code-branch coverage or exhaustion of all unknown features. Newly discovered features first save a PlanRevision before formal testing. Portions with new business questions are skipped and reported under existing rules.

Existing backend entry points use BackendActionDescriptor: actionId/revision, entry-point type, HTTP method/path or executable identity, parameter schema, permitted working directory, environment-variable allowlist, business side effects, external-service triggers, result observation, data links, and retry conditions. Models select actionId and submit structured parameters, never complete shell commands. Descriptor changes create a new version; active runs keep referencing the original version.

Management commands use explicit executables and argv arrays: no concatenated commands, arbitrary user shell profiles, dependency installation, or configuration changes. A command's “read-only” description does not prove isolation; child processes remain subject to protected-path, permission, and DSH confinement checks. Block an entry point if required protection cannot be obtained. Observe final state for background-task triggers by business linkage ID; HTTP 202, job submission, and exit code 0 establish acceptance only.

Actual third-party actions use ActionAuthorization containing at least environment, service, action, recipient/amount or data scope, allowed count, expiry, and whether resend is allowed after verification. Confirmation cards reference a fixed authorization-draft version; out-of-scope actions require reconfirmation. Indirect sending discovered by code analysis also links authorization. Skip absent real services under confirmed rules; inability to tell whether a service is real does not establish “no service.” Without idempotency or reliable querying, lost receipts mean unknown outcomes; authorization counts cannot establish occurrence.

R54 EnvironmentDeclaration precedes formal execution and business-data preparation, binding environment nature, account/tenant, data scope, user-confirmation message, and relevant configuration digest to each entry point. Test environments may confirm the full test-data set. Changes in production/unknown environments require kind=environment-action ActionAuthorization referencing explicit PlanRevision, case/preparation/cleanup steps, target-record scope, counts, and expiry. Existing kind=external-service authorization remains independently necessary; neither insufficient authorization permits dispatch, and absence of third-party sending does not bypass environment authorization.

Executors classify actions by actual effects, not GET/POST, button names, or “read-only” labels. Plans describe known side effects of necessary login and observation. Actions that may create records, affect shared state, or simulate faults also validate environment scope. On entry-point/relevant-configuration changes or observations contradicting declarations, close new dispatches for affected scope and recheck; other verified entry points may continue. User declarations are not technical attestation, and environment authorization cannot lift source-write prohibitions.

**DD05: Natural Language and Tool Presentation**

The application profile does not assemble unrestricted sidebar terminals or their service entry points. Upstream user terminals run with system-user permissions; merely hiding buttons or assuming the Agent sandbox covers them is insufficient. Ordinary DSH conversations remain available; session archival and plugin changes must account for unfinished persistent tasks.

Natural language first identifies the associated project and runId; use a single clear context directly. Generating cases, changing rules, executing tests, pausing, and canceling are different commands. “Generate cases only” fixes plan-only and prepares no business-changing data. Runtime validates model-proposed business commands; explicit Client controls use the same service entry point. Status queries do not start an Agent.

Ordinary chat and execution sessions have separate lifecycles linked through runId and originatingSessionId. Chats without a project do not automatically load other projects' materials; project chats follow the same read-only policy. An execution Agent's tool catalog narrows to the current task, but executors ultimately enforce capability restrictions. Switching conversations or closing chat views does not release test resources.

Host presenters derive presentation solely from inputs, results, and existing metadata; Client does not infer execution state from wording. Conversation nodes carry stable business IDs and committed revisions and reread facts after reconnecting. Pending items appear only in their owning desktop conversation.
