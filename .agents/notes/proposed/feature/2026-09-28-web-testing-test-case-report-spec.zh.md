# Agent Note: 测试用例与报告规格

Status: proposed

[English](2026-09-28-web-testing-test-case-report-spec.md) | 中文

## 问题

测试结果需要明确的预期、执行证据和可复现缺陷信息，供用户与 coding agent 理解。

## 提案

状态：现行产品规格，尚未实现或验收，不是实际测试报告。关联[产品需求](2026-09-28-web-testing-requirements.zh.md)、[技术架构](../architecture/2026-09-28-web-testing-architecture.zh.md)及[验收标准与追踪](../testing/2026-09-28-web-testing-acceptance.zh.md)。领域记录、Session 日志、附件原件和导出引用的技术归属见 TD03、DD06–DD09；不另建报告专用模型日志或附件存储机制。

本规格约束用例准备、执行、结论与交接：开测前确认必要业务预期，执行中新发现的普通业务疑问先跳过受影响部分，确认后新建用例版本并实际补测。具有页面入口的用例须实际操作页面；后端触发、数据准备、报告生成及源码分析均不能代替该操作。平台、源码只读、环境授权与数据清理边界以产品需求为准。

**预期依据与结论边界**

每条断言保存 expectationAuthority、来源版本及适用性，采用以下三类依据。操作许可、范围确认和模型置信度均不能自动提升依据等级。

| 依据 | 可以形成的结论 | 不能据此推出的结论 |
|---|---|---|
| confirmed-business | 来自用户明确确认、仍适用的已确认用例或明确承载该规则的已接受 skill（技能）；核验相应业务预期。 | 确认一个规则不等于确认代码中其他推断；整份 skill 接受不确认其中没有表达的业务规则。 |
| applicable-generic | 来自有版本的通用测试规则，且已记录当前控件／场景适用性，例如内容被遮挡导致无法操作；核验该通用要求。 | 通用规则不能决定优惠门槛、谁能审批等项目业务意图；有实际冲突时转待确认。 |
| implementation-only | 仅来自现有代码／页面；可以记录 observationComparison 的 matched／mismatched／unknown，展示“与当前实现一致／不一致／无法比较”。 | 匹配不等于业务正确；不将这类诊断作为必测业务断言的 passed 或完整验证证据。 |

criticalRuleReview 在首次开测及相关变更时，按业务流程集中展示适用的金额、权限、状态、删除与外部动作规则；保存逐条来源、用户回答和用例修订，不要求用户重写完整需求。未获确认的关键规则先解决再执行依赖它的业务变更；普通未明确预期保留待确认，独立已具备依据的检查遵守原调度规则。模型不能仅凭“实现很明确”免除此核对。

每条必测业务断言的 verdict 与诊断比较分开；implementation-only 的业务 verdict 为 needs-confirmation，观察匹配不改变它。纯实现诊断单列数量，不进入必测业务／通用验证的通过分子。必须验证的业务断言仍留在分母；依据分类、缺失和排除理由可由报告数据重算。已确认业务规则与适用通用规则分别统计，只有全部适用必测断言满足原完成规则，才可声明全面验证完成。

**用例准备、执行和补测**

1. 分析本次完整项目的各代码目录、各端页面、角色、用户测试要求、skill 和历史资产，整理功能清单、单项及跨入口流程用例，并核对功能与用例的对应关系；纳入适用的异常恢复、文件内容、跨时间及历史数据兼容场景，先列出必要前置条件和准备步骤。首次测试必须先有用例；此阶段不以“准备”为名提前变更被测业务数据。
2. 若有用户指定或项目当前采用的历史基线，比较代码与功能依赖，展示新增、改变、移除和间接受影响的用例。代码变化提供实现证据；变化是否符合新业务要求，不能仅凭代码判断。
3. 开测前集中提出明确问题并审阅 criticalRuleReview；关键规则即使代码没有歧义也核对，附原预期、新建议、相关代码和影响用例。用户通过自然语言回答后，答案写入用例的新版本，再按已保存的准备步骤和既有授权准备业务数据。已经确认且没有相关变化的规则不重复询问；用户只要求生成用例时不执行这些准备动作。
4. 有页面入口的用例执行真实浏览器与必要电脑操作；没有页面入口的后端用例使用现有接口或已有管理命令触发，按各自预期核验。执行发现的新业务疑问先跳过受影响的检查项，继续独立用例，不在这一阶段为了普通业务歧义频繁打断用户。
5. 生成报告，分开呈现缺陷、工具执行问题、环境问题及待确认预期。支付、短信、邮件的真实外部动作确认和必要登录接管，仍按已确认规则处理。
6. 用户回复待确认事项后，将回答落实到用例版本；关联当前测试版本与环境，重新准备前置条件并实际补测。保存补测记录，保留原报告和原用例版本。不能靠改状态将未验证项变为通过。

执行期间发现原清单遗漏的功能时，先记录发现依据。预期已明确且处于本轮范围及既有授权内的场景，增补用例并保存计划变更后执行；新的业务疑问继续按既定规则跳过并汇总。原有用例及已执行记录保留各自版本，不能事后用新增用例重新包装此前的执行过程。

用例至少保存以下字段。

| 字段 | 内容要求 |
|---|---|
| 标识与版本 | 项目内稳定用例 ID、用例版本、创建与变更依据。 |
| 执行实例 | 本轮具体环境、角色或跨角色流程、浏览器、视口、数据组及异常条件的适用组合；每个实例具有独立 ID，各次复试关联原实例。 |
| 功能与需求 | 功能 ID、页面入口、需求描述、代码或用户确认来源；区分推断与已确认规则；每条断言标注三类预期依据及适用性，关键规则确认绑定消息和版本 |
| 所属业务流程 | 流程 ID、参与入口与角色、业务记录的关联方式、正常及适用异常分支。 |
| 适用条件 | 版本范围、角色、业务状态、浏览器及项目确认的网页视口；适用时包含浏览器缩放、DPR 和原生操作的显示条件。 |
| 前置条件 | 需要的账号、数据、关联记录、环境服务、前序用例。 |
| 测试数据 | 精确值、生成方式和本次实例；空白、换行和边界数据保留原值及转义表示。 |
| 数据与文件准备 | 所需状态、准备入口、实际记录及依赖、原始附件引用、内容预期、准备结果和缺失条件。 |
| 异常条件与恢复 | 受影响页面或请求、注入方式与时机、结束条件、生效及解除证据、异常期间与恢复后的业务断言。 |
| 业务时间 | 触发时刻、相关时区、预期时刻或允许窗口、计划与实际观察时间；区分真实定时触发及提前执行处理逻辑。 |
| 历史材料来源 | 旧业务记录、附件、会话或缓存的来源版本及适用条件；无法确认的来源和无法取得的材料明确记录。 |
| 执行中增补 | 发现入口或状态的时间与依据、新增用例及计划版本、覆盖范围变化和关联待确认问题。 |
| 操作与预期 | 每一步的实际交互或后端触发方式、观察点、预期结果、判断依据；哪些步骤必须使用键盘或桌面操作。 |
| 跨入口步骤 | 逐步记录入口、角色与会话、同一业务记录标识、前后状态和关联证据；角色间切换及异步等待不能省略。 |
| 证据要求 | 关键截图、执行记录以及适用的请求、日志、只读数据库核验。 |
| 后置处理 | 按已确认策略保留缺陷复现及关联数据，清理其他本轮新增数据；记录对其他用例的影响，不得修改被测源代码。 |
| 未决事项 | 待确认问题、受影响步骤、用户回答及落实到哪个用例版本。 |

**报告呈现形式**

提供应用内报告及下列导出形式；使用同一份结构化测试记录生成，避免多份报告结论不一致。

| 形式 | 面向谁 | 用途 |
|---|---|---|
| 对话摘要与应用内报告 | 用户 | 对话先说明结果和缺口；展开后查看功能、用例、问题和证据，直接通过对话补充业务预期或要求复测。 |
| 离线 HTML | 用户及其他阅读者 | 可浏览完整报告和随包截图，不依赖登录应用或仍然有效的远程链接。 |
| Markdown | 用户与编程助手 | 提供总体摘要、逐条问题和明确复现步骤；单条问题可以独立交接。 |
| JSON | 程序与编程助手 | 保存有版本的结构、稳定 ID、用例结果、证据索引、历史关联和来源，便于检索与比较。 |

导出包含上述文件及必要证据的报告包。具体文件组织示意如下，尚未生成实际报告包。

```text
report-<run-id>/
  report.html
  report.md
  results.json
  issues/
    BUG-001.md
  questions/
    Q-001.md
  evidence/
    ...截图、可用轨迹、相关日志片段与测试数据...
```

报告使用相对证据引用，复制报告包后仍能打开。编程助手材料使用项目内相对文件路径、源码快照标识和定位信息，不仅依赖测试机绝对路径。单条 Markdown 的“复制问题”应包含修复所需的上下文和证据引用；需要图片或轨迹时，可以导出该问题的材料包。当前应用只生成材料，不自行启动其他编程助手、发消息或修改代码。

**报告总体内容**

| 部分 | 必须回答的问题 |
|---|---|
| 本轮结论 | 哪些验证已完成？发现了哪些问题？是否还有覆盖缺口？不能只有“测试完成”或单一通过率。 |
| 批次与环境 | 项目、入口、源码快照、运行版本、时间、Windows／浏览器／视口及角色；保存各入口的环境声明、数据操作范围和授权引用，声明与技术核实分开。原生操作另记屏幕条件。 |
| 规则与配置 | 本批次采用的用例、需求确认、skill、底座及模型配置版本是什么？实际模型版本无法获知时明确记为未知。 |
| 范围与功能清单 | 从哪些代码、路由、页面及用户补充识别了哪些功能？每个功能对应哪些场景和用例？用户明确不选的专项是什么？ |
| 全部用例结果 | 每条用例采用哪个版本、有哪些计划内执行实例、每个实例执行到了哪一步、各项断言如何、证据在哪里？通过项也必须可追溯。 |
| 完整业务流程结果 | 哪些跨入口流程已经贯通？每一步使用哪个角色、入口和业务记录？失败或阻塞发生在哪里，后续哪些步骤未验证？ |
| 缺陷清单 | 缺陷等级、影响、所在模块、复现与证据、代码定位及历史状态。 |
| 未验证清单 | 哪些功能或断言没有验证，为什么，影响哪些相关用例，如何解除阻塞并补测？ |
| 待确认业务问题 | 具体问题、已观察到的事实、可选业务预期、影响用例和用户确认后的处理方式。 |
| 执行异常 | 模型、工具调度、浏览器、环境、空间不足或任务停滞的原因及恢复情况；补齐会话工具结果仅修复协议可继续性，未开始与结果未知必须分别记录；与产品缺陷分开统计，不能用工具停滞判定被测业务失败。 |
| 运行统计 | 当前／累计活动耗时、墙钟跨度、各类等待、调用与重试、已知 token 及未知用量请求数；与会话指标同源，不重复计数，不估造账单。 |
| 异常恢复验证 | 主动模拟了什么条件，是否实际生效及解除？页面和业务恢复结果是什么，哪些真实服务故障尚未验证？ |
| 数据与文件验证 | 所需数据是否准备成功，导入或导出内容有哪些实际核验结果，证据文件在哪里？ |
| 跨时间流程 | 哪些用例仍在等待，哪些已到时核验？触发和观察时间是什么，是否错过窗口，结论能证明到什么范围？ |
| 旧数据兼容 | 使用了哪些历史材料及来源版本，哪些行为经过验证，哪些条件无法重建？ |
| 执行中范围变化 | 原始计划之后发现了哪些功能，何时增补了哪些用例，哪些仍待确认？覆盖分母如何变化？ |
| 测试数据处理 | 本轮新建的数据、保留及理由、已清理和清理失败；已有数据的修改与删除另行记录，说明对后续复现和回归的影响。 |
| 历史与补测 | 与此前批次相比新增、再次出现、经本次验证未复现、仍未验证的问题。业务预期改变导致用例替换应单独说明，不能称为 Bug 已修复。 |
| 基线与版本变化 | 本次与哪个基线比较，各代码模块和运行入口是什么版本？测试期间是否变化，哪些结果受到影响或需要重新核验？ |
| 用户处置与纠正 | 用户标记误报、确认行为符合预期或暂缓修复的理由、时间、适用版本及关联用例调整；原始观察和证据保留。 |
| skill 草案 | 建议补充的知识、具体差异、依据与确认状态；保持与当前生效规则的区别。 |

用户没有选择的性能压测或安全专项列为“本轮范围外”，不混入本轮跳过数。范围内但缺少外部服务的流程列为“跳过／未验证”，不得记为通过。未发现问题不等于产品不存在问题；结论始终对应本轮明确列出的范围和证据。

用户执行中明确移出项目时，保存新的计划版本，单列原范围、当前范围和移出项；已产生的观察与结果保留。不能通过把失败、阻塞或待确认的实例自动移出范围，使覆盖率变为 100%。范围外和范围内跳过采用不同统计类别；报告结论指向对应的计划版本。

源码与运行版本对应关系记录为已核实、用户声明或无法核实，并附依据。源码哈希不能单独证明网址的运行版本；无法核实时，实际页面证据仍可保留，代码定位与版本归属需注明不确定性，不能宣称已可靠监测所有部署变化。

适用的异常恢复检查属于完整测试默认范围。计划内制造的断网、延迟或失败本身是测试条件，产品是否正确处理该条件才是断言；模拟未生效或未解除属于执行问题。保留异常发生前、期间及恢复后的证据，说明实际影响范围。浏览器模拟的服务错误不能作为真实后端发生故障及恢复的证据。

数据准备和文件核验分别记录结果：准备记录或附件成功不代表其业务用例已通过，上传或下载成功也不能代替内容检查。历史材料记录来源与适用版本，无法获得旧数据时不能用新建记录代替兼容验证。

跨时间用例在到达观察窗口并实际核验前保持等待；阶段报告注明剩余项与预计核验时间，不把任务正常等待记成产品失败，也不提前出具整轮完成结论。重新打开应用后若已错过必要观察时刻，记录可补查的日志或最终状态及仍然缺失的时间证据，不能假定定时触发已经按时发生。

清理在测试结果、报告和证据保存后进行，其结果以补充记录关联原批次。保留数据需能够关联到缺陷或待补测用例，并包含必要的依赖记录；不能为了清理其他新增数据而级联破坏复现条件。清理失败记录目标、执行方式、错误、当前状态和对下一轮测试的影响，不覆盖原来的用例结果。报告中的新增、修改、删除记录不意味着具备完整备份或可以自动撤销所有业务变更。

清理前的 ReportRevision 明示“清理待处理”；清理成功、失败或按既定规则停止后，产生包含处理结果的新版本，原报告继续可读。对外说明区分测试断言是否完成、清理是否完成和整轮是否结束。导出固定一个 ReportRevision 及其证据清单，不混用导出期间更新的记录；文件和引用核对完成后才说明导出成功。

跨盘或网络目录导出也遵守完整性规则：临时材料或未完成的复制不能显示为完整报告，不覆盖已有完整版本；导出状态与材料缺失分别说明。具体临时目录、完成清单和发布协议见[详细设计 DD09](../architecture/2026-09-28-web-testing-design-recovery.zh.md)。

R54 授权不足、空间等待或停滞导致未验证的部分保留在本轮范围和缺口中，不能自动缩小分母或改变历史预期。业务数据清理执行前同样复核环境与授权；生产环境不能沿用测试环境的自动清理许可。

R55 的本地资产删除与上述业务清理分别呈现。用户确认删除历史证据后，保留最小处置记录与原结果归属；应用查看旧报告时显示材料已由用户删除、影响的复现／补测条件，不假称原证据仍可读取。已经离线导出的包不会被远程改写；之后再次导出须列出当时实际缺失。活动任务、当前基线或其他保留报告引用的材料不能随批次清理被误删。

**执行结束与结果分类**

任务是否仍在运行、执行实例到了哪里、验证结论是什么，应分别存储。以下结果首先用于具体执行实例；用例模板和功能按全部计划内实例汇总，不能用一次通过代表所有条件都已验证。

| 结果 | 判断条件 | 对覆盖的含义 |
|---|---|---|
| 通过 | 必须执行的步骤已执行，全部适用且必须验证的断言有证据满足。 | 已完成该用例验证。 |
| 失败 | 有证据证明至少一项已明确的预期不满足。 | 保留已验证部分及失败证据；剩余未执行断言仍单独记缺口，不能默认全部检查完毕。 |
| 待确认 | 缺少可以据以判断的业务预期，已按规则跳过受影响项。 | 对应断言未验证；报告需提出明确问题。 |
| 阻塞 | 缺前置条件、依赖故障、登录不可用或执行器不能可靠完成，无法得出产品结论。 | 未验证；保存已尝试步骤和原因。 |
| 跳过 | 仍在本轮范围内，有明确未执行理由，例如已确认无真实外部服务。用户移出范围的项目另行统计。 | 未验证；必须保留理由及来源，不删除原计划中的缺口。 |
| 未执行 | 尚未尝试，或任务取消等导致没有执行。 | 未验证，不能隐藏或计入通过。 |

重试是同一执行实例的多个 Attempt，不增加用例或实例覆盖分母。实例失败也可能同时包含未验证的后续断言，因此统计不能只把“通过数＋失败数”当作完整覆盖数。同一用例的两个视口若只执行了一个，另一个仍是缺口；不能把已完成实例的断言用于另一实例。

有限复试保留第一次失败及所有后续尝试；后一次成功不能将先前失败删除或改为未发生。对相同或不同条件下的结果分别说明，不能仅因“失败后成功”就证实具体原因。用户选择暂缓修复不改变失败记录；标记误报或确认新业务预期则新增处置及规则版本关联，不能覆盖历史证据。

实例汇总给出代表结论所依据的 Attempt，同时保留“曾失败”及各次差异。判定一条完整流程通过，需要一次满足前置条件和版本一致性的完整执行；不能从几次分别中断的尝试中拼接成功步骤冒充一次贯通。局部断言补测可以增加对应证据，但不能据此自动改成整条流程已经通过。

故障恢复更新后的新批次通过 RecoveryLink 关联封存旧批次，报告保留各自的应用组合、用例版本、观察和 UNKNOWN 动作核实记录；不能把旧批次改为正常完成，也不能拼接跨版本步骤声称一次流程贯通。

跨入口流程必须以同一笔业务的关联数据证明各步骤衔接。各端的单项用例通过不能替代整条流程实际执行。流程中断时保留已通过步骤、失败或阻塞步骤和未验证后续步骤，不能据此把所有参与模块都认定为产品缺陷。流程数据的保留及清理同时考虑各端关联依赖。

摘要分别显示功能、用例模板、执行实例和必须验证断言的数量与完成情况。断言分母是当前计划内适用实例的必测断言总数；有实际证据完成判断的断言进入验证分子，未执行、待确认或缺少证据的不进入。验证完成可以包含失败，必须与通过率分开。一个用例模板只有在其全部计划内实例的必测断言都完成时才算完整验证，功能还需有完整性核对结果。所有比例展示分子、分母及计划版本，不用代码阅读量、点击次数、模型 DONE 或置信度替代覆盖。

摘要同时列出各依据类别的数量、必测业务预期待确认数及实现诊断匹配数。错误实现与其自身推断一致时，业务正确性仍待确认；执行模型、报告总结模型和用户界面均不得将它改写为业务通过。

执行中增补功能与用例时，摘要保留初始范围及变更记录，展示当前实际分母；新增后尚未执行或待确认的项不能漏出统计。等待业务时间是任务或步骤的执行状态，对应尚未完成的断言仍计为未验证，不因此产生一条新的独立用例。

所有功能对应的必测用例和断言完成实际操作与判断后，才可以称为本轮全面验证完成；验证完成仍可包含发现缺陷。自动恢复、等待必要用户操作和等待业务时间的任务继续保存待推进状态，可生成阶段报告。普通业务疑问已按规则跳过、必要条件明确缺失或执行能力不支持等形成覆盖缺口，且本轮已无仍需等待推进的项目时，出具“本轮执行结束，覆盖不完整”的报告并列补测清单。持续性的暂时 API 故障按恢复策略处理，不作为快速跳过全部余项的理由。

“本轮执行结束”还需清理已有明确结果或无法继续的原因；正常等待、可自动恢复的清理故障或未处理的必要确认仍属于待推进事项。报告生成不自动触发批次结束，已取消任务保留取消状态和未清理记录。

这套结果分类用于如实表达被测项目的验证情况，不能替代本工具的交付标准。若首版承诺的操作或验证能力因本工具未实现而阻塞，应同时记录为工具能力缺口；生成了完整报告不等于该能力通过交付验收。

**单条缺陷的交接内容**

| 字段 | 具体要求 |
|---|---|
| ID 与标题 | 稳定问题编号；标题包含页面或功能、触发条件和异常结果。 |
| 类型与影响 | 功能、数据、视觉等产品问题；严重程度、受影响角色与流程。不能把自动化失败直接归为产品 Bug。 |
| 版本与环境 | 本次批次、代码版本、运行版本及对应关系、Windows 版本与架构、浏览器、被测页面视口、缩放、角色和必要环境条件。 |
| 对应用例 | 用例 ID 与版本、需求依据、失败断言和失败步骤。 |
| 跨端定位 | 适用时记录流程 ID、入口、角色、关联业务记录、异常出现前后的状态和被影响的后续步骤。 |
| 前置条件 | 账号角色、业务状态、数据关系；匿名材料需保留能够复现的数据结构。 |
| 精确测试数据 | 原始文本或附件引用，空格、换行、长度等明确展示；不要把边界数据改写为描述性概括。 |
| 复现步骤 | 从明确入口开始编号，写清点击位置、输入内容、按键和观察点；不能只写“执行失败”。 |
| 预期结果 | 具体应出现的行为，并注明依据是用户确认、skill、通用规则还是代码推断。预期未定的问题转待确认。 |
| 实际结果 | 可观察的结果、发生时间、实际值、错误信息及失败位置。 |
| 证据 | 截图、步骤记录、DOM 或布局观测，以及可用的请求响应、控制台、后端日志与只读数据结果；逐项关联到步骤和断言。 |
| 出现频率 | 实际尝试次数、出现次数和各次条件。没有复试则写“一次观察，未复试”，不宣称稳定复现。 |
| 相关代码 | 项目内相对路径、快照中的行号、符号或函数、关联请求与调用关系，足够解释代码为何相关。 |
| 原因分析 | 分开列已证实的事实、疑似原因和未排除因素。无法定位原因时明确说明，不捏造文件、行号或结论。 |
| 修复后的验收 | 重新执行哪些步骤和断言，需覆盖哪些相关回归场景。可以提出修复方向，但不能将未经验证的建议写成确定解法。 |
| 历史关联 | 首次发现、历史同类问题、关联批次及补测结果；同一问题关联多个用例，避免重复计数。 |

视觉缺陷额外保留：原始截图与标注图、视口和缩放、页面滚动位置、触发数据、遮挡或溢出的元素及可观测尺寸。没有设计稿时，以能够明确说明的异常作为判断依据；单纯审美偏好或预期不明的视觉差异列为待确认。原始截图保留，标注图不能替代原始证据。

导出的编程助手材料应自包含：不要求修复 AI（人工智能） 先读取整个聊天历史，才能知道业务预期。项目访问令牌、密码、验证码和完整会话 Cookie 不作为复现材料导出；使用角色及凭证引用说明需要哪类访问，保留非敏感的复现条件。

报告中的页面文本、日志及源码片段按数据转义显示，不能作为活动 HTML 或脚本执行。原始证据与脱敏导出件分开标识，说明因脱敏或材料缺失造成的复现限制；不能为了自包含而导出凭证，也不能把修改后的证据当成未处理原件。历史代码位置引用当时保存的材料，原文件后来改变不应将旧问题自动定位到新内容。

后端用例及对应问题还应记录已有入口、接口方法与参数，或命令、参数及必要工作目录；敏感内容使用引用或脱敏值。证据包括触发时间、响应或输出、任务标识、相关日志、可用的只读数据结果及最终业务状态。接口返回“已接受”或命令退出成功不能代替异步结果验证。手动触发处理逻辑与自动定时调度的验证结果分别记录；无法触发或无法观察最终结果时，如实列出覆盖缺口。

**缺陷示例，仅示意结构，并非实际发现**

```text
问题：BUG-001｜客户详情：多行备注保存后显示为一行
关联用例：TC-CUSTOMER-017，版本 3
定位：客户管理 → 编辑客户 → 备注；客户详情 → 备注展示
前置条件：有编辑权限的测试账号；一条允许编辑的测试客户
测试数据：第一行\n第二行（包含一个真实换行）

复现步骤：
1. 打开测试客户，进入编辑页面。
2. 在备注输入“第一行”，按 Enter，再输入“第二行”。
3. 保存并打开该客户的详情页。
4. 刷新详情页，观察备注分行情况。

预期：保存、查看和刷新后，备注均保持两行。
依据：用户已确认的“备注保留换行”业务规则。
实际：详情页将两行显示在同一行；编辑页面重新打开仍有换行。
证据：输入后、保存后和刷新后的截图；相关操作记录。
相关代码：真实报告填写已核对的项目文件、符号及源码快照位置。
原因状态：尚未证实；需核对接口返回值与详情页文本呈现方式。
出现频率：实际报告填写观察与复试次数。
修复验收：本例通过；补测连续换行、首尾换行、长文本及编辑回显。
```

这个示例能够说明用户看到的错误和修复后的标准，同时明确原因尚未证实。实际报告不能在未查看接口、数据库或代码时，直接断言“后端丢失换行”或“某个 CSS 属性错误”。

**待确认问题的结构与处理**

每个问题有独立 ID、具体业务问题、代码及页面事实、影响的功能与用例、已跳过步骤、候选预期以及用户回答。候选选项仅帮助表达，支持自然语言补充，不通过默认勾选代替用户回答。

例如：“删除客户时，其历史订单应保留并显示客户已删除，还是禁止删除存在订单的客户？”应附当前观察和受影响用例。收到回答后显示将如何调整断言及适用范围，写入新用例版本，并安排真实补测。不同规则分支影响的数据准备和验证步骤也应同步更新。

普通用例更新已由用户要求执行；若还建议将回答沉淀为 skill，应额外展示 skill 草案并获得确认。历史批次保留当时的规则版本，不能用今天的业务规则重新包装此前的结果。

**证据采集与持久化归属**

已确认默认记录操作步骤、关键截图、失败证据及相关日志；全程录像按需开启。报告与必要证据默认保留，由用户管理清理。每条用例保存时间、输入及断言结果，网络、控制台、后端日志及只读数据库证据按相关性关联到步骤。完整浏览器轨迹的采集机制按 DD02、DD06 和 DD09 实现，不能据此自动开启全程录像或自动删除历史证据。

用例、用例版本、执行批次、执行尝试、逐步观察、断言结果、问题、待确认事项和证据应独立持久化，并与 DSH 会话及日志关联。会话用于沟通与控制，不能充当唯一结果数据库。展示报告或切换对话不应改变正在运行的测试。

运行批次固定采用已确定的规则，每次执行绑定明确的用例版本。按已确认规则增补新发现的场景时，创建新的计划版本并保留原始计划，不改写已执行用例。新增业务确认形成新的用例版本，并由后续关联补测采用。模型路由可以改变分析或动作选择方式，但不能直接改写既定断言或覆盖缺口。底座升级不能导致旧报告和证据关联失效，存储格式与迁移机制见 DD06、DD09 及 DD12。

本规格的正式验证统一归入[验收标准与追踪](../testing/2026-09-28-web-testing-acceptance.zh.md)的 AC07、AC15、AC27–AC31、AC33、AC38–AC53 及 DD13 相关场景，不维护第二份验收清单。历史探针示例不代表最终候选验收通过。
