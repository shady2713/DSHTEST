# Agent Note: 产品需求

Status: proposed

[English](2026-09-28-web-testing-requirements.md) | 中文

## 问题

开发者需要在版本完成后检查完整业务行为和可见交互，同时保持被测源码只读。

## 提案

状态：现行产品范围，共 R01–R58；已有本地探针和受限原型，最终产品仍未验收；当前交付状态由[协作指南](../process/2026-09-28-web-testing-agent-guide.zh.md)维护。技术实现以[技术架构](../architecture/2026-09-28-web-testing-architecture.zh.md)及三份详细设计为准，产品通过条件以[验收标准与追踪](../testing/2026-09-28-web-testing-acceptance.zh.md)为准。唯一基座版本与上游规则来源为[基座与上游升级](../process/2026-09-28-web-testing-upstream-baseline.zh.md)。

产品面向个人开发者：用户完成一个版本的开发并启动项目后，提供完整代码和被测网址，应用自动理解项目、组织测试，通过浏览器和必要的电脑控制模拟人工操作，积累测试资产并生成报告。同时保留 DSH 对话能力，用于分析、讨论和维护 skill（技能）。

核心目标是全面、可追溯地测试项目。速度和成本通过模型路由、确定性执行和历史资产复用优化，不能通过减少已选择的测试范围或放宽判断标准实现。

以下产品边界已经确认。

| 编号 | 已确认要求 | 具体含义 |
|---|---|---|
| R01 | 单人使用的桌面应用 | 面向个人，不建设团队、组织、协作权限等管理体系。 |
| R02 | Windows 10 22H2（build 19045）及以上，x64 | C02 已确认最低 Windows 10 为 22H2／19045，并支持 Windows 11 x64；更早 Win10 与 ARM64 不纳入首版。测试 PC 网页，移动端后续扩展。按首版目标验证实际系统、原生依赖及运行行为。 |
| R03 | 采用 DSH 底座及官方桌面路线 | 直接沿用官方桌面源码、界面及工程体系，通过插件和必要适配增加测试能力；遵循官方扩展机制，按固定版本验证后升级。C03 已确认个人使用首版采用官方支持的未签名本地安装路线、手动更新；正式签名及自动更新后续再做，不降低工程检查；普通更新保持任务保护，另提供用户明确选择且兼容性已验证的故障恢复更新；封存旧批次不冒充完成或取消，未知动作保留待核实 |
| R04 | 全部自有代码遵循 DSH 工程规范 | 桌面、插件、前端、脚本、测试和文档均在所选版本的官方规则下开发；底座版本与适用规范一起管理。 |
| R05 | 用户提供全部项目代码 | 包括前端、后端及项目内其他相关代码；不局限于前端仓库，不按编程语言或框架限制项目接入，也不要求用户预先选择技术栈。 |
| R06 | 用户负责启动被测项目 | 应用接收已经可访问的网址；自动部署、启动项目及安装其依赖不属于当前确定的主流程。 |
| R07 | 从代码自动生成需求认知 | 用户不必先编写需求文档；代码产出候选预期。区分已确认业务规则、适用通用规则和仅实现推断；关键金额、权限、状态流转等即使实现明确也集中确认，不能用实现一致性替代业务正确性。支持对话、测试要求和 skill 补充。 |
| R08 | 没有设计稿 | 页面视觉检查主要从实际页面发现异常；历史截图可成为后续比较材料。 |
| R09 | 覆盖全部功能的集中测试 | 一个版本开发完成后集中测试，包含所有输入控件、换行、增删改查、页面交互及样式问题。不能把能力局限于简单表单。 |
| R10 | 支持选择和输入测试要求 | 用户主要通过自然语言表达范围和要求；对话内选项、卡片和快捷操作作为辅助，不要求先填写完整配置表单。 |
| R11 | 性能压测和安全专项按需勾选 | 不默认加入每次全面测试；勾选后需要相应测试目标和执行参数。 |
| R12 | 只测试，不修改被测项目代码 | 普通对话、测试、模型路由、skill、动态启用的工具和重试均不得执行修改被测源码、配置或依赖的操作；官方引导的工具开关及人工审批不能解除这一边界。用户已确认使用当前 Windows 账户下的应用层受控操作：禁止任意终端、代码编辑器和无限制桌面控制，作用不明的操作阻塞并说明；接受其不是操作系统级隔离保证。可以分析问题并提出建议。 |
| R13 | 测试环境业务数据允许增删改 | 在 R54 确认的测试环境和数据范围内，允许通过业务入口操作新旧数据；用户确认全量测试数据时可覆盖全部业务记录。不扩展到生产或未知环境，不构成修改源代码的授权。 |
| R14 | 生成报告，不自动修复 | 保存问题和证据供用户处理；不自动修复代码、提交修改或创建修复 PR（Pull Request）。 |
| R15 | 保存测试历史 | 支持新版本测试、回归测试和针对历史问题的复测。 |
| R16 | 长程任务持续执行 | 可恢复的模型 API 故障必须有自动重试机制，不能一次失败就让整个任务结束或依赖用户反复发送“继续”。 |
| R17 | 模型调用没有费用额度 | 不设置应用层模型费用上限，不因累计费用达到阈值而暂停任务。仍需避免无效循环与无意义调用。此项不自动授权支付等真实业务操作。 |
| R18 | 按任务路由模型 | 按需求推理、视觉、确定性步骤和局部结构化决策匹配能力；支持可替换的轻量决策模型，Jev 仅为候选例子，不绑定品牌、提供商或专有原语。至少接通并验收一种真实轻量路线，避免所有操作依赖大型多模态模型；稳定回归步骤优先采用有前置核验的确定性执行；轻量路线通过质量与总收益门槛后才成为对应任务的默认路线，未获收益不影响已合格路线继续工作 |
| R19 | 支持用户配置 skill | 补充知识、测试方法、业务流程等，并可通过对话逐步完善。 |
| R20 | 保留原生 DSH 对话体验 | 原生 DSH 对话是主界面，交互参考 Codex、ZCode，可关联项目，也可不关联项目。对话中的文件处理能力受 R12 限制。 |
| R21 | 主动提出 skill 改进草案 | 测试后可以主动整理建议；用户确认后才保存并生效，不能自行修改已生效规则。 |
| R22 | 支持多种登录方式 | 包括账号密码、验证码、短信和扫码。具体自动化与人工接管流程按后续规则设计。 |
| R23 | 可以使用专用电脑测试 | 完整、可靠执行优先；能够不占用桌面的操作尽量支持与日常使用并行，不要求所有电脑控制步骤都能后台运行。 |
| R24 | 支持补充运行证据 | 按用户可提供后端日志及只读数据库核验能力设计；实际路径、连接及可访问范围仍需按项目配置，不能仅从“有源码”推断运行环境已可访问。 |
| R25 | 外部业务执行前确认 | 支付、短信、邮件等真实操作需向用户确认；没有真实服务则跳过对应外部流程。跳过原因必须进入报告，不能计入通过。 |
| R26 | 自然语言驱动测试全过程 | 用户通过对话发起测试、表达范围、追加要求和控制任务。计划、进度、浏览器、报告及 skill 改动通过卡片或侧栏呈现，不把“测试工作台”设计成脱离对话的传统任务表单流程。 |
| R27 | 先生成用例，再执行测试 | 开始实际用例执行前，分析完整项目代码、测试要求、已有 skill 和历史记录，生成测试用例；不清楚的业务预期在此阶段向用户询问，回答落实到用例。 |
| R28 | 执行中新增业务疑问先跳过 | 不自行猜测正确预期；跳过相关用例或受影响的检查项，继续独立用例，最终在报告中列出。用户确认后更新用例版本，再执行对应测试。支付等外部操作确认和登录接管仍遵守原有规则。 |
| R29 | 按用例逐项执行全部功能 | 全面测试需要像人一样执行全部功能对应的用例；未验证部分最终进入报告。生成用例、读代码、接口成功均不能替代真实页面执行。存在缺口时不能宣称全部功能已验证。 |
| R30 | 新版本开测前确认用例更新 | 读取当前代码并与用户指定或项目当前采用的回归基线比较，提出新增、修改、删除及受影响用例；涉及业务行为和预期变化的内容，在执行前询问用户并更新用例。实现变化本身不是业务正确性的证明。 |
| R31 | 报告面向用户和编程助手 | 清楚说明问题在哪里、如何复现、预期与实际差异、证据和相关代码，使用户能够理解，也使编程助手能够据此修复。当前应用继续只测试与生成报告，不修改被测代码。 |
| R32 | 覆盖没有页面入口的后端功能 | 定时任务、消息处理、回调等功能也纳入清单。允许通过现有接口或项目已有管理命令触发，再结合页面、日志和只读数据库验证。有页面入口的功能仍需实际操作页面；源码只读及真实第三方操作确认规则不变。 |
| R33 | 保留问题数据，清理其他新增测试数据 | 保留缺陷复现所需数据及其关联数据；其他本轮新建数据在测试结束、报告保存后自动清理。已有数据的修改、删除分别记账，不承诺自动还原。清理结果及失败原因进入报告。 |
| R34 | 仅在桌面应用对应会话内提醒 | 需要用户接管或确认的事项，通过所属会话呈现；交互参考 Codex、ZCode。当前不建设 Windows 系统通知、手机推送、短信、邮件等提醒渠道。 |
| R35 | 内置浏览器为主，独立浏览器补充 | 内置环境受限时，由应用控制独立 Chrome／Edge 执行相关流程，结果统一入报告并注明实际环境。 |
| R36 | 关闭窗口后继续后台测试 | 关闭窗口不等于退出或取消测试；应用继续运行。明确选择退出应用时保存进度并退出；退出及更新判断纳入全部持久批次，包括未加载会话的等待、暂停和待恢复任务。所需桌面操作仍遵守前台条件。 |
| R37 | 重开应用后核验并自动续跑 | 崩溃或重启后重新打开应用，先核对环境、登录和已提交操作，再续跑未完成任务；用户主动暂停的任务保持暂停，已取消任务不自动恢复；故障更新封存的旧批次只经恢复流程核实并关联续测，不直接自动派发。 |
| R38 | 默认记录并保留必要证据 | 默认记录操作步骤、关键截图、失败证据及相关日志；全程录像按需开启。报告与必要证据默认保留，由用户管理清理。 |
| R39 | 应用内报告及多格式导出 | 应用内查看，导出 HTML 供人阅读，Markdown／JSON 和证据包供编程助手使用，内容来自同一批次记录。 |
| R40 | 区分应用窗口与被测页面尺寸 | 应用自身窗口与缩放参考 Codex／ZCode；被测项目的前端视口尺寸由应用在开测前向用户询问并保存到项目测试配置，后续按确认的配置执行。 |
| R41 | 开测前检查用例完整性 | 将代码与页面识别出的功能入口、角色和业务状态与用例逐项对应；发现缺少用例时补齐或说明原因，不能仅凭已生成用例全部执行就宣称测全。 |
| R42 | 多入口项目的完整业务流程测试 | 一个项目可关联多个代码目录、网址及角色。需要跨管理后台、用户前台等入口追踪同一笔业务，验证状态、数据及角色可见结果，形成流程级结论。 |
| R43 | 按业务需要验证并发及多角色交互 | 覆盖共同编辑、审批后的状态同步等适用场景；属于业务正确性检查，不替代按需选择的性能压测。 |
| R44 | 识别测试期间的版本变化 | 测试中检测到代码或部署版本变化时记录并核对，隔离受影响结果，不能把不同版本的数据混为同一版本的验证结论。 |
| R45 | 回归比较基线可指定且可追溯 | 用户可以自然语言指定比较版本；代码、用例预期及视觉参考各自关联版本，不自动以未完成测试或有问题的截图替换原基线。 |
| R46 | 保留初次失败，支持有限复试 | 先保存失败证据，满足前置条件后有限复试，记录各次条件与结果。之后成功不能抹去此前失败；与模型 API 故障重试分别处理。 |
| R47 | 用户可以纠正或处置测试结论 | 支持自然语言标记误报、确认行为符合预期或暂缓修复，记录理由及适用版本。预期变化落实到用例版本，skill 修改仍经草案确认，历史记录保留。 |
| R48 | 测试任务避免相互干扰 | 同一环境且共享业务数据的独立测试批次默认排队；系统鼠标键盘同一时刻由一个任务控制。普通对话和代码分析可以继续。 |
| R49 | 异常恢复测试默认纳入完整测试 | 根据项目功能生成适用用例，在受控测试浏览器内模拟断网、请求延迟或失败，验证提示、输入与业务数据保留及恢复后的行为。记录模拟条件和实际验证范围。 |
| R50 | 自动准备测试数据和文件并核验内容 | 开测前列出所需数据状态，通过已允许的业务入口准备；生成适用的正常、边界及错误文件，核验导入、导出的实际内容。无法准备的条件列为覆盖缺口。 |
| R51 | 支持跨时间业务流程 | 用例明确触发条件、等待时间和最终观察点，持久化等待进度并到时核验，期间继续独立测试。已有入口提前触发处理逻辑的结果与真实定时触发分开记录。 |
| R52 | 回归包含适用的旧数据兼容检查 | 验证历史业务记录、旧附件及适用的已有登录或缓存，追溯其来源版本。只有新版本及新数据时，明确旧数据兼容缺少验证条件。 |
| R53 | 执行中持续补齐功能与用例清单 | 发现新入口或状态时记录发现依据；预期明确的场景先补充用例并记录计划变更，再执行。存在新业务疑问的部分按 R28 跳过并汇总确认。 |
| R54 | 开测前确认环境性质与数据操作范围 | 持久记录用户对各入口环境性质、账号／租户及数据范围的声明。生产或未知环境默认不执行业务变更及有影响的异常模拟；需要执行时先确认具体流程、记录范围和副作用，超范围或相关环境变化后重新核对。 |
| R55 | 本地资产空间监测与用户清理 | 显示占用与剩余空间，提前预警；通过对话发起按批次清理并确认影响。空间不足时保留任务并停止无法保存必要证据的步骤，不自动删除历史。存储上限可选，默认不设硬配额。 |
| R56 | 对话式首次模型配置与凭证管理 | 复用官方模型编辑及凭证服务，通过会话引导和配置卡片设置提供商、模型及路由，验证连接和所需能力；凭证经专用输入管理，可更换或删除。未配置轻量决策路线不阻断其他已具备能力的路线，缺少必要能力则明确提示。 |
| R57 | 检测任务整体无实质进展 | 识别反复观察、重新规划或重复恢复却未推进的情况，排除正常等待；先有限恢复并推进独立项，无法推进时持久等待并在所属会话提示，不空转、不伪报完成。 |
| R58 | 运行中可查看进度、耗时和模型用量 | 在所属会话查看当前阶段、有效进展、等待原因、耗时、调用与已知 token 用量；缺失用量如实标注，动态范围与已结算结果分开显示，不引入费用停止条件。 |

这些要求通过统一的对话入口承载测试和知识维护；下列行为是需求细化，具体控件实现见详细设计。

已确认的测试路径：完成所需模型配置 → 用户指定项目、入口网址和测试目标并确认环境性质 → 分析代码、页面、角色、skill 与历史基线 → 生成单项及跨入口流程用例并检查完整性 → 确认业务疑问、预期变化及所需操作授权 → 将答案写入用例 → 执行并记录进展、空间与用量 → 新业务歧义跳过相关项、继续独立测试 → 生成报告 → 用户确认待确认事项 → 更新用例并补测。

完整测试的用例准备同时覆盖适用的异常恢复、数据与文件、跨时间流程和历史数据场景。执行前完成并核验相应前置条件，执行中按 R53 记录功能发现和用例增补；各阶段的范围、计划版本与证据保持可追溯。

准备工作区分“列出准备步骤”和“执行会变更业务数据的准备操作”。后者遵守 R27，在相应用例及业务疑问处理后执行；“只生成用例”的请求不授权提前创建或清理业务数据。

**环境、首次配置与持续运行：R54–R58**

R54 按入口记录测试／生产／未知环境及用户声明来源，不能根据 localhost、域名或登录成功自行证明环境性质。相关入口、账号租户、后端指向或部署环境发生变化时重新核对；仅版本号变化且已核实环境归属不变时可复用声明。开测前保存允许的数据操作范围；同一声明范围不因重开应用而反复询问。生产／未知环境需将数据准备、修改删除、清理及有业务影响的故障模拟列入具体授权流程；不能以“全面测试”默认开放。授权可以覆盖明确的用例组和记录范围，不按每次点击机械询问；真实外部服务仍须满足 R25，权限不能相互替代。未知或授权不足的部分留在范围内并记录缺口，不自动从“完整测试”中移除。

R55 的占用统计覆盖应用状态、源码／skill 快照、证据、录像、受管浏览器档案及导出临时材料，区分应用资产与被测项目数据。会话可打开批次占用卡片、预览清理影响并确认执行；共享证据、活动任务及当前回归基线引用的资产不能直接删除。存储上限可由用户设置，默认不设硬配额；剩余空间预警和保存能力检查仍生效。空间不足进入可恢复等待，空间恢复后先核验再继续；不静默关闭用例要求的录像或删减证据。完整换机／重装迁移包暂不列为首版承诺，已有升级备份要求保留。

R56 不要求先购买或配置每一种提供商。首启可以先配置项目，或复用已有模型开展普通对话；在测试前确保所选任务所需模型能力可用；一个具备多项能力的模型可以承担多种任务。配置卡片说明连接验证会发生少量真实请求，区分凭证、网络、模型名和能力不支持。凭证通过专用控件保存为引用，不进入聊天、skill、模型提示或报告；删除正在使用的凭证先展示影响，受影响任务保留待配置状态。用户未配置轻量路线时使用合法替代路线；产品须验收至少一种真实轻量路线及替换机制，不要求 Jev 或 TypeSafe 专属验收。

R57 按阶段观察实质进展：分析形成有依据的新材料结果、执行推进有效步骤或结算断言、疑问得到解决等；只增加 token、刷新时间或反复改写同一计划不算进展。业务定时等待、API 退避、用户暂停、接管、环境或空间等待单列，不能套同一个墙钟超时。有限恢复无效时保留停滞原因和解除条件，只在所属会话提醒，独立可执行项继续；提醒去重。该机制不设置整个任务的调用总额上限，也不因停滞将测试自动判通过。

R58 的查询读取已记录事实，不为显示状态额外调用模型。耗时区分本次活动时长、累计活动时长和墙钟跨度，暂停及各种等待分别显示；用量包括已发生重试及备用路由请求，未知用量不能当零。覆盖分母变动有说明，发现新用例时不能维持虚假的固定完成百分比。不要求首版提供账单精确金额估算，也不产生费用阈值停止。

**多入口项目与跨端流程**

项目按完整业务系统组织，可以在同一测试环境中关联多个代码目录、多个前端入口及其后台服务。保存入口名称、网址、对应代码模块与版本、适用角色、账号引用和所需依赖；用户仍负责启动项目。网址、账号和运行证据等缺失信息在具体项目开测前补齐，不要求用户先整理成完整配置表单。

跨入口用例以同一笔业务及其关联数据贯穿各端。例子：“用户端提交申请 → 管理后台找到同一申请并审批 → 用户端查看最新状态 → 其他角色核验适用的数据可见范围”。每一步都记录使用的入口、角色、操作、业务标识、预期状态与实际证据，不能在每个页面各创建一条无关数据后宣称流程已经贯通。

角色会话按项目、身份和用例需要管理；在两个角色间切换不应意外覆盖彼此登录状态。涉及异步处理时，按照已明确的业务预期观察状态变化，记录等待过程和最终结果。正常、驳回、撤回、重复操作等分支，根据项目实际存在的流程和已确认规则生成用例，不臆造业务要求。

流程级结果与单步结果同时保留。流程中断时指出已经验证的步骤、发生异常或被阻塞的位置，以及后续未验证部分；一个流程失败不等于每个参与模块都已证实存在缺陷。清理策略要考虑跨端数据依赖，保留复现整个问题所需的关联记录。完整性检查也应覆盖跨端流程，不能只统计各入口页面的单项用例。

R48 的排队对象是可能互相干扰的独立测试批次；R43 的并发验证是同一测试用例内有计划地协调多个角色或会话的动作，二者应分别表达，不能因批次排队而取消业务并发场景。

知识维护路径：创建关联项目或独立对话 → 分析代码、讨论业务或查看测试证据 → 用户要求整理知识，或应用主动提出建议 → 生成或修改 skill 草案 → 展示具体改动 → 用户确认 → 保存为可用于后续测试的版本。

按已确认的澄清规则细化自然语言行为：“测试这个项目”先生成用例，必要业务疑问得到回答并落实到用例后执行；“先给我测试用例”只产出用例；“继续上次回归”关联已有批次并先核对当前版本与环境。无需为已经明确的每条用例增加重复确认。支付等外部动作和 skill 生效继续遵守已经确定的确认规则。

支持以下对话交互。它们需要作用于真实任务状态，不能只生成文字回复。

| 用户表达示例 | 产品行为 |
|---|---|
| “完整测试这个项目，网址是……” | 解析测试范围，复用项目资料，展示计划与执行进度。 |
| “只回归订单模块，重点检查换行和重复提交” | 形成明确范围和检查项，保留与历史用例的关联。 |
| “现在测到哪里了？” | 读取当前进度并回复，不中断正在运行的测试。 |
| “再加上删除后刷新页面的检查” | 更新计划，在适合的步骤边界生效并记录变更。 |
| “暂停这次测试”“继续上次任务” | 操作对应批次的生命周期；目标有歧义时只澄清任务归属。 |
| “打开这个问题的操作过程” | 展示对应证据、步骤和浏览器记录。 |
| “把这个经验补进表单测试 skill” | 生成具体修改草案，经用户确认后保存。 |

对话是控制入口，结构化计划、执行状态和证据是可核对的结果。项目导航、内嵌浏览器、文件选择、结果卡片和必要的设置界面可以存在，但不应成为每次测试必须依次填写的向导。测试任务与当前聊天页面的显示状态分离，避免查看报告、切换会话或询问进度改变测试执行状态。

提醒方式按 R34 执行。在所属会话标记“待你处理”，在对话中说明原因、受影响步骤及需要用户完成的操作，支持通过自然语言回应或接管对应页面。提醒需与实际待处理事项关联，用户切换会话后仍可找回。等待期间保存进度，继续可独立执行的用例；没有用户回答不能视为同意。执行中新发现的普通业务歧义仍按 R28 跳过并集中入报告，不因有会话提醒能力就改为逐条中途询问。具体卡片和会话标记样式属于后续交互设计，不表示当前已实现，也不声称复制了参考产品的具体机制。

读代码得到的是有依据的需求推断。源码可以描述现有实现，但不能单独证明原始业务意图，也不能可靠发现完全未实现、且没有任何其他线索的需求。产品需要保留这一事实，不把实现行为自动等同于正确预期。

开测前生成按业务归组的关键规则清单，至少覆盖适用的金额／计费、角色权限、状态流转、删除／级联及真实外部动作；每条展示当前实现、候选预期、来源和影响用例，不只询问模型自认模糊的规则。已有用户确认且版本适用的规则复用，不重复打扰。用户确认测试范围或允许操作不等于确认全部业务规则；规则确认必须绑定具体内容与版本。

报告并列展示已确认业务规则、适用通用规则与仅实现推断的核验范围。仅与代码一致可记录诊断性匹配，不能获得“业务预期通过”或占用其验证分子。必测业务预期缺依据时保留待确认与覆盖缺口；新答案进入新用例版本并实际补测。具体判定归[报告规格](2026-09-28-web-testing-test-case-report-spec.zh.md)。

浏览器操作、输入检查、视觉检查及业务流程核验以运行中的页面和业务结果为对象，产品使用不依赖用户预先声明项目语言。代码分析由应用识别目录、文件、接口与调用关系；语言专用解析器可以增强精确定位，但不能成为开始测试的必填配置。遇到无法可靠解析或理解的代码时，记录具体分析缺口，继续已有依据的页面和业务验证；必要的业务疑问按既定流程确认，不伪造代码定位，也不因缺少某个解析器而静默删除相关功能。

为每条需求记录功能入口、相关代码、页面证据、业务前置条件、预期行为、依据来源及待确认事项。用户明确补充的规则应与代码推断区分；两者发生冲突时记录冲突，不静默覆盖。输入材料中的角色、约束和数据关系，用于生成适用场景。

将覆盖情况关联为“功能 → 场景 → 用例 → 操作与断言 → 证据 → 结果”。“全部功能纳入测试”是产品目标；覆盖率必须注明分母和已知范围，不能用已识别清单的完成率宣称发现了所有功能或不存在任何缺陷。

同一用例在用户已选的不同角色、视口、数据或运行条件下，需要有对应的实际执行实例；测过其中一个条件不能替代其余条件。实例统计及范围变更的统一定义见[报告规格](2026-09-28-web-testing-test-case-report-spec.zh.md)。从代码理解业务有助于生成与定位用例，但不能据此宣称被测项目具有已测量的语句或分支覆盖率。

用例应先于执行形成可保存的测试资产。每条用例包含稳定编号、版本、所属功能与需求依据、账号角色、前置条件、精确测试数据、逐步人工操作、对应预期与判断依据、依赖用例和需要的证据。空格、换行及特殊字符同时保留原值与转义表示。用户的业务回答记录来源、适用范围及确认时间，不能只存在于聊天记录里。归入 skill 的修改仍另行生成草案并经用户确认。

新版本先比较本次代码与用户指定或项目当前回归基线的代码快照，再结合依赖关系提出用例变更。默认采用最近已确认且适用的基线，不能简单取最后一次未完成批次。将变化分为新增、业务预期变化、流程或定位变化、功能移除及间接受影响。向用户确认时展示具体的原预期、新预期建议、代码依据和影响范围，不能只问“是否更新所有用例”。不依赖 Git 仓库一定存在；没有可比较的历史快照时，应说明无法可靠得出历史差异，并按首次测试整理当前用例。

每个参与流程的代码模块与运行入口分别关联版本。检测到测试期间的源码或部署变化时，先记录变化时间和受影响模块；涉及版本归属不明的后续步骤需先核对，不将其继续算作原版本结果。通过关联的新批次或明确的版本分段继续测试，原记录保留，不能自动把此前已执行证据归到新版本。

源码快照只能证明本地材料的版本，不能单独证明当前网址正在运行同一份代码。版本对应关系应标明核实依据，并区分已核实、用户声明及无法核实；缺少运行版本信号时不承诺识别每次部署变化。此时可保留实际页面观察，代码定位及版本结论必须说明对应关系的不确定性。

产品失败的复试按 R46 执行。先保留现场，再在可重建前置条件且操作符合原有授权范围时有限复试；支付、短信、邮件等真实外部动作仍受原确认范围约束。报告保留各次失败和成功的记录，呈现观察次数及差异。用户标记误报、确认业务预期或选择暂缓修复时，按 R47 增加处置记录，不覆盖原始执行证据；“暂缓修复”不改变失败事实。

用户确认更新后保存新用例版本，旧版本及旧批次结果继续保留。执行中遇到新业务疑问，记录已执行步骤与观察，跳过依赖未知预期的剩余步骤；不能凭部分步骤成功将整条用例判为通过。用户回答后创建关联的补测记录，重新满足前置条件并执行受影响用例，不能仅修改报告状态。补测结果与原批次关联，原始记录不覆盖。

一轮全面测试的目标是所有功能对应的用例都完成实际执行和判断。仍处于自动恢复、等待必要用户操作或等待业务时间的任务保留待推进状态，可以出具阶段报告。普通业务疑问已按 R28 跳过、必要条件明确缺失或执行能力不支持等形成覆盖缺口，且本轮已无仍需等待推进的项目时，可以出具“本轮执行结束，覆盖不完整”的报告；不能称为全部功能已验证。临时模型 API 错误继续进入恢复流程，不得借此将剩余用例批量标记跳过并结束。详细结果分类与报告设计见下方关联规格。

以下是内置通用检查范围；按实际功能和已确认规则生成适用用例，不对无关控件机械套用。

| 检查类别 | 检查内容 |
|---|---|
| 输入控件 | 空值、纯空格、前后空格、长度边界、超长文本、中英文、特殊字符、清空和粘贴。 |
| 多行输入 | 单次及连续换行、首尾换行、多行粘贴、保存后重开、详情及列表中的展示。 |
| 键盘与焦点 | Tab、Enter、Shift+Enter、Esc、焦点顺序、焦点丢失及误提交；按控件语义确定预期。 |
| 新增和修改 | 校验提示、保存、取消、重复提交、刷新后结果、关联状态更新。 |
| 查询和列表 | 搜索、筛选、排序、分页、空结果、清空条件及组合操作。 |
| 删除 | 确认、取消、关联关系处理、删除后的查询与访问。 |
| 跨功能及跨入口流程 | 同一笔业务在不同入口、角色、页面、接口和后台步骤之间的数据、状态及展示一致性；提供流程级和步骤级结果。 |
| 角色与数据隔离 | 按角色验证可用功能和可见数据；账号及其准备方式在具体项目开测前补齐。 |
| 业务并发 | 依据业务规则检查共同编辑、重复操作或多个角色交互产生的状态冲突；不等同于性能压测。 |
| 页面视觉 | 重叠、遮挡、溢出、截断、错位、长内容撑破布局、弹窗与下拉层，以及不同 PC 窗口尺寸。 |
| 错误反馈与响应 | 页面异常、接口失败后的反馈、无响应和明显卡顿；不自动等同于性能压测。 |
| 主动异常与恢复 | 按 R49 默认验证适用的断网、请求超时及失败场景，观察异常期间和恢复后的提示、数据与操作结果。 |
| 文件与数据准备 | 按 R50 准备所需记录与附件，核验导入结果、导出内容和适用的边界及错误输入。 |
| 跨时间流程 | 按 R51 检查适用的过期、定时处理等流程，分别记录等待和最终业务结果。 |
| 历史数据兼容 | 按 R52 使用有来源的历史数据、附件及适用会话或缓存检查新版本。 |

通用检查应内置可用；用户 skill 用于补充或调整，而不要求用户从零编写每个输入框的测试方法。已选择的必测规则需要落实为测试项，不能仅把一段文字交给模型后就视为已经执行。

模拟人工操作需要匹配用例目的。测试键盘行为时，应执行相应按键和焦点操作；直接设置输入值不能替代该类测试。页面流程测试也不能因为直接接口调用成功，就标记浏览器交互已经覆盖。测试数据中预先指定的空值、换行、长度和特殊字符应被保留，执行模型不得自行改成更容易提交成功的数据。

没有页面入口的后端功能按 R32 使用已有触发入口。在用例中记录触发方式、参数、预期状态变化、观察渠道和依赖服务；入口或必要条件缺失时列为未验证，不因读到了代码就判定通过。已有命令也不得修改被测源码、配置或依赖，项目启动仍由用户负责，数据库仍只读核验。异步任务需关联任务标识、日志与最终结果，不能把接口接受请求或命令正常退出等同于业务执行成功。手动触发任务验证的是相应处理逻辑；定时调度是否会自动触发，需要另有对应证据。

没有设计稿时，结合布局规则、截图理解和历史对比判断视觉问题。首次截图是观察证据，不自动成为正确标准。对比需要考虑窗口尺寸、数据、加载状态、字体和动态内容；视觉差异并不必然是缺陷。可明确证明的异常与需要用户判断的样式疑点应分别呈现。

**异常恢复、数据与时间场景及执行中补充用例**

R49 的异常检查属于完整功能测试的默认范围。每条用例先确定受影响的页面或请求、异常发生时机、持续或结束条件、恢复方式及预期结果，再在受控测试浏览器内执行。模拟范围限于相应测试目标，不应切断应用自身模型调用或其他用例的连接。执行器需要确认模拟实际生效，并在结束或恢复任务时核对模拟是否已解除；未能可靠制造或解除条件时记录执行问题及受影响项。浏览器模拟错误响应的结果用于判断该条件下的页面处理，不能据此认定真实后端故障及其恢复已经验证。提交结果不明确时，仍按既有规则先核验业务状态，避免恢复时重复提交。

R50 的数据准备是可追溯的测试步骤，记录目标状态、准备入口、实际记录与依赖；使用已有数据时记录其来源，清理遵守 R33。文件按项目实际支持的类型、结构及业务规则准备，存放在应用拥有的位置；核验适用的字段、记录数、精确值、换行、编码或展示等实际结果，不能只凭成功提示或文件存在判为通过。准备失败不能当作对应业务已验证；数据准备也不能替代被测页面必须执行的交互。

R51 的时间用例记录触发时刻、相关时区、预期到期时刻或允许时间窗口、观察渠道及实际观察时间；未明确的业务时限在开测前澄清。任务等待业务时间期间保存状态，调度其他独立用例；等待本身不需要持续调用模型。应用重新打开时核对是否已到期及是否错过观察窗口，再决定可以验证的结论。观察到最终状态不能凭空补出未记录的准确触发时间。未到验证时刻的项显示“等待业务时间”，可生成阶段报告，不能提前将整轮判为完成。真实定时触发与通过现有入口提前执行处理逻辑分别记录，仍遵守源码和配置只读边界。

R52 按实际功能选择有来源的历史记录、附件、会话和缓存进行兼容检查；来源版本无法确认时如实记录未知。历史材料须有对应的预期与证据，新版本生成的数据不能冒充旧版本产物。此项在用户已启动的版本上验证兼容结果；自动部署旧版本、执行升级或迁移不属于当前确认的执行流程。无法取得历史材料或无法重建所需条件的项目，在报告中列出缺口。

R33 会清理不需要保留的本轮新增数据，因此不能同时假定每轮成功用例的数据都会留给未来兼容测试。当前优先使用用户已有或提供的历史材料；报告与证据保留不等于业务数据库中仍存在对应记录。若以后需要由工具长期保留成功用例的业务基线数据，应单独调整清理规则，不能借 R52 自动扩大保留范围。

R53 要求执行期间将新发现的入口、角色状态或动态功能与原清单核对。预期明确且处于本次测试范围及既有操作授权内时，先形成新增用例和计划版本，再执行；记录发现时间、依据及覆盖数量的变化，不倒填用例冒充预先设计或已经执行。新增业务疑问按 R28 处理。增补不覆盖已执行用例及其规则版本，也不自动改变已确认的业务预期或生效 skill；若发现部署版本变化，同时按 R44 处理。

长任务遵循以下行为；状态和恢复协议见 DD07–DD08。官方后台运行、Jobs 或日程消息均不能单独替代持久测试状态。

| 场景 | 行为 |
|---|---|
| 临时超时、限流、服务错误 | 记录失败并自动重试，采用退避等待；界面显示正在恢复及原因。 |
| 等待到期、定时任务等业务时间 | 保存触发与预计核验时间，显示等待状态并继续独立用例；到时恢复核验，重新打开应用时核对是否错过必要观察窗口。 |
| 主模型持续不可用 | 在配置允许、能力适合的模型范围内切换备用模型，并记录实际路由。 |
| 单条用例发现缺陷 | 保存失败结果，继续不受影响的用例。 |
| 浏览器异常、页面变化 | 重新观察状态，恢复前置条件；避免根据过时控件信息继续输入。 |
| 登录失效 | 尝试自动恢复；必须扫码、填写验证码时进入等待接管状态，保留进度。 |
| 凭证失效或必须人工解决的问题 | 在所属会话提示并保存待恢复任务，不把永久错误无限重复调用当作进展。 |
| 用户关闭窗口 | 保留后台任务及所需浏览器资源，继续测试；不能因销毁聊天窗口而取消任务。需要前台的电脑操作仍需满足相应执行条件。 |
| 用户明确退出应用 | 保存进度及在途操作状态，停止执行并退出。 |
| 崩溃、退出或电脑重启后重开应用 | 核对环境、登录、用例前置条件与已提交操作后自动续跑；主动暂停或取消的任务不自动继续。恢复粒度按 DD07–DD08 执行，不包含开机自启动。 |
| 电脑控制与普通对话同时使用 | 会话切换不终止测试；系统鼠标键盘由一个执行者占用，界面显示占用状态。 |
| 无可用真实外部服务 | 按 R25 跳过对应外部步骤；其他能够独立验证的部分继续。 |

模型请求重试和业务操作重试必须分开。例如点击提交后超时，恢复时先核实提交结果，不能直接重做并产生重复数据。用例之间也需要管理数据依赖，避免删除测试破坏后续用例的前置条件。

测试数据按 R33 管理。为本轮创建的数据记录所属批次、实体标识、关联用例、创建依据和依赖关系，清理时先排除缺陷复现及其关联数据；待确认或待补测用例仍需依赖的数据也暂时保留，并注明原因。不能仅凭名称或时间猜测某条数据属于本轮。删除关联记录前核对级联影响，无法确认归属或影响范围时保留并报告。先持久化测试结果及证据，再执行清理，将保留清单和清理结果作为报告补充记录保存。清理仍通过允许的业务入口进行，不直接写数据库，不修改源码、配置或依赖，也不绕过真实第三方操作确认规则。已经被删除流程移除的数据，保留其必要的准备和操作记录，不能承诺所有缺陷都能靠保留一条现存记录直接复现。

“持续执行”不意味着电脑断电后仍能运行，也不意味着可以自动完成所有短信或扫码认证。任务状态包括：待执行、执行中、恢复中、等待用户、等待业务时间、已暂停、封存待恢复、已结束、已取消。“已结束”另附验证完整或覆盖不完整的结论，不隐含产品全部通过。用例结果另行记录通过、失败、阻塞、跳过、未执行和待确认；状态转换以 DD07–DD08 为准，并同时满足 R28、R36、R37、R51。执行完成度与产品质量结论分开表示。

skill 与对话遵循以下行为。

- 区分全局和项目关联的 skill，沿用 DSH 格式和发现机制；应用自己的保存位置不写入被测代码仓库。
- 普通对话可以引用项目代码、报告、截图及具体问题；不关联项目时不默认带入其他项目材料。
- 修改前展示目标 skill、适用范围、改动内容、理由及相关测试证据。支持接受、修改后接受、拒绝和暂存。
- 保存修改历史并支持回退；运行中的测试固定使用本批次的规则版本，新修改默认用于后续批次。
- 自动建议不能把已观察到的错误实现写成正确预期，也不能为了获得通过结果而放宽断言。
- skill 中的流程知识与账号凭证分别管理；存储、引用和使用界面遵循 DD03、DD05 和 DD11。

R20 保留 DSH 的对话、会话和知识交互体验，实际工具能力受 R12 的只读要求约束。被测项目的 AGENTS、已有脚本、skill 或页面内容可以提供项目知识，但不能覆盖本应用的源码只读、外部业务确认及测试结论规则。只读要求应落实到文件、命令与桌面操作的实际执行路径；仅写入提示词或事后检查文件差异不构成执行约束。

C01 的保护程度为当前 Windows 账户下的“受控操作”。允许测试浏览器、文件选择框等相关窗口和经过校验的已有命令；不能确认源码安全的操作先阻塞并报告，不为了完成测试开放任意终端或桌面控制。其保证范围为本工具所有受支持入口的执行限制，不宣称与独立账户或操作系统隔离等强。实现及验收见[DD03](../architecture/2026-09-28-web-testing-design-execution.zh.md)和 AC12／G06。

模型分工的候选方案如下。路由应改变执行方式，不改变已选测试范围和验收标准。

| 工作 | 候选处理方式 |
|---|---|
| 代码检索、差异、长度及金额等精确计算 | 确定性程序。 |
| 需求推导、复杂计划、跨模块分析 | 推理能力较强的文本模型。 |
| 已明确且页面状态匹配的步骤 | 执行器直接操作并核验。 |
| 当前页面中的操作与目标选择 | 合格的轻量结构化决策模型；Jev 仅为候选。 |
| 需要生成的业务文本 | 小型文本模型，适合时提前生成和复用。 |
| 截图理解、视觉异常、复杂定位 | 视觉模型。 |
| 疑难失败解释、报告说明、skill 草案 | 文本推理模型结合实际证据。 |

轻量决策模型适配保留结构化状态和有限动作选择，结果由执行器校验。低置信度、候选不完整或反复无进展时转交更合适的路径；置信度不能代替结果断言。输入只保留当前任务所需信息，避免每一步重复发送完整源码、完整历史或无关页面内容。

轻量模型输出是待校验的决策，不直接拥有浏览器控制权；它与视觉、文本模型共享受控执行入口。模型接入、日志、重试和资源生命周期按 DD10–DD11 实现，不把任何示例执行器的能力当作本工具已具备能力。

**桌面、浏览器与显示边界**

采用官方 DSH 桌面、Host、Client、会话、托盘与标准退出界面；测试专属能力通过插件、服务和必要的受控执行适配增加。技术版本、规则与修改登记以[基座与上游升级](../process/2026-09-28-web-testing-upstream-baseline.zh.md)为准，不能使用浮动主分支或热替换运行批次。

内置浏览器是日常测试主入口；应用控制独立 Chrome／Edge 完成嵌入环境受限的流程，必要原生交互由 Windows 受控执行。浏览器载体由 P01 在同等场景下比较官方 webview 与 WebContentsView 后决定，不预设哪一条维护成本更低，也不开发两套完整宿主再选择。

独立浏览器是应用执行的补充路径，仍须记录步骤、证据和报告；只有确需验证码、扫码等条件才交给用户接管。不能假设外部登录自动传回内置浏览器；相关后续业务可在同一外部会话完成，并注明实际环境。内置 Chromium、Chrome 和 Edge 的结论各自归属真实执行环境，修改 User-Agent 不能充当另一浏览器的验收。

浏览器能力边界在 DD02 的矩阵逐项记录：输入和按键、多标签／窗口、跨域 iframe、Shadow DOM、富文本／Canvas／拖拽、上传下载、权限提示、打印及输入法。不能把所有弹窗改为当前页导航、把路径上传算作原生选择框验证，或把粘贴中文算作输入法候选验证。当前载体不支持的首版承诺项属于待实现能力，不得静默删除。

多角色会话按项目、身份和用例隔离，支持新建干净状态及保留登录状态；重建浏览器后仍须核验业务前置条件。接管前停止新派发并处理在途动作，归还后重新观察，旧元素或坐标不能继续使用。需要前台的输入与原生操作必须满足焦点、窗口和桌面条件，不承诺全部后台执行。

被测页面与应用界面隔离；页面、子框架和弹窗不得获得 DSH 文件、模型凭证及桌面 IPC 权限。保持真实网页限制，不通过关闭跨域限制或一概忽略证书错误取得通过结果。

应用自身窗口尺寸、布局和界面缩放由官方桌面能力及适用布局决定，保留窗口调整状态；窄窗口允许折叠侧栏或切换对话与浏览器，不以固定参考尺寸造成操作区不可访问。应用须处理高 DPI 及不同缩放显示器间移动；Windows 物理像素、窗口逻辑尺寸、界面缩放、网页 CSS 视口及浏览器缩放分开记录与换算。

被测项目首次配置或要求变化时，在用例阶段询问并保存视口宽高及有要求的浏览器缩放、DPR／显示条件；可依据代码响应式断点给出候选，复用无变化的已确认配置。应用窗口或屏幕分辨率不自动成为网页测试视口。折叠侧栏、调整窗口或界面缩放不能静默改变测试条件；预览缩放不能代替对应视口的真实执行。环境不能满足目标条件时，记录具体缺口。

工程验收遵循基座文档指定版本的官方根目录及就近目录规则。按改动选择类型检查、静态检查、行为测试、快照、构建和文档检查；完整覆盖率及平台矩阵按适用的官方 CI 要求执行。不能通过关闭规则、伪造测试结果或将未执行项计为通过来声称符合规范。仓库与规划文档已经落位；应用实现、运行检查及集成验证尚未完成。

工具交付验收与被测项目的单轮结论分别定义。报告如实记录未验证项，是结果真实性要求；如果首版承诺的功能因工具自身缺少能力而无法执行，该能力仍未完成交付，不能仅靠生成“未验证”报告通过验收。58 条需求在[验收标准](../testing/2026-09-28-web-testing-acceptance.zh.md)映射到具体行为、成功及失败场景和所需证据；最终候选验收仍待完成。所引用的 DSH 工程代码覆盖率要求适用于本工具开发，不代表用户项目已经获得代码行或分支覆盖率。

报告形式、覆盖统计、缺陷内容、编程助手交接材料及待确认项处理以[测试用例与报告规格](2026-09-28-web-testing-test-case-report-spec.zh.md)为准。实现可以细化排版，不得删减规定字段和证据。

应用内对话给出摘要并打开可展开的报告；导出离线 HTML 供用户查看，Markdown 与结构化 JSON 供编程助手读取，证据随包携带。报告必须包含完整用例结果、缺陷、覆盖缺口及待确认问题，不能只列发现的 Bug。历史报告不可被补测结果覆盖。默认记录操作步骤、关键截图、失败证据和相关日志，全程录像按需开启；报告和必要证据默认保留，由用户管理清理。具体证据采集按 DD02、DD06 和 DD09 实现。

具体项目开测前仍需提供或确认：代码与运行入口的对应关系、账号角色、环境性质及数据范围、必要运行证据、业务关键预期、测试视口和已有回归基线。这些是项目参数，不重新协商已确定的产品范围。

本文件定义产品要求；实施顺序及验证门槛见[开发里程碑与验证计划](../process/2026-09-28-web-testing-milestones.zh.md)，各 agent（智能体） 的职责、文件所有权及交接方式见[agent 开发与协作指南](../process/2026-09-28-web-testing-agent-guide.zh.md)。
