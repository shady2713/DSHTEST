# @deepseek-ai/dsh-web-test-models

[English](README.md) | 中文

## 概述

本包只负责回答一个问题：这个会话能不能跑、跑在哪。它决定每种任务类型可以用哪条提供方路由，以及一次连接测试实际证明了什么。它按各提供方自己的协议发出真实请求，把结果分类为密钥错误、模型不可用、模态不匹配、必须改动的请求、配额耗尽或瞬时故障，并把每条选择绑定到其验证所依赖输入的摘要上。凭据变更会把被中断的工作停进可恢复等待，并保留它原本的路由。

<a id="use-this-package"></a>
## 使用本包

组合层把本服务挂到 LLM 运行时与凭据服务之上，并声明唯一随部署变化的选项：一条已存储的选择在多久之内仍然有效。

```ts
import type { Context } from '@deepseek-ai/cordis'
import WebTestModels from '@deepseek-ai/dsh-web-test-models'
declare const ctx: Context
await ctx.plugin(WebTestModels, { verificationTtlMs: 600_000 })
// Official settings automatically persist selections and resolve provider apiKeyEnv references.
```

调用方索取路由，得到的要么是一条选择，要么是一个封闭的原因：

```ts
import type { Context } from '@deepseek-ai/cordis'
import type { ModelRoute, TaskRoute } from '@deepseek-ai/dsh-web-test-models'
declare const ctx: Context
declare function render(reason: Extract<TaskRoute, { kind: 'not-ready' }>['reason'], detail: string, rejected: Extract<TaskRoute, { kind: 'not-ready' }>['rejected']): void
declare function run(route: ModelRoute): Promise<void>
const decision = await ctx.webTestModels.selectRoute('analysis', { reverify: true })
if (decision.kind === 'not-ready') render(decision.reason, decision.detail, decision.rejected)
else await run(decision.selection.route)
```

### 哪些可配置、哪些不可配置

验证窗口可配置。官方 settings 在 models 的 Loader entry 下持久化 `selections` 与仅追加的 `policies`；凭证引用从提供方目录的正式 `settingsNs`／`settingsPath` 读取，缺持久存储明确失败。配置不能放宽就绪判定、任务最低能力和凭证变更后的可恢复等待。

<a id="understand-the-implementation"></a>
## 理解实现

### 分类顺序就是契约

一次真实请求产生一个分类，顺序决定它。

1. **harness 自己抛出的 code。** 缺失或格式错误的密钥、以及适配器无法解析自己的模型，都是先于任何提供方正文就成立的事实。
2. **模型装不下的请求。** 上下文窗口溢出不判为 `transient`，因为重复它还会溢出；该变的是请求本身。它先于各状态步裁定，因为正文即使同时报告了服务端故障，描述的仍是一条需要缩短的请求。
3. **`5xx`。** 提供方在报告自己的服务端，因此它正文里关于模型、模态、密钥或账户的任何措辞都不成立——`500 internal error: unknown model in cache shard 7` 与 `500 upstream returned 400 insufficient quota for shard 3` 都是服务端故障，因为 `5xx` 是产出那句话的进程的事实，而不是所寻址路由的事实。
4. **明确的凭据措辞。** 正文说被拒的是凭据本身时，优先于同一句里点名的任何模型、配额或地址：`invalid api key: this key may not use model gpt-4o` 判为凭据，`invalid api key supplied; see our models page` 也是凭据——其中的 "models" 位于一句帮助语里。多数分支既点名密钥又对它作出判断（`invalid api key`、`api key is expired`）；其余分支陈述的是该引用得到的结果而不是它的过错——未认证（`unauthorized`、`unauthorised`、`authentication`、`not authorized`、`not authorised`）或被直接拒绝（`permission denied`，以及 `access denied`——网关拒绝某个资源时用的就是这句话，而被拒的资源正是凭据被拒的东西）。它们全都在评判调用方，而 `your api key has exceeded its rate limit` 里的那个名词一个都不是：那是一把触到请求速率上限的可用密钥，因此判为 `transient`。这一步排在配额耗尽与 `404` 之前，是因为密钥本身被拒时给账户充值没有用；也因为 `404 unauthorized`、`404 "Access denied"` 与 `404 "You are not authorized to perform this action."` 是同一句话、只能有一种读法：拼写不能改变结论，同一句正文落在 `400` 上同样是凭据，而不是一次重试。
5. **配额耗尽。** 账户层面的事实优先于该账户上关于某一个模型的一切事实：同时点名"模型已弃用"与"配额已耗尽"的 `400` 判为"付费"，因为耗尽账户上任何模型都跑不起来。`QUOTA` 或 `ACCOUNT_QUOTA` code、正文声明配额的 `404`，以及 harness 自己的 `isQuotaExceededError` 读不出的提供方措辞都落在这里。`402` 并入这一步而不是单列一步，因为它的状态码名称本身就是答案，正如 `415` 对模态那样，而且它此前在顺序里根本没有对应步骤——因此一条 `402` 的耗尽账户此前完全依赖措辞。`Your credit balance is too low. Please top up` 与 `Your usage limit was reached` 在该匹配器之外；`Billing hard limit has been reached` 与 `Your account balance is insufficient` 则把结论放在名词之后、或整个从句之后，而不是紧挨着名词。"rate" 被有意排除，因为每分钟的请求数上限该由"稍后再来一次"回答，而不是靠充值。
6. **`404`。** 请求走到了提供方的路由层而地址不在那里，无论正文回显了什么都是模型答复，因为走到这里的请求已经通过认证。正文声明配额的 `404` 在第 5 步已裁定，因此不受本步影响。
7. **`401`。** 提供方拒绝的是凭据本身，无论正文还提到了什么。
8. **模型答复。** 正文点名模型，或某个 `4xx` 拒绝了一个**被点名的授权**：授权／权限措辞之后，在同一子句里跟着它所针对的对象。这条拒绝在任何 `4xx` 上都要读，而不只在 `403` 上：正文已经写明了拒绝，而 `400 "not permitted to use model gpt-4o"` 与 `400 "not permitted to use this API"` 就是 `403` 会给出的同样两句话；把这条读法绑在提供方自己挑的一个数字上，等于把一条被永久拒绝的请求送进无界重试——而 `400` 恰恰是提供方最常用于这类拒绝的状态码。两个要件仍然都必需，因此不含拒绝措辞的正文不算，无论里面有多少数字：`Forbidden: request id 12345`、`Access denied to resource 7f3a-22` 与 `error 403 (region: eu-west-1)` 都没有说出一个拒绝。被点名的对象是一个**复合提供方标识符**——只由字母、数字、`-` 与 `_` 构成，至少由一个分隔符连接，每一段都是字母数字，且至少含一个数字——或者 "model" 这个词本身；该对象不必是 "model" 这个词：`You are not entitled to gpt-4o-vision-preview` 点名了一个模型，而 `Insufficient permissions for this API. See our models page.` 没有点名任何模型。判据是 token 自身的构造，而不是一份主机名单，因此 `gpt-4o-vision-preview`、`deepseek-v4-pro`、`gpt-5-turbo` 与加引号的 `"gpt-4o-mini"` 都算数，而点分地址、`host/path` 形式的文档链接、裸端口与加引号的句子都不算：`.` 或 `/` 引入的是主机、点分版本或路径，而没有分隔符的裸数字是计数或端口。两个要件之间的填充也不得跨越逗号、冒号或括号，因为它们开启的是列表、标签或旁注，而不是延续同一个从句。仍然有一类形状是模糊的、且被判作模型目标：两段的 `<word>-<blob>` id（例如 `org-9f2b`）与两段的模型 id（例如 `gpt-4o`）无法区分，而排除该前缀会把每一个真实的两段模型 id 一并排除。
9. **模态答复**，当提供方在一句话里同时说出两件事时，它携带的是其中更强的一个断言：`400 "This model does not support image input; your plan does not permit it"` 判为能力答复，因为旁边那句拒绝措辞没有点名任何具体对象，否则会被读成凭据。只有 `400`、`415`、`422` 能成为模态答复，因此携带模态措辞的 `403` 仍然是"拒绝调用方"。
10. **点名了对象以外内容的 `4xx` 拒绝。** 拒绝措辞若在同一子句里没有跟着对象，就是对凭据的拒绝——拒绝的是密钥、账户，或整个 API——无论它落在哪个 `4xx` 上，因此带着 `Your account is not permitted to use this API` 的 `400`、`422`、`429` 与 `418` 都判为 `rejected-credential`；一条声明了拒绝的 `429` 是那条拒绝，而不是它的状态码名称所暗示的重试。
11. **`403`。** 走到了提供方、拒绝了调用方、没有点名任何模型，且没有写出本包能读出的拒绝。
12. **`408`、`425` 或 `429`。** 这三个状态码的自身名称表示"此刻还不处理"，而不是"按收到时的样子拒绝这条请求"，因此逐字相同的另一次请求很可能成功。`409` 不在其中：冲突说的是请求与某个状态不一致，而不是"稍后再来"。
13. **其余任何 `4xx`。** 提供方按收到的样子拒绝了这条请求，而本包没能从正文读出任何原因，因此判为 `rejected-request`：那就是处置——改掉所发的东西——而逐字相同的重试无法解除一次拒绝。`400` 上"模型装不下的请求"也由此得到回答，这正是 `400 "prompt is too long: 210000 tokens > 200000 maximum"` 不再是一次重试、且不需要自己那份词表的原因。代价是：`rejected-request` 同时也是"模型装不下的请求"所用的判为，因此真实处置其实是换模型、换凭据或充值的 `4xx`，会被冠以"请求"之名。另一个选项是 `transient`，而它声称"逐字相同的另一次请求未必会重复失败"——没有任何 `4xx` 支持这句话。
14. **其余一切判为 `transient`**：传输失败、重定向、自相矛盾的失败对象上出现的成功状态码，以及本包从未见过的任何正文。对这些失败，唯一诚实的说法只是"逐字相同的另一次请求未必会重复"。

三条规则让模糊的状态码可判定：对"是谁的问题"的明确解读优先于顺带提及，这正是把顺带提到某个模型的密钥拒绝与模型授权区分开的那条规则。状态码只收窄范围，本身不决定分类——除非状态码**就是**答案：`415` 在状态码自身的名字里写明了输入类型，`422` 是提供方解析了负载并拒绝，`400` 是纯文本路由的答复，而 `5xx` 永远不评判该路由、该密钥或该账户。第三条是 `4xx` 是什么：提供方按收到的样子拒绝了这条请求。因此它的正文在任何状态码上都要读，而且没有任何 `4xx` 是 `transient`——`transient` 赖以成立的说法是"逐字相同的另一次请求未必会重复失败"，而这对于一条已经被拒绝的请求不可能成立。

### 能力要么被声明，要么就不存在

路由选择按能力匹配，且需求在花掉请求之前就已裁定。任务类型声明它需要的模态；只有归属适配器声明了该模态的候选才被接纳。没有声明任何模态的适配器并不是"纯文本路由"——它是一项能力未知的路由，而未知不能满足需求。因此纯文本路由永远不会服务视觉任务，该任务类型会报告 `capability-absent`，而不是被送往读不了图像的地方。

`toolUpdate` 原样取自适配器自身的声明。缓存 token 上报不是本包断言的提供方特性：它读自探针真实响应所上报的 token 用量，因此某条路由的提供方若未上报缓存字段，就被记录为没有缓存，任何界面都无法在本包未曾测量过的提供方之间承诺缓存收益。

### 选择绑定在它被验证的对象上

一条选择之所以就绪，是因为一次真实请求在仍然成立的输入上作出了答复。持久化记录携带所选的提供方与模型、本版本的 schema 版本、验证时刻，以及对提供方目录条目、适配器解析出的精确模型元数据、路由凭据引用三者的 SHA-256 摘要。实时摘要不同的记录会先由一次新的真实请求重新验证再继续提供；不愿付出请求代价的调用方会收到 `reverification-required`。

记录的模态列表是摘要**无法**承载的事实，因此它要对照实时声明进行比较，而不是被假定。摘要覆盖的是适配器**关于**该模型公布的字段；能力记录把模态列表并排放在同一文件里，因此一份被手工编辑过的列表仍然带着一份有效的摘要。列表与适配器当前声明不一致的记录——更宽或更窄——都会被拒绝并报为 `reverification-required`，而不是被读成 `capability-absent`，因为只有真实请求才能说清两者中哪个才是当前事实，而实时声明很可能正带着记录所缺的那个模态。已存储的记录还要与它被提供时所在的那只时钟比对：晚于当前时刻的验证时刻能满足任何窗口，因此本机时钟读作未来的 `verifiedAt` 会被拒绝，而不会被当作刚刚验证过。

设置文档是用户可以手工编辑的文件，因此消费方读取的每个字段都被检查而不是假定：schema 版本、摘要、路由及其凭据引用、能力记录及其每个字段、任务类型、验证时刻。本版本读不了的记录——`capabilities.inputModalities` 被写成字符串 `"image"`、本版本不路由的模态、不在凭据语法内的引用、封闭联合之外的任务类型、某个任务类型键下的 `null`——都不是选择。调用方允许时它由一次真实请求重新验证，不允许时它被报告为 `reverification-required`；它绝不会按写下的样子被服务，而存放在与其自身任务类型矛盾的键下的记录同样被拒绝。一个被拒绝的值只让那一个任务类型失去决策，因此一次手工编辑无法让整份概览失效。需求只能由模态的**列表**满足，因此字符串永远无法满足需求。

### 凭据变更会停住工作；既不丢弃，也不改道

`credentials/reference-updated` 会把所有正在运行、且其绑定路由正是通过该引用取密钥的工作停进可恢复等待。票据保留自己的身份、任务类型、原本的路由，以及打断它的引用；第二次变更不会重启等待，而绑定到其他引用的工作继续运行。恢复时只针对**那条**路由发出真实请求，要么返回同一条路由，要么报告等待继续。恢复期间绝不重跑选择，因此在途请求无法更换模型，且 `WorkRegistry.resume` 会拒绝任何指向其他路由、或携带拒绝而非答复的报告。

等待同样能挺过其他操作。报告一个被停住的单元"已完成"会被拒绝：被中途打断的工作并没有完成，把它结算掉会把它从等待中丢弃，因此票据会保留其路由、停住原因以及打断它的引用，直到它恢复，或被 `forgetWork` 丢弃——这是调用方结束一个已决定不恢复的被停住单元的唯一方式，而且并不声称该工作已完成。当一次决策里既有真实拒绝、也有目录阶段已排除的能力缺失时，首行会同时点明这两类，因此绝不会声称一条从未发过请求的路由"未通过连接测试"。

凭据变更会使已存验证失效，并停放受影响的票据，不会选择另一条路由。配置、规划和恢复要求探测前观察到的凭据代次一直保持到持久写入完成和就绪发布。探测后的模型查询或写入期间发生变更，均须重新探测；较早的在途写入不能清除该失效标记，也不能通过覆盖较新的已验证记录恢复就绪。停放票据仍可通过 `waitingWork` 与 `resumeWork` 在原路由上恢复。

### 凭据引用是名字，绝不是值

路由携带其提供方配置档案取密钥所用的 `CredentialRef`，正是这个名字让凭据变更可以归因到受影响的工作。本服务从不读取或存储凭据值，也绝不把凭据值放进请求：界面使用的读取半边是 `CredentialInfo`，它没有值槽位；探针自身的请求由路由与任务类型构成，值只会在适配器内部、由拥有它的凭据提供方送到提供方。

提供方失败先在内部按原文分类。返回的失败、诊断和导出仅含闭集原因及合法 HTTP 状态；自由文本 message、code、requestId、地址查询参数和 Authorization 均被丢弃。清理过程不读取凭证库。

### 策略是规则集；选择是已验证的事实

`RouteSelection` 回答"这条路由是否答过"。`RoutePolicyRevision` 回答另一个问题——对这类任务，走哪条路由、备选是什么、超时多少、哪个校验器、什么升级条件——两者并存。规则集没有验证就是未经验证的，验证没有规则集则对同类任务的下一件事无所不谈，所以谁也不取代谁。各自携带自己的模式版本，并列存在：选择是 `web-test-routes/1`，策略是 `web-test-route-policy/1`；任一版本本发行版不认识的记录都读作不可读，而不是被强行套用。

一条策略点明任务类型、在该类型可被送往某条路由之前该路由必须声明的能力、主路由与备选路由以及各自钉住的确切模型版本、输入生成版本、请求与整段任务的时限、结果必须通过的校验器，以及运行停止并交出控制的条件。其中没有任何一项是由某次请求证明的，这正是它与选择的区别。

**字段都是 `readonly`，原因就是不可变性。** 运行在某一个修订版下被接纳，并从接纳它的那条记录读取自己的 `routeRevision` 与结果归属，因此后来的修订版无法改写已在途中的工作的归属。修复凭据是在某个引用之下写入新值；引用是名字，所以已记录的选择逐字节不变。模型或能力的变化因此**签发新的修订版**，而不是改写当前修订版——这让"不静默热换运行规则"成为可检验的事实，而不是一句愿望。

**做不了这项工作的路由被拒绝，绝不被降级。** `satisfiesPolicy` 返回候选路由缺少哪些能力，而不是返回一条可以改送的路由，因为"因为可用"而非"因为能读这张图"而挑中的备选，正是 `requiredCapabilities` 要防的失败。同一条规则也管着存储读取：`parseStoredPolicy` 检查它交出的每一个字段，拒绝路由点不出模型的记录，并返回 `undefined`，让调用方从实时配置重新签发策略，而不是在读不懂的规则下运行任务。

**超时是可恢复失败，取消是控制结果。** 两者触发同一个 `AbortSignal`，因此 `classifyDeadline` 靠对照策略自身时限的已用时长或显式取消来区分，绝不只看信号；超时带 `recoverable: true`，因为补救办法是在备选路由上再发一次请求。于是 `deadlineDecision` 把超时的请求送往已声明的备选，没有备选时升级，而任何超时都不会被报成取消。校验器拒绝同样绝不被读成模型拒绝：模型答了，只是答案没通过本策略声明的某项检查，所以 `validateAgainst` 返回自己的判为类型，而不是把结果塞回连接判为。策略未声明的校验器也不会被静默执行——运行会升级，而不是自行扩大规则。

`selectRoute(taskType, { reverify: false })` 与同选项的 `survey` 仅报告仍可复用的持久选择；无记录、不可读、失效或无法满足任务的记录均返回未就绪，不执行模型探测或持久写入。调用方须显式传入 `reverify: true` 或使用 `configureRoute` 才能验证并保存路线。

应用启动后，持久选择必须先执行一次真实验证，因为凭证可能在应用停止期间改变。成功写入后，运行中的应用可在配置的验证窗口内复用；观测到凭证变更则使该复用失效。

复用资格属于本进程验证的完整选择记录。状态读取期间若凭证改变，返回未就绪；另一条路线成功保存不能使该读取的旧记录获得验证。

`getPolicy(kind)` 严格读取最新持久化修订；`issuePolicy` 对主路线和备选路线执行真实探测，并检查全部最低能力后追加不可变修订。`admitPolicy` 重新验证主路线，返回冻结的 `PolicyRecord` 与凭证等待票据。`exact-value` 从不派发模型；解析列表和接纳路线均为独立副本。

### 六类任务类型，以及它们映射到的三种任务类型

这些类型比本包按模态路由的任务类型更细，因此每类都点名它满足的那个任务类型的要求，而不是假装自己就是其中之一：

| taskKind | 任务类型 | 默认能力 | 升级给谁 |
|---|---|---|---|
| `requirements` | `analysis` | 文本输入 | 来源或规则冲突时交给用户 |
| `candidate-selection` | `analysis` | 文本输入 | 交给会话本身，重新观测或等待 |
| `visual-inspection` | `vision` | 图像输入 | 交给会话本身，重新观测或等待 |
| `exact-value` | 无 | 确定性解析 | 语义未定义时交给用户 |
| `defect-explanation` | `analysis` | 文本输入 | 交给会话本身，拒绝无依据的结果 |
| `skill-draft` | `analysis` | 文本输入 | 交给用户，由用户确认 diff |

`exact-value` 不点任何任务类型，也不要求任何能力，因为它的规则就是确定性解析与比较，而"不要在不必要处引入模型判断"正是规则：把它派给文本模型，恰好会加上它所禁止的那种判断。本发行版不路由的类型由 `requireForKind` 拒绝、由 `knownTaskKind` 报告为不存在——绝不会用最接近的一类来回答，那与能力检查所防的是同一种静默降级。

<a id="model-experience"></a>
## 模型体验

### 被接纳的效果

#### 模型看到什么

什么也没有。就绪的路由会发出它一向发出的请求。选择本身不新增 Session 事件，也不新增模型输入；它只改变循环在构建请求前所寻址的提供方与模型，因此路由未变的重新验证之后，缓存前缀仍然有效。

#### Token 影响

只有探针自身的最小请求消耗 token，而且只在选择是被验证而非从仍处于 `verificationTtlMs` 之内的已存储记录读出时。

#### KV 缓存影响

本包自身策略不产生任何影响。记录的 `reportedCacheTokens` 是对提供方响应的观测，而不是对本包所发任何请求的改动。

### 被拒绝的效果

#### 模型看到什么

没有可用路由的任务类型不会被派发，因此模型看到的不是错误而是"什么也没有"。封闭的原因与诊断信息交给提出请求的界面，每条拒绝都带着它本来要走的路由以及未被选中的原因。

#### Token 影响

没有。被拒绝的任务类型不会被派发，因此本会验证候选路由的探针不会运行。

#### KV 缓存影响

没有。被拒绝的任务类型不发出请求，因此既不会新增可缓存的提示前缀，也不会使已有前缀失效。

## 已知限制与后续工作

<a id="known-limitations-and-deferred-work"></a>

这些限制界定了本包何时不适用。它们是当前的包内约束，不是任务待办清单。

- **视觉就绪需要图像输入。** 应用经官方附件 admission 提供 `probeImage`；缺图像时在发请求前返回 `rejected-modality`，真实图像 block 与适配器声明必须同时成立。
- **会为未列出模型合成元数据的适配器，使 `rejected-model` 经该适配器不可察觉。** DeepSeek 适配器会解析任何模型 id 并把其模态默认成文本，因此 `INVALID_MODEL_INFO` 在它身上永不触发，模型不可用只能从提供方自己的答复中观察到——而那需要可用的密钥。在此之前，这类路由被当作连接失败拒绝。该分类本身仍可通过另一适配器的 `NO_ADAPTER` / `INVALID_MODEL_INFO`，或通过提供方的 `404` 到达；缺的是一家真实提供方给出这样的答复。
- **一个超出 harness 匹配器形状的上下文溢出，由通用 `4xx` 读法兜住。** `400 "prompt is too long: 210000 tokens > 200000 maximum"` 此前判为 `transient`，调用方会重试一条必然以同样方式失败的请求。`isContextWindowExceededError` 能匹配 `maximum context length`、`too long for this model` 与 `exceed(s|ed) … context`，但匹配不了正文里给出两个 token 计数做比较的写法。现在它判为 `rejected-request`，而且**不需要**为它自己补一份词表：通用的 `4xx` 读法已经回答了这个问题，因为溢出的请求必须被缩短。这与上面的配额匹配器不同，后者是对 `isQuotaExceededError` 缺口的补偿，因为它要给出的处置（"付费"）与通用读法给出的处置（"改掉所发的东西"）不是同一个动作。
- **失败对象上的 `200` 按其正文来读。** `200 "internal error: insufficient quota"` 判为 `exhausted`。携带成功状态码的失败对象是自相矛盾的输入，而分类器读的是文本；本包不期待提供方真的产出这种输入。
- **URL 方案（scheme）被拒判为请求拒绝。** `400 "image_url must be one of the supported schemes"` 判为 `rejected-request` 而非 `rejected-modality`，因为正文陈述的是"这条请求如何携带图像"的事实——这个方案该路由不读——而不是"这条路由能否承载图像"；`MODALITY_WORDS` 点名的是输入类型或模态，而 `image_url` 是字段名。代价是这个判为只给出动作而不给出具体改法：处置是换掉请求（例如改用内联方案），而该改什么，正文里没有写。
- **封闭判为集合里没有一条能命名法律／策略层面的拒绝。** `451 "Unavailable For Legal Reasons"` 且正文无任何可读措辞时判为 `rejected-request`，这是集合里最不失真的一个：处置确实是"别再原样发这条请求"，但被冠以的名字是请求，而不是那项法律限制。
- **被 `4xx` 回答的传输故障会读成请求拒绝。** 网关用 `400` 回答 `upstream connect error or disconnect/reset before headers` 或 `Connection reset by peer` 时判为 `rejected-request` 而非 `transient`。harness 自己的 `TRANSPORT` code 在真实链路上从不带状态码（无连接可读），因此没有任何可依据的信号能把它与一次真正的 `400` 区分开，而为它新增词表是在没有观测的情况下猜测提供方的措辞。
- **点不出模型的路由在发出任何请求之前就地被拒绝。** 目录阶段会为适配器未注册任何模型的提供方记下 `model: ''`，而 `listModels` 调用失败的提供方同样不贡献任何模型，因此这一行是常态而非异常。流式发送其中任何一条，都会把一次真实的出站请求发到一个从未被点名的模型上，而提供方对这条畸形请求自己的回答，随后会被记成关于该路由的陈述。因此 `probeRoute` 返回 code 为 `EMPTY_MODEL` 的 `rejected-request`，且从不调用 `llm.stream`；选这一判为而不是 `rejected-model`，恰恰是因为它描述的是请求，而不是断言该提供方在此不提供该模型。

<a id="dev-note"></a>
### 开发备注

不发布运行时不变量的配套检查。本可以比对的三件事——实时提供方目录、实时适配器声明、已存储的选择——各自只被一个方法读取，而调用方据以行动的决策就是该方法的返回值，而不是可能与之分叉的第二次观测。

注册表按设计只存在于进程内。被停住的票据指向用户仍在查看的工作，它是运行中会话的事实而不是持久授权；"哪条路由被验证过"这一持久记录是已存储的选择，不是这个队列。
